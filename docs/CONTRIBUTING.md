# CONTRIBUTING: MOD を提供する

作った MOD を同梱に入れてほしいときに読む文書。
MOD の書き方は [TECH.md](TECH.md) にあり、ここではライセンス・送る前に揃えるもの・取り込みの手順を扱う。

MOD は同梱に入れるほかに、自分で配ることもできる。

| | 同梱に入れる | 自分で配る |
|---|---|---|
| 配る人 | このプロジェクト | あなた |
| 保守 | こちらが引き受ける（下記） | あなた |
| 番号 | こちらが振り直す | 自分で決める |
| 入れ方 | 次のリリースに入る | 受け取った人が GUI の `MOD を追加…` で入れる |

この文書は同梱に入れる場合を扱う。
自分で配る場合に守ってほしいのは「[名前がぶつからないようにする](#名前がぶつからないようにする)」だけ。

## ライセンス

提供は MIT で受ける。
このプロジェクトの配布と同じライセンスで、別の取り決めは無い。

- 著作権はあなたに残り、譲渡は求めない。
  名前は `mod.json` の `"author"` と [NOTICE](../NOTICE) に載る
- 同梱後は MIT で配る。
  あなたを含む全員が、再配布・改変・商用利用を MIT の条件で行える
- 取り込んだ後の保守（ゲーム本体の更新への追随、他の MOD との衝突の解消、ローダの API 変更への追随）はこちらで行う。
  あなたに続ける義務は無い

他のライセンスで配りたい場合は同梱できないが、自分で配ることはできる。
その MOD がローダの機能（`instantale_modloader.*`）を使うことは MIT が許している。

他人のコードを含む場合は、そのことを書いて渡すこと。
出所を確かめられないものは、配った後では取り消せないため、同梱を保留する。

## 送る前に揃えるもの

1つの MOD はフォルダ1つ。
最低限の中身は `mod.json`（メタデータ）と入口の `.py` の2つ。

```text
my_mod/
    mod.json
    my_mod.py       # apply(ctx) を持つ
    DOC.md          # 遊ぶ側から見た説明。無ければこちらで書く
```

テンプレートが `runtime/mods/_template/` にあるので、複製して使える。

| 揃えるもの | 見るところ |
|---|---|
| `mod.json` に `entry` / `api` / `kind` / `name` / `description` / `author` | [TECH.md §3.1](TECH.md#31-最小の形) |
| 入口が `def apply(ctx):` である | [TECH.md §3.1](TECH.md#31-最小の形) |
| Python 3.10 の構文で書く | ゲームに組み込まれているのが CPython 3.10。3.11 以降の構文は注入した時点でエラーになる |
| 書き込み先が `out\`（ログ）と `state\`（永続データ）だけ | [TECH.md §3.11](TECH.md#311-書き込み先out-と-state) |
| 設定を持つなら `"settings"` の宣言とコード側の定数の既定値が一致している | [TECH.md §3.8](TECH.md#38-gui-から変えられる設定ctxconfig) |
| `python tools/check_mods.py` が通る | [TECH.md §2.3](TECH.md#23-静的検査toolscheck_modspyは必ず通す) |
| タイトルが「入れると何が起きるか」の一文になっている。DOC.md は遊ぶ側に要ることだけ | [TECH.md §2.7](TECH.md#27-mod-の文書docmd) の「タイトルと本文」 |
| ソース・DOC.md・`mod.json` に、検証の経過と遊んだデータ（世界名・生成された人物の名前・セーブの中身・自分の PC のパス）が残っていない | [TECH.md §6.1](TECH.md#61-mod-とローダの作り) |

番号は付けなくてよい。
取り込むときにこちらで振る（下記）。
フォルダ名は内容が分かる名前であれば何でもよい。

`apply()` は1つのプロセスで何度も呼ばれる。
不具合の原因になりやすいので、
送る前に [TECH.md §3.4〜§3.6](TECH.md#34-まだ現れていない対象を狙う保留と再適用) を読んでおくこと。

取り込みでこちらが直すことが多いのは、次の4つ。
理由は [TECH.md §6](TECH.md#6-注意点ルール一覧) にある。

- ゲーム本体にある処理（値の計算・描画・生成）を自前で作り直している
- ラッパーが受けた引数を位置引数に直して `orig` へ渡している
- フックの中で `ctx.mod_dir` などの `ctx` の値を読んでいる
- 書いた後に追加された共通部品（[TECH.md §5](TECH.md#5-共通部品)）や、他の MOD との窓口を使っていない。手元のローダが古いと分からないので、送るときにどの版を元に書いたかを添えてほしい

### 名前がぶつからないようにする

MOD どうしが名前を共有すると、例外は出ずに片方の機能が効かなくなる。
次の4つは MOD ごとに別の文字列にする。

| 何 | 決まり |
|---|---|
| 自前ボタンのマーク（mark キー） | `mod_` で始めること（`ui.MARK_PREFIX`）。同梱が使っているものと重なれば `tools/check_mods.py` がエラーにする（[TECH.md §5.1.1](TECH.md#511-組み立て)） |
| プロセス内に保持するデータ（`sys` の属性） | 名前に `instantale` と自分の MOD 名を入れる（同梱は `_instantale_<自分の名前>_store` の形が多い）。検査はしていない |
| `state\` のフォルダ名 | 自分の MOD 名にする。他の MOD のデータを読むときはフォルダを作らないこと（[TECH.md §3.11](TECH.md#311-書き込み先out-と-state)） |
| ログの名前・LLM の `manager_name` | 自分の MOD 名にする |

意図して共有する場合は `mod.json` で宣言する。
他の MOD のデータを読む、相手が置いたマークを見る、はこのローダでの正しい連携の方法
（MOD どうしは import しない）。
その名前が自分のものでないと宣言しておけば、衝突と区別できる:

```json
"shares": ["npc_profiles"]
```

宣言が無いまま同じ名前を2つの MOD が使うと `tools/check_mods.py` がエラーにする。
規則は [TECH.md §3.2.3](TECH.md#323-mod-どうしは-import-しないローダの共通部品は共有する)。

## 送り方

GitHub の Issue か Pull Request で受ける。

- <https://github.com/Flossian/InstantaleModLoader/issues>

公式 Discord などの DM でもよい。

フォルダを zip にしたものでもよい。
動いている様子（ログ・スクリーンショット）があると確認が早い。

一緒に書いてあると助かること。

- 何をする MOD か。1〜2行でよい
- どのゲームの版で動かしたか。どのローダの版を元に書いたか
- ローカルの LLM とクラウドのどちらで試したか（両方あればその旨）
- 未確認のまま残っていること

動かない状態や、途中までの試作でもよい（`404_party_talk` は試作を受け取って正式化した）。

## 取り込みでこちらがやること

送られた MOD に、こちらで次のことをする。

1. 番号を振る。
   提供元を表す `4xx` の番号帯に入れる（提供された計測 MOD は種別どおり `2xx`）。
   番号帯の意味は [TECH.md §3.2.2](TECH.md#322-同梱-mod-の番号帯)
2. 同梱の環境に合わせる。
   他の MOD との適用順（`mod.json` の `after` / `before`）、重なる機能の調整、
   ローダの共通部品（[TECH.md §5](TECH.md#5-共通部品)）を使う形への書き換え。
   `runtime\mods\load_order.json` に名前を載せる（載せないと `docs/MODLIST.md` に出ず、
   `tools/build_mods.py --check` がエラーになる）
3. オフライン検証を1つ書く。
   `tools/tests/test_*.py`。ゲーム無しで動き、CI が全件を実行する
4. `DOC.md` を用意する。
   無ければこちらで書く。`docs/MODS.md` は各 MOD の `DOC.md` をまとめたもの
5. 作者名を載せる。
   `mod.json` の `"author"` に名前、[NOTICE](../NOTICE) に著作者として記載する。
   `docs/MODLIST.md` の「提供を受けた MOD」にも出る。
   `tools/check_mods.py` が検査するのは提供者の名前が NOTICE にあるかだけで、
   MOD ごとの行は見ない（同じ人の2つ目からは、載せ忘れても CI は通る）

既にある MOD への機能の提案（PR）も同じで、
`"author"` の末尾に名前を足す（先頭は元の作者なので動かさない）。
この場合は `docs/MODLIST.md` の「提案を取り込んだ MOD」に出る
（`130_currency_unit` / `314_area_move_custom` がこの例）。

2 で変えた内容は `docs/VERIFICATION.md` のその MOD の節に記録する
（DOC.md と `docs/MODS.md` は遊ぶ側に要ることだけを書くので、そちらには置かない）。
`409_fix_crafted_item_type` の節（VERIFICATION.md §3.104）がその例。
