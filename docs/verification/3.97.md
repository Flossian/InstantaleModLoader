# 3.97 街の出来事（`338_`）: 引き直し（#10）と手のマウス（#1）のほかは実機で成立・宿代の素の額の取り違えをローダで直した・良い出来事と表のファイル（版2）は実機で成立

開発中は `918_town_incidents` の名前で動かした。遊び方と設定は `338_` の DOC.md、実機の経緯は VERIFICATION_LOG.md [§2.92](2.92.md)。
記録は `out\town_incidents.log`。依頼を消す経路は GAME.md §2.9、画面左下のアイコンの列は GAME.md §2.34。

## 決めた仕様（再検討しない）

- 名前は「街の出来事」。疫病・魔物も入るので「治安」より広い名前にした
- 出来事は表のファイルから読む（同梱の `incidents.default.json` の18種と、足す出来事の `kinds\`。2026-10-13 に決めた）。中世ファンタジーに限らず、サイバーパンク・西部劇・ポストアポカリプスなど、どの世界でも成り立つものにする。呼び名と文は LLM がその世界の言葉で書く
- 困り事（15種）は放っておくと2段悪化して（兆し・悪化・深刻）、最後は自然に収まる。段の間隔（60日で1段・最後の段から90日で収まる・1回の日数送りで1段まで）と頻度（30日ごとに25%・同時に3つ（2026-10-13 に本人が2から変えた）・終わった街は180日休み）は設定で変えられる
- 良い出来事は解決の依頼を作らず、出来事ごとの段を進む（2026-10-13 に決めた）。祝祭・豊作・交易の活況は 兆し → 盛況 → 収束、にわか景気は 予兆 → 過熱 → 崩壊 → 収束（弾けて収まる4段）。起こりやすさは困り事の半分（表の `weight` 0.5）。「最盛期」は兆しから一段飛ばしの感があるので「盛況」、収まりかけは「下火」でなく「収束」にした
- 街の規模で起こりやすさを変える（出来事ごとの `size` と `weight`。重みの付け方は `incidents.weights`）
- 効くのは値段・宿代・会話・情景描写。難易度には触らない（`318_` と共有する窓口が無い）
- 宿代の段はローダの宿代の関所に置き、`315_` が決めた額の上に掛ける
- 発生の様子は、よその街の掲示板の貼り紙ではなく、ゲーム内の一覧（`122_` の形の窓）で見せる。アイコンは画面左下のゲームの4つを少し左に詰め、その右に置く。絵は注意の標識（色つきドット絵、普段・乗せた・押したの3枚）、窓に枠を付ける
- 一覧の日付（日数／あいまい）と影響（数字／言葉／出さない）は設定で切り替える。設定は独自の画面（6タブ・一覧の見本・記録）
- 街の勢力（`339_`）との連動は、この MOD から 339 への一方向。339 がこの MOD の控えを読み、この MOD は勢力を知らない
- ほかの冒険者（ライバル冒険者の MOD（開発中）など）が出来事の依頼を片付けたら、出来事はそこで終わる。
  誰が狙い・片付けたかはローダの窓口 `quest_claims`（TECH.md §3.3.18）に聞く（2026-10-13 まではその MOD の控え `state\rival_adventurer\` の `taken` を直に読んでいた。片付ける人物が増えても読めるように窓口へ移した）。
  終えたときに片付けた人の名前を出来事に残し（`end_by_name`）、終わった欄はその名前で書く（名前を残す前に終えたものは「ほかの冒険者」）
- 困り事の依頼は窓口 `quest_claims` に「急ぎ」として置く。ライバル冒険者の MOD はこれを、どの土地のものでも先に狙う（その MOD の設定で切れる）

## 控えの形

`state\town_incidents\<世界×主人公>.json`。
同じ世界で主人公を作り直したら引き継がない。
読む MOD は `WorldStore(ctx, "town_incidents", own=False)` で読み、`mod.json` の `shares` に `town_incidents` を書く（TECH.md §3.2.3）。
この形を変えるときは、読む側（`339_`）と揃える。

```json
{"events": [{"id": 3, "area": "2", "area_name": "灰の都", "kind": "epidemic", "stage": 2,
             "status": "active", "started": 120, "stage_day": 180, "ended": null,
             "end_by": null, "quest": "57", "goods": null, "tries": ["epidemic"],
             "text": {"name": "…", "rumor": "…"}, "told": {}, "good": false, "stage_name": "悪化"}],
 "seq": 3, "next_roll_day": 210, "cooldown": {"5": 400}, "cleanup": []}
```

| 項目 | 中身 |
|---|---|
| `events[].area` / `area_name` | 土地の id（文字列）と、起きたときの街の名前 |
| `events[].kind` | 出来事の英名。世界観に依らない（同梱は `outlaws` `epidemic` `invaders` `unrest` `shortage` `aftermath` `counterfeit` `hoarding` `anomaly` `abductions` `contraband` `crackdown` `power_vacuum` `influx` `boom` `festival` `harvest` `trade`。`kinds\` で足した英名も入る） |
| `events[].stage` | 1〜段の数（困り事は 1〜3 が兆し・悪化・深刻、にわか景気は 1〜4） |
| `events[].good` / `stage_name` | 依頼を作らない良い出来事か、いまの段の名前（版2 から。起きたときと段が進むたびに書く）。`339_` が段の名前を決め打ちせずに読むため。版1 の控えには無いので、読む側は無ければ 1〜3 を兆し・悪化・深刻と読む |
| `events[].status` | `pending`（文の答え待ち。まだ何も効かない）／`active`／`ended` |
| `events[].started` / `stage_day` / `ended` | 始まった日、今の段の起点の日、終わった日（ゲームの通算日数） |
| `events[].end_by` | `player`（プレイヤーが片付けた）／`rival`（ライバル冒険者の MOD が片付けた）／`natural`（自然に収まった） |
| `events[].quest` | 片付ける依頼の id。まだ作っていなければ null |
| `events[].goods` | 買い占めで選んだ品の種類。ほかは null |
| `events[].text` | LLM が書いた文（呼び名・段階ごとの概要と情景・店・収まり・依頼・噂）。無ければ表の文。版1 の控えの概要は段に依らない1文（`summary`） |
| `cooldown` | 土地の id → 次に起きてよい日 |

終わった出来事は直近の20件まで残す（`339_` は「前回から」の出来事を材料にする）。

## 作りの根拠

### 出来事の表

版1 は表を `incidents.py` の中に持っていた。
良い出来事を足すのに合わせ、出来事を外で足せるようにファイルへ出した（2026-10-13 に決めた。書き方は `338_` の DOC.md「出来事を足す」）。

- 表は MOD のフォルダの `incidents.json` があればそれ、無ければ同梱の `incidents.default.json`（`120_` の名簿・`132_` の種と同じ名前の分け方。TECH.md §3.1.1.1）。同梱の既定を書き換えた人の分は、更新のときに `incidents.json` へ改名して残す（`gui.SHIPPED_DEFAULTS`）
- 足す出来事は `kinds\` に1ファイル1出来事。名前の順に読み、同じ `key` は差し替え、`{"key": …, "enabled": false}` だけのものはその出来事を止める
- 読むのは注入のとき（`incidents.reload_kinds`）。設定画面も同じ関数で読む
- 書き間違えた出来事（要る項目が無い・`tone` や品の種類が決まった語でない・2段目から `into` が無い・JSON が壊れている）は理由を集めて飛ばし、ほかはふだんどおり使う。理由はログの `WARN kinds:` と設定画面の「出来事の種類」タブに出す
- 値段の効き目は段ごとに `prices` の並びで書き、読むときに `(品の種類, 買い/売り, 段ごとの %)` へまとめる。同じ品の買値と売値を別の率にできる（にわか景気の崩壊は買値 -10%・売値 -25%）
- 種類ごとの入切は、版1 の15個の設定（`KIND_OUTLAWS` など）をやめて1つの `DISABLED_KINDS`（英名のカンマ区切り）にした。足した出来事の数だけ設定を宣言できないため。版1 で切っていた分は、注入のときと設定画面で設定の控えから拾って足す。設定画面で保存すると、宣言に無い版1 の項目は控えから消える（`modtool.save_settings` は宣言の項目だけを書く）

### 良い出来事の筋

- 依頼の有無は表の `quest` で決める（`null` なら良い出来事）。良い出来事は、掲示板で依頼を作らせず（`needs_quest`）、ギルドへの案内も添えず、窓に依頼の行を出さない
- 頼み文の決まりは出来事に合わせて組む。概要（`summary_1`〜`summary_4`）と着いたときの1行（`arrive_1`〜`arrive_4`）は段の数だけを書かせて残りは空にさせ、良い出来事は依頼の中身を空にさせる。LLM が書くのは4段目までで、5段より多い出来事の5段目からは表の文
- 概要は段ごとに書かせる（2026-10-13 に決めた）。版2 の最初の形は起きたときの1文だけで、にわか景気の崩壊の段でも「押し寄せ大いに賑わっている」と出た。段が進むたびに頼む形（頼む回数が出来事1つで3〜4倍になり、日数送りでゲーム自身の語りの頼みと重なる）は採らず、起きたときの1回の頼みに段の数だけ欄を足した。窓は今の段の欄を出し、無ければ最初の段の文（版1 の控えの `summary` もここで読む）。
  ゲーム抜きで同じ頼み文と型を直接送って確かめた（テストワールドの にわか景気・感染症の流行・祝祭を各2回）。Claude Haiku 5.5 も Eclipsed-Phoenix-26B-A4B（ローカル）も、全回で段ごとに書き分け（崩壊の段は値の暴落・秩序の乱れ、収束の段は落ち着き）、段の数より後の欄は空、良い出来事の依頼の中身は空だった。1回の時間は Haiku が 4.2〜6.0秒（足す前の実機の記録は 3.2〜6.7秒）、ローカルが 2.3〜3.1秒。文の長さは最長 72字で、上限の 90字に収まった。ゲームの中で窓に段ごとの文が出るところは見ていない（窓が今の段の文を選ぶのはオフラインの検査）
- 窓の色の調子は段の `tone`（`bad`・`good`・`calm`）から決める。`bad` が3つ続けば黄・橙・赤、1つだけなら赤（にわか景気の崩壊）、`good` は薄い緑・緑、`calm` は灰。目盛りも段ごとにその色で塗る
- 次の段への言い方（「悪化するまで」「盛り上がるまで」「弾けるまで」）と、最後の段から収まるまでの言い方（`end`）、終わった欄の言い方（`ended`。「自然に収まった」「落ち着いた」「収束した」）も表から引く
- `339_` は控えの `good` と `stage_name` を読み、趨勢の材料に「（良い出来事・過熱）」「〜は落ち着いた」と書く

### 依頼は、その街の掲示板を開いたときに作る

ゲームの依頼の生成（`DisplayQuestChoice.generate_random_quest`）は引数を取らず、いまいる街の依頼を作る（GAME.md §2.9「掲示板で作った依頼と、それを消す」。2026-10-10 に3回とも）。
出来事はプレイヤーの居ない街で起きることが多いので、起きた時点では作れない。
掲示板を開いたとき（`DisplayQuestChoice.execute`。ゲームの別スレッドで、待機の表示もゲームが出す）に作らせる。

### 自然に収まった依頼は5か所から消す

生きた一覧（`world.quests`）だけから消すと、読み直したときに依頼が戻る（`save_data_dict['quests']` に残っているため。GAME.md §2.9）。
依頼1件ごとにダンジョンの土地も1つ作られる。
消すのは、生きた一覧・セーブの辞書・街の依頼の並び・ダンジョンの土地の2か所の5つ（ローダの `ui.remove_quest`）。
5か所とも消して読み直し、掲示板を開き、次の依頼を作らせるまで誤りは出なかった（各1回）。
依頼と土地の id は使い回されないので、控えの `quest` を id で持っても取り違えない。

### アイコンの列

版2（2026-10-13）から、このアイコンは左下に直接は並ばず、ローダの MOD 用のボタン（歯車）の一覧の1行になった（TECH.md §3.3.15。MOD が増えるほど列が詰まり、1280×720 では 6つ目で箱が重なる計算だったため）。注意の標識は一覧の行の絵として残る。以下は版1 で左下に並べていたときの記録。

ゲームの4つのアイコンは、`icon_button_layout`（FloatLayout）の中で位置を比率、大きさを 40px の固定で持つ（GAME.md §2.34）。
足すアイコンもゲームと同じ型（`HoverableButton(普段, 乗せた時, 押した時)`）で作る。
絵は 32×32 で描き、40×40 に引き伸ばしてから同梱する（`tools\make_town_incidents_icon.py`）。
ゲームは 32×32 の絵を 40px へ近いドットで引き伸ばし、4列に1列（0・4・8…番）を 2px にする。その並びは中心に対して左右対称でないので、左右対称の標識がゲームの中では崩れて見えた。
こちらで太らせる列と行を中心に対して左右対称に選んで（1・5・9・13・18・22・26・30番）40×40 にしておくと、ゲームはそのまま 1:1 で描く。画面の写真と同梱の絵を比べ、不透明なドット 656 個がすべて一致した。
太る列の数はゲームの絵と同じ8列なので、ドットの粒の大きさは変わらない。

足すアイコンを並べるのはローダの `hudicons`（TECH.md §3.3.15）。
左の余白（0.07）を右にも取り、5つを等間隔に置き直す。
1980 幅の画面で、間は 51px から 35px になる。
ボタンの箱どうしを等間隔にすると、絵ごとに端のドットの明るさが違うため（袋は端が暗く、背景に溶けて細く見える）、見えている絵どうしの間が 43・40・40・42px とばらついて見えた。
`hudicons` が見えている部分どうしの間で並べるように直し、42・41・41・42px になった（残る1px は 32 ドットの絵を 40px に引き伸ばす丸め）。

ゲームの4つの「乗せた時」の絵は、HUD の画面が自分の4つにだけ知らせて切り替えている。
同じ型のボタンを足しただけでは知らせが届かず、一度乗せた絵のまま戻らなかった。
`hudicons` がマウスの位置を見張り、足したアイコンにも同じ知らせを出す。
一覧を開くときは、キャラ情報と同じ音（`アイコン_キャラシート.wav`）を開くときだけ鳴らす（ゲームのキャラ情報も、閉じるときは鳴らさない）。

### 各地の出来事の窓

版2 で、文字だけの窓を `339_` の勢力と情勢と同じ作りにした（ローダの `panels`。TECH.md §3.3.17）。中身は `incidents.view_model`（辞書と文字列だけ。検査で通す）、描くのは `window.py`。設定画面の見本は今までどおり `view_lines`（文字の行）で描く。

| 所 | 書き方 |
|---|---|
| 見出しの下 | 現在地　ミストル（この街で霧の市場の買い占めが進行中）／（この街で進行中の出来事はない） |
| 札の上段 | 街の名前・出来事の呼び名・段階の札（困り事は兆し 黄・悪化 橙・深刻 赤、良い出来事は兆し・盛況 緑・収束 灰、にわか景気の崩壊は赤） |
| 目盛り | 段の数だけ。最初から今の段まで段ごとの色で塗り、今の段は濃く。下に「発生から75日。悪化するまで約45日。」（言い方は出来事ごと。設定であいまいな言葉にもなる） |
| 札の行 | 概要、影響（設定で数字・言葉・出さない。数字は主人公から見て得＝緑・損＝赤・売り買いが同じ向き＝橙）、依頼（困り事だけ。掲示板に出ている／まだ出ていない（〜で掲示板を開くと出る）＝灰／冒険者の〇〇が解決に向けて動き始めた。＝橙／掲示板から消えている＝灰） |
| 右の欄 | この1年に終わったもの。日付・街と呼び名・終わり方（解決した＝緑、冒険者の〇〇が解決した＝橙、自然に収まった・落ち着いた・収束した＝灰） |

ライバルが依頼に目を付けた状態は、版1 では「冒険者〇〇が狙っている」と書いていた。街の困り事に対しては合わない言い方なので「解決に向けて動き始めた」に改めた（2026-10-13 に決めた）。

### 宿代

宿代を効かせる処理（ボタンの額・手持ちの断り・前払い調整）は、v1.15.0 までは `315_vacation_custom` が持っていた。
315 が入っていないときにもこの MOD の宿代の段が効くように、ローダの宿代の関所（`prices.install_inn`。TECH.md §3.3.4）へ移した。
315 の決めた額の上に、この MOD の段が掛かる。

宿代の額はセーブに数としては残らない（ゲームは部屋の種類ごとの決まった額を引く）。
残るのは部屋選びの画面の選択肢の文言（`game_variables["buttons"]` の「個室(125G)」）だけ。
関所は画面の文言からゲームの素の額を控える作りで、ロードで戻った文言が前の起動で段を掛けたものだと、
保存の後に設定を変えた・この MOD を切った回は「今の答えの文言」とも食い違い、段つきの額を素の額と取り違えた。
実機では、部屋選びで保存 → 段の強さを 0 にして起動し直す → 読み込むと `room: quality 'private_room' shows 125G` と控え、
個室を選ぶと前払い調整で 25 を足してゲームが 100 を引き、75 しか減らなかった。
ローダの窓口 `choices` に `from_save()`（ロードで戻った選択肢を、人物が揃った後の組み直しまで真）を足し、
関所はその間は素の額を控えないようにした。
最初は「ロードの後の最初の組み直し」だけを真にしたが、実機では人物が揃う前の組み直しで文言が書き直されず、
揃った後のロードの後の組み直しで控えていたので、そこまで含めた。
直した後の実機では、同じ手順で `back to the game's own` に戻り、個室でちょうど 100 が引かれた。
同じ取り違えは v1.15.0 の `315_` 単体でも起き得た（関所を移す前の `relabel_room` が同じ判定）。
部屋の名前は変えずに宿代だけ変えていて、部屋選びの画面で保存し、宿代の設定を変えてから起動し直すと、保存した 315 の額を素の額と控えていた。
2026-10-13 に `tools\tests\test_vacation_custom.py` へ2場面（150 で保存 → 200 に変えて読む・素の 100 へ戻して読む）を足した。
`from_save()` の条件を外すと、200 のところ 150、100 のところ 50 しか引かれずに落ち、今の形では通る。
実機では起こしていない。v1.16.0 のリリースノートのバグ修正に 315 として載せる。
検査は `tools\tests\test_vacation_custom.py` の「ロードで戻った段つきの文言を、起動し直した後に素の額と取り違えない」（直す前のコードでは落ちる）。

### 依頼を作らせる間の待機の表示はゲームに任せる

掲示板の `execute` はゲームの別スレッドで走り、ゲームは押した時点でボタンの旗を下ろして待機の表示（点送り）を出している（GAME.md §2.4）。
作りかけの版では、その中で `ui.Screen.busy_on` / `busy_off(restore=False)` を重ねていた。
`busy_on` はその時点の旗（ゲームが下ろした後の False）を覚え、`busy_off` はそれを戻す。
実機では、掲示板が出た後に依頼を押しても画面が変わらず、手で操作すると動き出した。
原因はこの重ねとみて外した。

外した後の実機では、依頼は作られたが掲示板の一覧が組まれず、ギルドの画面のままだった。
`206_probe_quest_flow` の記録では、作らせた後に続けて呼んだゲームの掲示板の処理の `update_button_display` が、選択肢を1つも変えていなかった。
依頼を作らせるために掲示板の部品（`DisplayQuestChoice`）をもう1つ作ることが、ゲームの中の状態と噛み合わないとみている（中身は読めないので確かめていない）。
そこで、作らせた回はその掲示板の続きを呼ばず、手が空いてから同じボタンの押下と同じ形（`process_choice`）で掲示板を開き直す。
開き直した回は依頼がもうあるので作らず、ゲーム自身の掲示板がそのまま出る（#5）。
