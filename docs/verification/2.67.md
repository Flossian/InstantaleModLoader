# 2.67 版2が実機で通り、鎖が端から端まで繋がった（`318_` / `221_`）

§2.66 で崩れた前提を直した版を1周した。
未確認だった7項目のうち6つが埋まり、鎖が依頼の難易度から店の品とクラフトの成果物まで通った。
生ログは `out\area_difficulty.log` / `out\item_level.log`（`221_`）/
`out\bounty_hunter.log`（`220_`）と、セーブの復号。

## 1. 上げた難易度で敵が強くなる

`get_enemy_*` に渡った実引数（`220_` の記録）:

| 難易度 | レベル | 能力値の基準点（normal / miniboss / boss） |
| --- | --- | --- |
| 3（素） | 4 | 7.56 / 8.89 / 10.99 |
| 4（素） | 5 | 8.17 / 9.60 / 11.87 |
| **23（`318_` が書いた値）** | **24** | **11.40 / 13.40 / 16.57** |

23 は依頼2 が「素 3 + 20」で書き換わった値。
ゲームはその数をそのまま `get_enemy_exp_lvl` へ渡している。
難易度を上げること自体に効き目がある（GAME.md §2.20 の「レベルは難易度+1」も3点目で再現）。

## 2. 作りたての依頼がその場で上がる

```text
search: 頼み文へ渡す難易度 5 -> 25
search: 土地 0 依頼 22 難易度 5 -> 25（素 5 + 20）
search: 頼み文へ渡す難易度 3 -> 33
search: 土地 0 依頼 23 難易度 3 -> 33（素 3 + 30）
```

依頼22 は 5、依頼23 は 3 で生まれている。
土地が +20 / +30 の状態でも素の帯から選ぶ ＝ §2.66 の実測が3例目・4例目として再現した。

## 3. ロードの1回で世界じゅうが戻る

`load: 世界 '<世界>' を寄せ直した（8件）` の2分後の戦闘で `get_enemy_exp_lvl('normal', 23) -> 24`。
8件を走査1回・控えの書き込み1回で戻し、上げた値が掲示板を通らない読み手にも届いている。

## 4. 雛形へ書かなくなった / セーブには残らない

| | 依頼 0 / 1 / 2 |
| --- | --- |
| 雛形 `world_data.json` | 25 / 24 / 23（版1 が焼いた値のまま動かない） |
| 生きた一覧 | 35 / 34 / 33（版2 が上げた値） |
| セーブ `savedata.json` | 5 / 4 / 3（素のまま） |

雛形は版2 の書き換えに追随しなかった ＝ もう書いていない。
セーブは全依頼が素の値のままで、設計どおり。

## 5. 店の品揃えが上がった（鎖の実物）

土地0 の店の品揃えに value 33 の武器と防具が入った。
セーブ上の土地0 の依頼難易度は `[3,3,3,4,4,4,5,5,5]` なので、33 は素のデータからは出ない数。

```text
get_quest_difficulties(土地0) -> [35,34,33,34,35,34,33,35]
get_area_quest_difficulty_for_tier(土地0, world, 2) -> 33
get_weapon_spec(33) -> 145
get_equipment_price(33) -> 1021
get_item_skill_usefulness(33, 'common') -> 10
generate_item_in_shopping(..., item_stock_tier=2)
```

- `tier` は整数（実測 2）。施設の `basic` / `standard` / `advanced` ではない。
  返った 33 は素の並び `[35,34,33,…]` の3番目と一致するが、1点なので式は未確定
- 品揃えを作っているのは `set_item_from_world_data` ではなく `generate_item_in_shopping`
  （`312_` の控えで `tier` がずっと `null` だった理由がこれ）
- `generate_item_in_shopping` は `None` を返す。
  品はそこから受け取るのではなく、主の持ち物へ入る
  （`generate_enemy_instance_from_quest_dict` と同じ形。GAME.md §2.20）

## 6. クラフトの式（一度も測れていなかった1箇所）

`ItemCraftManager.calculate_modification(item_type, item_price)` は float の倍率を返す。
成果物の値段は素材の合計値段にそれを掛けた値:

```text
素材 value 2 + 8（合計の値段 30.75）
  get_equipment_level_from_price(30.75) -> 2
  calculate_modification("weapon", 30.75) -> 24.375
  30.75 × 24.375 = 749.53125
  get_equipment_level_from_price(749.53125) -> 27     成果物の武器: value 27  攻撃力 116
```

副産物（`material`）はその 1/5。2例とも合う:

```text
  calculate_modification("material", 30.75) -> 9.512195…
  30.75 × 9.512195… = 292.5   →  292.5 / 5 = 58.5
  get_other_item_level_from_price(58.5) -> 14         副産物: value 14

  （もう1例）合計 1.25 × 24.375 = 30.46875 -> value 8
             副産物 30.46875 / 5 = 6.09375 -> value 2
```

「素材が高いほど成果物が良い」が実測で成立した。
`318_` が在庫を上げれば素材が上がり、クラフトも自動で追随する。
倍率は種別と値段で変わる（`weapon@30.75` は 24.375、`material@30.75` は 9.5122）が、
式の形は2点では出ない。
