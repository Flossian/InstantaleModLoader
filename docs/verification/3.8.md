# 3.8 売買画面の救済経路（`108_`）: まだ一度も通っていない

> `superseded: main_024` で降ろした（§3.8.1）。
> 既定では読み込まれないので、下はデバッグモードを入れたときの話。

修正は入っているが、はみ出しが再現していないので救済側のコードは実地では未実行
（`out/inventory.log` の192件はすべて正常サンプル）。
次に売買画面で落ちたとき、または `ok` 以外の行が出たときが確認の機会:

| ログ | 意味 |
| --- | --- |
| `ok ...` だけが並ぶ | 復元位置がそのまま使えている（正常。寸法の基準として使う）。版2から行頭に時刻が付き、見本はグリッドの種類（situation・cols・rows）ごとに1プロセス1件（版1は注入ごとに最初の30件） |
| はみ出しを捕まえた行 | 救済へ流した。別のマスに置かれるので見た目が変わっても正常 |
| 落ちる | 救済が効いていない。`is_valid_placement` の判定と実際の `slots` 長を突き合わせる |

**そもそもなぜ復元位置がはみ出すのかは未解明**（グリッドの列数が画面ごとに違うのか、
ピクセル→マスの変換が別スケールなのか）。
`inventory.log` に所持品側と売買側の両方の寸法が出るようにしてあるので、
再発時にそこから詰められる。

## 3.8.1 `108_` を `superseded: main_024` で降ろした

| | 状態 |
| --- | --- |
| 落ちた原因 | 確定（§2.16） |
| 修正が読み込まれること | 確認済（正常サンプル192件） |
| 救済経路が走ること | **未発火**（192件すべて `ok`） |
| 本体が直したのか MOD が防いでいるのか | **判定不能**。他の5本と違って印が無い |

このクラッシュは狙って起こせず、はみ出しの理由も未解明なので再現手順を組めない。
したがって「症状が出ない」も根拠にならず、今後も区別できない見込み。
無害だから残すという理屈は通るが、
それでも降ろすのは**確かめられないものを既定で配り続けない**という一点。

戻すときは、売買画面で落ちたらデバッグモードを入れて注入し直し、
`ok` 以外の行が出るかを見る（切り分け表は §3.8 のものがそのまま使える）。
救済が発火したら、それが「本体は直していなかった」ことの証拠になる。
