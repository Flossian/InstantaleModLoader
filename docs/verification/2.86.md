# 2.86 画像生成の出口とバックエンドを4つの一族で測った（`230_`）

DLL のプロキシでやっている画質強化（解像度・LoRA の付け替え・サンプラー上書き）を
ローダの MOD へ移せるかの下調べ。
`230_probe_image_generation` を版1から版5まで直しながら、バックエンドを替えて5回起動した。
ゲームの側の結論は GAME.md §2.33。

| 問い | 答え |
| --- | --- |
| 選ばれた一族だけが import されるか | そう。注入の時点（タイトル画面）では `sdcpp` も `image_generation` も0件 |
| 名指しせずに当たるか | 当たる。4つの一族すべてで出口を包めた（`sdcpp_cuda` と書いていたら3つで外れていた） |
| 出口は1つか | 一族につき1つ。生成6回すべてが通り、`upscale()` と `generate_video()` は0回 |
| 種類の印は届くか | 届く。上の層でスレッドに立てた印が出口で読めた（印の無い出口は最後の版で0件） |
| TAESD はいつ決まるか | `load_sd_pipeline()` の中。import から構築の開始まで 0.27〜0.62 秒 |

数えた件数は、一族4つ・パイプラインの構築6回・生成6回（背景4・立ち絵2）・構築の引数1回ぶん（`sdcpp_cpu`）。

probe 側で2回外した。
どちらも実装へ持ち越す教訓になる。

種類の印を `apply()` のクロージャに置くと、当て直しを跨いだ回に届かない。
上の層を包んだ apply と出口を包んだ apply が別世代になると、
`threading.local()` の入れ物がクロージャごとに別になる。
`diffusers_openvino` の1回目で `kind=None` が出た（スタックからの予備は拾っていた）。
版5 でモジュール側の入れ物へ移し、同じ経路で印が届くことを実機で確認した。

出口のクラスを `txt2img_pipe` の型からだけ引くと、構築そのものを包めない。
建った後にしかクラスが手に入らないので、`__init__` の実引数が1件も録れなかった。
版4 で manager のモジュール側からも引くようにして、`sdcpp_cpu` で構築の引数を録った。

5秒ごとの見張りでは間に合わないことも確かめた。
import と構築が同じ関数（`set_ai_models`）の中で閉じているので、間隔の問題ではない。
`sys.meta_path` の先頭に観測者を置き、他の finder が作った spec の `loader` だけを包んで、
モジュールの本体が走り終えた直後に入る形にしてある（実測6回で import の 11〜119 ミリ秒後に包めた）。
