# 3.113 何本もの MOD が自分で包んでいたロード・日数・到着・会話の相手への差し込みを、ローダの窓口へ寄せる（`loads` / `durations.on_days` / `arrivals.on` / `modnpc` の notes）: 31 本を乗せ替え、オフラインの検査は通過・ロード・世界・日数・到着・会話の相手の経路は実機で成立（10-23）・338/339/911 の日数と到着・新規開始は未

2026-10-22。
外から受けた構造の評価で「ゲーム本体の更新への耐性」が弱いと言われ、そのとおりだと見た。
`drift` は包みの外れや引数の変化を知らせるが、直す所の数は減らない。
直す所が MOD の数だけあるのは、同じ関数を何本もの MOD が自分で包んでいるため。

## 分かったこと

2026-10-22 22:34 の注入の台帳（boot #2。137 本・1159 件。同じ行を省いた分は boot #1 から補った）で、2本以上が包む対象は 199 件。
probe（2xx）とローダを除き、MOD 自身が対象の名前を書いている包みは 445 件あった。

LLM の送り口（`send_request` 系）は 14 本が既に `llm.wrap_outgoing` 経由で、名前はローダの1か所だけだった。

包みの重なり順は台帳の並び（実際に当てた順）で、`load_order.json` の並びとは違う所がある（probe の 214 が 336 より内側など）。

## 決めた仕様（A〜D をすべて行う）

- 包むのはローダの1枚。MOD は前後の処理だけを渡す。共通部品は `gates.py`（TECH.md §3.3.21）
- A・A' は新しい窓口 `loads`、B は日数送りの関所（`durations.on_days`）、C は `arrivals.on`（施設は到着の番号の包みと同じ1枚）、D は `modnpc` の notes
- 呼ぶ順は自分で包んでいたときの重なりと同じ（前の処理は新しい順、後の処理は古い順）。D の足す順は各 MOD の `NOTES_PRIORITY`（321 が −6 から 301 の −1）で宣言する
- 素通しでない包み（引数や戻り値を変えるもの）は MOD に残す。第一声の差し替え（300・339・911）、依頼の生成への差し込み、`return_to_title`（333）など
- probe は窓口を通さず直に包むまま
- `check_mods.py` に、probe 以外の MOD がこれらの対象を自分で包んでいたら note を出す決まりを足した（CI の `--strict` では問題）。会話の5関数は正当な直の包みが残るので対象にしない
