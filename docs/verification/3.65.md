# 3.65 Stable Diffusion の解像度・サンプラー・モデル・プロンプトを差し替える（`343_stable_diffusion`）: 解像度・材料の差し替え・サンプラー・敵の素の値・diffusers 系・SDXL 一式・プロンプトの規則とモデル別の雛形は実機で成立・skip と版20 の二重掛けの直しは未

開発中は `916_stable_diffusion` の名前で動かし、v1.19.0 で `343_` に正式化した（2026-10-26）。遊び方と設定は `343_` の DOC.md、ゲーム側の読み方は GAME.md §2.33、読み取りの測定は VERIFICATION_LOG.md [§2.86](2.86.md)。下の「版」はこの MOD の `mod.json` の版。

## 書き込みに入る前の計画（`230_` の読み取りが決着した時点）

この節は 916 を作る前に書いた計画で、下の記録で全部片付いた（出口で寸法を上げる・建つ前に材料を書く、とも実機で成立）。
読み取り側は4つの一族で決着した（GAME.md §2.33 / VERIFICATION_LOG.md [§2.86](2.86.md)）。
残っているのは**書き込み側**で、2xx の probe では測れない（読み取りだけの約束）。
9xx の試作で次の2つを当てる。

| 確かめること | やり方 | 見るところ |
| --- | --- | --- |
| 出口で寸法を上げて下流が通るか | 出口の `width` / `height` を上げて立ち絵を1体作る | 背景抜き・縮小・減色・顔の切り出し・保存・表示。`extract_and_save_face` は箱を 330/512 の定数で縮めるので、立ち絵の寸法を変えると顔がずれる（GAME.md §2.30） |
| 建つ前の差し替えが構築まで届くか | `taesd_path` を空にしてからワールド選択を押す | `pipe_init` の実引数と、絵が出るか（TAESD を使わず VAE で復号する道に落ちる） |

前提が1つある。
**別配布の DLL プロキシが入っていないことを確かめてから測る。**
入ったままだと出口の後ろでもう一度書き換わるので、効果が混ざる（GAME.md §2.33 の末尾）。
計測時点では入っていない（3つのバックエンドとも `stable-diffusion.dll` と `-real.dll` のハッシュが一致）。
`-real.dll` が在ることは入っている証拠にならない。

`131_sharp_portrait` と `local\smooth_background` が同じ経路の後段を包んでいる。
立ち絵を大きくするなら、131 側が立ち絵 512x1024 を前提にしている箇所を実寸から求める形へ直すのが先（[§3.43](3.43.md)）。

## 当てる先と、名指ししない理由

出口は一族につき1つで、実機で4つ確かめてある（GAME.md §2.33）。

| `sd_backend.name` | 出口 | 当たる項目 |
| --- | --- | --- |
| `sdcpp_cuda` / `sdcpp_vulkan` / `sdcpp_cpu` | `<sdcpp_*>.stable_diffusion:StableDiffusion.generate_image` | 寸法・方法・steps・cfg・スケジューラ |
| `diffusers_openvino` | `optimum.intel.openvino.modeling_diffusion:OVStableDiffusionPipeline.__call__` | 寸法・steps・cfg（方法とスケジューラは同じ口が無いので落とす） |

モジュール名は `config.json` から組み立てられない。
`sdcpp_cuda` は `image_generation.sdcppcuda`（下線が落ちる）、
`diffusers_openvino` は `image_generation.diffusers_openvino`（下線が残る）。
そのため出口は `sys.modules` と生きたパイプラインの型から引く。

材料（チェックポイント・TAESD・VAE・LoRA の置き場）はパイプラインが建つ前にしか書けない。
建てる関数 `load_sd_pipeline` を包み、その直前に書く（版15）。
最初の1回は import から構築の開始までが 0.27〜0.62 秒しかなく、5秒ごとの見張りでは包みが間に合わないので、
`sys.meta_path` の先頭に観測者を置き、モジュールの本体が走り終えた直後に包みと書き込みを済ませる。
**この観測者は本来ローダの語彙**（TECH.md §3.2.3）で、試作の間だけ MOD が持っている。
正式化のときは `instantale_modloader` 側（`sd.py`）へ移す。

版14 までは観測者だけで書いていた。
観測者は import の瞬間にしか効かず、同じプロセスで2回目のワールド選択をしても
import は走らない（Python が sys.modules に持っている）ので、
注入し直して設定を変えても構築には前の値が残る作りだった。
230 の記録では `load_sd_pipeline` は全プロセスで `#1` しか無く、
**同じプロセスでの2回目の構築は一度も測っていない**。版15 の経路もまだ実機で当てていない。

## 実機で確かめたこと

| # | 確かめること | 見るところ |
| --- | --- | --- |
| 1 | 建つ前の差し替えが構築に届く | **決着（2026-09-18）。届く。** import の直後に書いた `taesd_path=''` が `StableDiffusion.__init__` にそのまま渡り、VAE 復号で背景が出た（2.8 秒。TAESD 有りは 2.7 秒で、この寸法では復号は律速ではない）。チェックポイント・VAE・LoRA の置き場も同じ経路なので、SDXL 化にゲームのファイルを触る必要は無い |
| 2 | 寸法を上げた絵が下流を通る | **決着（2026-09-18）。通る。** 832x1664 のまま背景抜き・保存・立ち絵・顔まで到達し、`131_` の切り直しは実寸で扱うので顔もずれない（切り出した 256x256 の中で顔が再検出できる）。外れた1体は寸法に依らず検出できない個体だった（同じ絵を 512x1024 や 416x832 に縮めても素の箱が0件） |
| 3 | 一族で結果が割れないか | **割れる（2026-09-18）。刻み次第。** `diffusers_openvino` で背景を 1536x768（画素 x2.25）にすると 64GB の RAM を使い切って SSD へページングを始めたので中止。1152x576（画素 x1.27）なら **15.1 秒で通った**（素の 1024x512 は 10.5 秒）。ただし**通った回も RAM は伸び、ゲームを閉じるまで戻らなかった**。形を固定して変換したモデルなので、寸法ごとに作り直したものが常駐する。**版3 でこの一族の寸法は既定で触らない**（設定で入にできる）。sdcpp 系は 1.625 倍でも素直に受ける |
| 4 | サンプラーの上書きが通るか | **決着（2026-09-18）。通る。** 2段目を `dpmpp2mv2` / cfg 5.0 に差し替えて立ち絵を2体作り、4.4 秒と 4.2 秒で出た（steps は 15 のまま）。方法名の差し替えも cfg の変更も効く。`SAMPLE_METHOD_MAP` に無い名前は設定が choice なので渡せない。**速さの比較には使えない**（素の 10.4 秒はモデルを読んだ直後の回で、こちらは温まった後） |
| 5 | 敵・モンスターの素の値 | **決着（2026-09-18）。立ち絵と全く違う。** `generate_enemy_image` から `generate_image_real_lcm` へ入り、**正方形 512x512 を1段**で描く（lcm / 5 / cfg 1、1.5 秒）。立ち絵の2段（256x512 と 512x1024、euler_a と dpmpp2m）とは寸法もサンプラーも別物。**版5 でこれに合わせた**（敵の既定を 512x512 に、段の名前を「背景」から「LCM の段」へ） |
| 6 | SDXL 一式 | **決着（2026-09-18）。MOD だけで成立。** チェックポイントと TAESDXL を指し、LoRA タグを外し、サンプラーを `euler_a` / 24 / cfg 5.0 にして、寸法を 1024x2048 にしたら人物として成立した絵が 21.7 秒で出た。ゲームのファイルは1つも触っていない（TAESDXL はゲームフォルダの外の絶対パスで読めた）。途中で2回外した経緯は下の「SDXL で踏んだ順序」 |

## 実測した時間（1.625 倍、`sdcpp_cuda`、2026-09-18）

| 段 | 素のゲーム | 1.625 倍 |
| --- | --- | --- |
| 立ち絵の1段目（256x512 から 448x832） | 4.8 秒 | 5.1 / 11.8 / 126.5 秒 |
| 立ち絵の2段目（512x1024 から 832x1664） | 10.4 秒 | 49.2 / 53.0 / 50.2 秒 |
| 背景（1024x512。設定は既定） | 2.4 秒 | 2.7 秒 |

SDXL（`waiIllustriousSDXL_v170`）で 1024x2048・`euler_a` / 24 / cfg 5.0 のときは、
立ち絵1体が **21.7 / 21.8 / 22.2 秒**（3体。構築は 4.2〜5.8 秒）。
SD1.5 の素（512x1024・LCM 5 steps）が 3 秒前後なので、7 倍前後の費用になる。

素の値はモデルを読んだ直後に測ったもので、温まった後は同じ設定でも 4 秒台まで下がる。
**倍率どうしの比較にだけ使い、速くなった遅くなったの根拠にはしない。**

安定して効くのは2段目の約5倍で、立ち絵1体が 15 秒から 60 秒前後になる。
1段目の 126.5 秒は **VRAM が溢れた回**で、寸法ではなく載っているものの合計で決まる
（同じ寸法の他の回は 5〜12 秒）。
拡大はその余裕を削るので、LLM を載せたまま上げると桁で遅くなる。

## 段は関数では決まらない（版4 で直した）

`diffusers_openvino` では**キャラの絵も `generate_image_real_lcm` を通る**
（実機 2026-09-18。画質が `highres_faster` のとき、512x1024 を 10.5 秒で1枚）。
版3 まではこの関数を「背景の段」と決め打ちしていたので、
この一族ではキャラにサンプラーの背景設定が当たる作りだった。
版4 から段は**種類と関数の組**で決める（背景は種類で決まり、
立ち絵と敵は `image_to_image_anime` なら2段目、それ以外は1段目）。

## モデルの系統に合わせる安全弁（版8）

今日踏んだ壊れ方は2つとも「モデルの系統と設定の食い違い」だった。
同じ踏み方をしないよう、**チェックポイントの中身から系統を見分けて**必要なぶんだけ直す
（設定「モデルの系統に合わせて直す」。既定は `auto`）。

見分け方は safetensors のヘッダ。
先頭8バイトがヘッダ（JSON）の長さで、その鍵がテンソルの名前。
本体は読まないので実測 0.00 秒（ヘッダは SD1.5 が 150KB、SDXL が 365KB）。

| 系統 | ヘッダに在る印 |
| --- | --- |
| SD1.5 | `cond_stage_model.*` |
| SDXL | `conditioner.embedders.1.*`（2つ目のテキスト符号化器）と `model.diffusion_model.label_emb.*` |

**名前でもファイルの大きさでも判定しない。**
名前は当てにならず（手元の `AnythingXL_inkBase` は XL と付くが SD1.5）、
大きさは量子化や差分で動く。

直すのは壊れると分かっている組み合わせだけ。

| 状況 | すること | なぜ |
| --- | --- | --- |
| SDXL のプロンプトに SD1.5 用の LoRA タグ | **ゲームが入れたタグだけ**外す | **プロセスごと落ちる**（実測）。規則で付け替えた先や足したタグ（SDXL 用）は残す。版14 までは全部外していたので、付け替えで SDXL 用にしたタグまで消えていた |
| SDXL で LCM の段の設定が素のまま | `euler_a` / 24 / cfg 5.0 にする | ゲームの 5 steps / cfg 1.0 では**マゼンタに潰れる**（実測） |
| 学習の寸法から離れた指定 | **警告だけ。値は動かさない** | 壊れるとは限らない（下を参照） |

設定で明示した項目は動かさない（素のままの項目だけ寄せる）。

**寸法を自動で動かすのはやめた。**
版8 では「SDXL に 0.9 メガピクセル未満は絵にならない」と読んで引き上げていたが、
**実測で否定された**。
安全弁なしの 1024x512（0.52 メガピクセル）の背景が SDXL で正しく出ている
（サンプラーだけは `euler_a` / 24 / cfg 5.0 になっていた）。
マゼンタに潰れていた回の原因は寸法ではなく**サンプラー**で、
壊れ方を寸法のせいにしたのがこちらの読み違いだった。

## 版20 で直した2つ（実機 2026-09-20 で見つかった）

SDXL プリセットを当てて立ち絵を3体作った回のログから。

**包みが二重に当たっていた。**

### 起動直後の生成で落ちた（版26 で直した）

1段の条件で起動し直した回に、ゲームが落ちた。
世界を読んで約7秒後に、ゲーム自身が立ち絵（512x1024、SD1.5 の LCM LoRA 入り）を描き始め、その回は書き換えが1つも当たっていなかった。
順番は次のとおり（ローダのログと `stable_diffusion.log`）。

1. boot #1 が manager の import を見て材料を書き、`load_sd_pipeline` を包んだ。SDXL を建て始めた
2. 建てている途中で boot #2（起動直後の注入し直し）が入り、boot #1 は用済みになった
3. boot #2 の当て直しは、まだ `txt2img_pipe` が無いので出口を包めなかった
4. 建て終わったとき、boot #1 の `load_sd_pipeline` の包みは用済みなので何もしなかった
5. 5秒ごとの見回りが出口を包む前に、ゲームが描き始めた。SD1.5 用の LoRA が SDXL に当たって落ちた

SD1.5 なら書き換えが抜けるだけで済むが、SDXL ではゲームごと落ちる。
直し方は2つ。

- sdcpp の一族は manager がクラス（`StableDiffusion`）をモジュール変数に持つので、建つ前でもクラスから `generate_image` を包む。ありふれた名前の `__call__`（diffusers 系）は、生きたパイプラインの型からしか包まない
- 用済みの `load_sd_pipeline` の包みが建て終えたら、いちばん新しい apply() の当て直しを呼ぶ（`HANDOFF`。注入のたびにモジュールは作り直されるので、`sys.modules` の今の同名モジュールから引く）

直した後の起動では、出口を包んだのはモデルを見分けた直後（boot #1・boot #2 とも、建て終わる前）だった。
起動直後にゲームが描き始める状況は、その後の起動では起きておらず、落ちる回そのものの再現は取れていない。
