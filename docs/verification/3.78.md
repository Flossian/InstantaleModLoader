# 3.78 計測（2xx）の見直し: ログの量・負荷・読み取り専用の破れ（オフラインで通過・実機は未確認）

`out\` が1か月で約585MB になり、そのうち `area_quest_difficulty.jsonl` だけで約100MB あった。
デバッグモードを常に入れて遊んでいるので、計測は全本が毎回動いている。
全本を読み直し、実ログを集計した。決着した計測も無効にせず、有効のまま直した。

見つかった型は4つ。

- **遊びの状態を変えていた**。`206_` の `quest_type` の総当たりが `QuestChoiceManager` を組み立て、それを受注と見た `318_` が依頼の難易度と `state\` を書き換えた（15件。`accept:` の時刻が総当たりの4〜7ms 後に並ぶ）。`214_` は注入のたびに共用の乱数を引く `get_npc_exp_level` を81回呼んでいた。`236_` の試し打ちも乱数を引く
- **内側の不具合を隠していた**。キーワードで来た引数を位置へ直して内側へ渡す包み（`223_` / `226_` / `227_` ほか）。[§3.76](3.76.md) の `333_` 版21 の `multiple values` は、227 が外側に居る起動では出なかった
- **起動時の記録を注入のたびに出し直していた**。1か月で apply 1,015回に対してゲームのプロセスは179個。スナップショットや総当たりを `sys` の印で1プロセス1回にした
- **決着済みの問いの記録と重い処理が、上限なし・判定より先に走っていた**。点送りの1コマごとの記録（`234_`）、子の数の変化での誤検出（`220_`）、店の外の品の誕生（`227_`）、主スレッドの外から Kivy を読む 20Hz のスレッド（`206_`）など

ローダも4つ直した（その後、既存 MOD のログの見直しで5つ目を足した）。
`modloader.log` は、遅れて当て直す boot で前の boot と同じ文面の定型の行を書かない（`log_unrepeated`）。同じ注入の前の boot の層の置き換えは件数だけ、締めの報告の先送りの節はモジュールごとの件数にした（対象ごとの `defer` の行はどの boot でも書く）。1回の起動で boot が4回走り、約7,600行・約940KB あった。同じログで試算すると約2,900行・約390KB。
`frames.owner_of` はコードごとに答えを覚える（`caller()` が1段ごとに `__main__` の全クラスを舐めていた）。
`tools\logrotate.py` は `*.jsonl` も送る（前は `*.log` だけで、世代送りを入れても probe の記録が積もり続けた）。
既存 MOD のログの見直しで、MOD が `ctx.log` で書く INFO 行（apply のたびの設定の要約）も同じ扱いにし、`modfacility` / `modnpc` の `registered` は同じ持ち主・世代・層の数なら1行、`snapshot of … taken` と関所の行（`modfacility` / `modnpc` / `durations` / `prices`）は中身が変わったときだけ書くようにした（`331_` は選択肢が組まれるたびに持ち株を登録し直していて、1分に170行を超えていた）。
`modnpc.LIFT_ROSTER` は `settings\loader.json` の `modnpc_lift_roster` で決める（前は `229_` の設定が書き換えていて、229 を入れている間は `330_` など ModNPC を使う全 MOD に効いた）。
