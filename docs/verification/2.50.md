[§2.49](2.49.md) とは向きが逆で、**ソースの側から当たった**。
ローダ本体と 67 個の MOD を読み、23 ファイルを書き換えたうえで実機で確かめた。

## 初回ブートで5つの MOD が落ちていた

`120_` / `128_` / `129_` / `212_` / `312_` が boot #1 で
`AttributeError: module '__main__' has no attribute 'World'` を出して降りていた
（6秒後の boot #2 で拾えるので普段は表に出ないが、
ブートが1回きりで終わるプロセスではこの5本が最後まで載らない）。

MOD ごとに見張りを持たせると同じものが5本ぶん増えるので、ローダ側の保留を広げた。
`__main__` の持ち主のクラスが無いだけなら、
未 import のモジュールと同じく `required` に関わらず保留にして、既存の見張りに拾わせる。
来たかどうかの見方だけは別（モジュールは `sys.modules`、持ち主は `resolve()` が通るか）。
葉は対象外にしてある（`World.generate_character` の葉が無いのは本物の間違いなので、
待たずに従来どおり投げる。待っても来ないものを待つと本物の間違いが紛れる）。

残った `128_` は別の失敗だった。
モジュールは `sys.modules` に在るのに関数がまだ定義されていない。
import は「先に `sys.modules` へ登録してから本体を走らせる」ので、
載っていることと中身が揃っていることは別。
走っている間だけ True になる `__spec__._initializing` を聞く見分けを足した
（`__main__` は起動スクリプトで spec を持たないから名前で特別扱いが要ったのであって、
普通のモジュールは聞けば答えが返る。こちらは葉も対象にしてよい）。
実機で初回ブートが `apply failed:` 0件・`boot complete: 65/65`。
`_initializing` は Nuitka のモジュールでも立っていた。

そのとき当て直しの合図が 4,874 文字になった（`__main__` のクラスが揃った瞬間に115件が1行に並んだ）。
対象は件数だけ書くように直した。
`206_` の 27,724 行と同じ形の失敗を、直した当日に自分でやっていた。

## `314_` の注入し直しまたぎ（成立）

## `307_` の3つは戻し、3度目に設計を疑って決着

`302_` の中断経路について「LM Studio を止めれば起きる」と書いたが、
起きる条件を確かめずに再現手順を書いていた。
同じ誤りの型で全修正を洗ったところ、`307_` の3つだけが
オフライン検証も実機ログも無いまま入っていた
（`test_area_move_dungeon.py` の130件はそれ以前の判定で、今回の3つを1件も見ていない）。
さらに `check_quest_alive` には設計の穴があり、
`app.current_quest_data` が読めないだけで「依頼が消えた」と判断して控えを捨てる。
道中の正常なセーブを読み直すたびに道が切れる。
3つとも戻した。

そのあと設計そのものを疑い、「ダンジョン踏破で日数は進むのか」を問い直した。
`TRAVEL_DAYS` は「道中のクエストと最後の移動の合計」の予算として作られていて、
使い切ると以後の `elapse_days` に 0 が渡り続ける。
これが暦の凍結の正体で、道中が日数を使う前提の上に立っていた。

前提は実機を動かさずに `output_data` で決着した。
`elapse_days` は LLM に渡している14種の権限の1つ（GAME.md §2.26）なので、
`response` に `{"type": "elapse_days"}` が入っている件数を全件数えた:

| manager | 使った / 総数 |
|---|---|
| `master_ai_facilitator`（自由行動） | **128** / 1004 |
| `master_ai_facilitator_from_conversation` | **17** / 161 |
| クエスト側 8 manager | **0** / 2029 |
| 他 40 manager | 0 |

クエスト側 2,029 件すべてで0件。
実行された144ステップの日数は 0日69 / 1日69 / 3日4 / 7日2（最大7日）で、すべて自由行動。
`road_travel.log`（2本しかない）・セーブの `backups/`（セーブエディタ製）・
`savedata_plain.json`（累計なので取り出せない）はいずれも答えを持っていなかった。
答えを持っていたのは LLM の記録だけだった。

直した形は `ダンジョン踏破（0日） → エリア移動 → 指定の日数が経過`。
切り詰めるのは段階 `moving` だけで、`armed` 以降の控えは `elapse_days` に触れない。
控えが外れなくても暦は止まらない（穴を塞ぐのではなく、害を消した）。
`journey.spend` は削除し、`days_spent` は
「`elapse_days` を通らなかった」の見張りとして残した。

## 「移動は別スレッド」は仮説ではなく実測だった（訂正）

「`307_` の『移動は別スレッドで走る』は出典の無い仮説で、実測3系統は同期側だった」と書いた。
誤り。
`206_probe_quest_flow` のコードに
「`process_choice` は `execute` をスレッドに渡して即座に返るので、
『after』は『最中』ではない」と実測済みで書いてあった。

3つのログの時刻を並べ直すと、
`process_choice` は 2ms で返り、その 2ms 後に `elapse_days` が来て、
`execute` が返るのは 5.7 秒後。
`314_` が呼び出し内の窓で足りるのは `AreaMoveManager.execute` そのものを包んでいるからで、
`process_choice` を呼ぶ側の `307_` には同じ形が取れない。
`307_` が控えをファイルに残すのは設計の正解で、「314 に寄せる」は退行になる。

## 書き込んだ内容を自己検算した

このセッションで書き込んだ数字と引用と参照を全て検算した。
`output_data` の総数が3つずれていた（2,021 → 2,029。計測の後に遊んだ分。増えた分も0件で結論は変わらない）ほかは、引用は逐語、時刻は実在、§参照は解決。
数字より問題だったのは断定の仕方で、推論を実測と同じ調子で書いた箇所が4つあり、調べ直すと4つとも覆った。

> 測ったことと、そこから考えたことを、同じ強さで書かない。
> 書く前に「これはどのファイルの何行目で確かめたか」を言えるかを見る。
> 言えないなら、そう書く。

## 教訓

- 出典の無い断定を仮説だと決めつけない。否定する側も測ってから言う
- 「窓で足りるか」は包んでいる相手で決まる。
  `execute` を包めば 5.7 秒開き、`process_choice` を呼ぶ側なら 2ms で閉じる
- 「オフライン N 件全通」を自分の変更の根拠にしない。その N 件がこちらの変更を見ているかは別
- 穴を塞ぐ前に、その穴が要る設計かを疑う。
  `307_` の予算の積み上げは `run_road` の docstring の当時の想定のためだけに在り、それが凍結を生んでいた
- 「引けなかった」は「無い」ではない
- `out\modloader.log` の ERROR / WARN を数える日を決める。
  ログの行数は版をまたいで積み上がるので今のコードの証拠にしない（`NameError` 119,840件のうち今のコードの話は 879件）
