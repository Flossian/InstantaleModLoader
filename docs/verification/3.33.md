# 3.33 注入がゲームの `__main__` を汚していた（修正済み）

本体のクラッシュ記録が、記録を書く前に自分で落ちていた。

```text
File "instantale.py", line 288, in report_crash
File "instantale.py", line 200, in make_crash_log
AttributeError: module 'datetime' has no attribute 'now'
```

`make_crash_log` は文字列を組んで返すだけで、`crash_log.txt` への書き込みも
送信もその後段にある。落ちている間はどちらも走らない。

**素の不具合ではなかった**

| 走らせ方 | 本体の `crash_log.txt` |
| --- | --- |
| MOD 無し（`MOD を外す`）で同じクラッシュ | 書けた（10件 → 11件、11157 → 11818 バイト） |
| 注入した状態で同じクラッシュ | 書けない |

`001_crash_recorder` が拾った14件（MAIN 6 / THREAD 8）は、
どれも本体の `crash_log.txt` に無い。
逆に本体が書けている10件は、どれも 001 が拾っていない＝注入前の回だった。
注入を始めてからの14件を「素の不具合」として数えていたが、全部こちらが壊していた。

**原因: 流し込むコードがモジュール階層で import していた**

`PyRun_SimpleString` は**ゲームの `__main__` の辞書で**流し込んだ文字列を実行する。
`tools/injector.py` の `BOOTSTRAP_TEMPLATE` は1行目がこうだった。

```python
import sys, os, datetime, traceback
```

本体は `from datetime import datetime`（クラス束縛）で持っているので、
この行がモジュールを被せていた。`datetime.now()` はクラスにしか無い。

```text
素の __main__.datetime = <class 'datetime.datetime'>
流し込んだ後           = <module 'datetime' ...>
```

`sys` / `os` / `traceback` も同じように上書きしていた。
表に出たのが `datetime` だけだったのは、本体がそこだけクラスで束縛していたため。

**直し方: 全体を関数で包んだ**

`import` も一時変数も関数の中に閉じ込め、モジュール階層に残るのは包みひとつだけ。
それも最後に `del` する。

**検算**

`tools/tests/test_injector_bootstrap.py` が `make_bootstrap()` の出力を
`ast` で解いて、モジュール階層に `import` も代入も無いことを見る（boot / unload の両方）。
踏んだ形（平らに書いた場合に束縛が消えること）も回帰として入れてある。

**切り分けに使った道具**

`219_probe_crash_log`。`make_crash_log` を包んで、落ちた呼び出しごとに
`title`・例外の連鎖・そのときの `__main__.datetime`・呼び出し元の経路を控え、
`datetime` を差し替えてもう一度組ませた結果まで記録する（結果は捨てて元の例外を投げ直す）。
実機1回で `RETRY with the shim -> OK, 1635 chars` が出て、
「差し替えれば本体と同じ書式の記録が出来る」ところまでは即決した。
`mods in path = yes` が出ていたのでこちら側を疑い、上の突き合わせに繋がった。

**直った後の実機（同じ店で1回）**

```text
datetime = <class 'datetime.datetime'>
datetime is sys.modules['datetime'] = False | has now = True
OK       3495 chars
  -> write_crash_log_to_file: 3495 chars
  -> should_skip_crash_log_server_send = False
  -> send_crash_log_to_server: 3495 chars
```

`crash_log.txt` は 11件 → 14件（11818 → 17023 バイト）。
増えた3件のうち2件は注入が `WinError 24` で失敗していた間のもので、
残る1件が注入済みの回。この1件が `live_crashes.log` の同じ時刻の記録と対応する。

**送信は意図して止める**

`report_crash` が後段を
`write_crash_log_to_file` → `should_skip_crash_log_server_send` → `send_crash_log_to_server`
の順に呼ぶこと、渡るのが `crash_log.txt` と同じ文字列であることは上の実機で確認した。
**`send_crash_log_to_server` の中身は読めていない**（凍結されている）。
外へ出す口だと見ているのは、関数名と `CRASH_REPORT_URL` という定数からの推測。

そのうえで、MOD 入りの記録を外へ出さないことにした（`001_crash_recorder`）。
本体自身は `should_skip... = False`＝送る判断をしていたので、止めなければ出ていた。
`crash_log.txt` は書かれるので手元には残る。
