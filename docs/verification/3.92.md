# 3.92 作業スレッドが死んだときに待機を終える（ローダの `stalls`）: 送信の失敗は実機で成立・`execute` の素の例外は実機の別経路で成立

作りは TECH.md §5.12、ゲームの送信と待ちの仕組みは GAME.md §2.12「送信と待ち」。
記録は `out\modloader.log` の `stall guard:` の行と、`001_` の `out\live_crashes.log`。

## 決めた仕様（再検討しない）

- MOD ではなくローダに置く（2026-10-08）。スレッドの名前・送信の閉包の在りか・`should_give_up` の別名はゲームの読み方で、`llm.ask` を使う MOD の頼みも同じ扱いになる。切るのは `settings\loader.json` の `stall_guard`
- 待機を終えたとき、状態は途中まで書き換わったまま返す。理由が見えて操作が返るほうを採る
- 4xx の送り直しは同じ送信スレッドの3回目で打ち切る（ゲームは32回）。5xx・時間切れ・接続の誤り・コードの例外（`KeyError` など）の送り直しは変えない
- 本文の欄の文は、どの行も `［MOD ローダ］` で始める

## 分かったこと

- それまでの記録（`live_crashes.log`、スレッドの死 59件）では、待機が残る死の大半は `execute` の中の例外（37件。ほぼ MOD を作っている最中の `KeyError` など）で、送信スレッドの 400 は10件だった
- 待っている `send_request` が見ているのは送信の本体の閉包の `response_from_llm`。`finished_event` は再実行のボタンの時計の旗で、立てても待ちは返らず、ボタンが出なくなっただけだった（最初の版。直した）
- 関数の閉包のセルは生きている間も読み書きできた（gc から引いた `send_request_on_id_main_body` の `__closure__`。`compiled_cell`）
- セルに印を書くと待ちはすぐ返り、返る途中で印を添字で引いて `TypeError` になった（`request_llm_inference_claude.py:220`）。2版目は印が返る前提で書いていて素通しになっていた。失敗を受けた呼び出しの例外を `LLMRequestFailed` に置き換える形に直した

## 確かめたこと（2026-10-09、ペルディション。`136_` の `CLAUDE_CUSTOM` を存在しないモデル名にして 404 を起こした）

- 自由行動（`master_ai_facilitator`）: 404 を3回受けて `giving up after 3 client error(s)`。送信スレッドの死 → `woke the call` → `Thread-2 (execute) stopped after the failed llm request` → `ended the wait (4 button(s), enabled=True)` が 0.33 秒で続いた。本文の欄に「LLM への依頼が失敗した（master_ai_facilitator）: NotFoundError 404: model: claude-nonexistent-0」「この行動は中断した。」「選択肢を戻した。」が3行とも印付きで出て、ギルドの4択が戻った（写真 `out\drive\stall_after_fix.png`）
- 戻った選択肢の「出る」を押すと、場面の語り（`narrator`。構造なしの送信）も同じ 404 で失敗し、同じ流れで待機が終わった。構造なしの送信の経路と、戻った選択肢が押せることを確かめた
- 1版目で止まった待ち（`finished_event` を立てた後）に、ゲーム内スクリプトで `response_from_llm` のセルへ印を書くと、待ちが返って呼んだ側（`336_` の包みを経由）が `TypeError` で死に、手当てが「処理が途中で止まった: TypeError …（336_crime_overhaul を経由）。」を出して待機を終えた。`execute` の素の例外の扱い（経由した MOD の名前・待機の終わり）はこの回で確かめた
- 元の設定に戻した後の自由行動は、手当ての包みを通って返事が出た。スレッドの死は0件
- 確かめていないもの: ローカル（llama.cpp）の送信。会話の直前の人物の詳細生成（`generate_npc_detail_and_ready`）の死。メインスレッドで呼ばれた送信の失敗。OpenAI / Gemini の 4xx の打ち切り（状態番号の読み方はオフラインの検査だけ）

## 世界作成の画面で止まった件（2026-10-11 に直した。実機の失敗では未確認）

`144_` を試した世界づくりで、町の生成（`create_settlement_detail`）の型の検証エラーが続いて送信スレッドが死んだ（[§3.95](3.95.md)）。
手当ては待っている頼みを起こし、生成のスレッド `Thread-58 (generate_world)` は `LLMRequestFailed` で死んだ。
画面は「世界を生成しています…」のまま「生成する」が押せず、ゲームを起動し直すしかなかった（2回）。

- 死んだのが `execute` ではないので、待機を終える側に入っていなかった。ゲームの `scripts.functions.finish_button_load(app)` は遊ぶ画面の待機の終わりで、世界作成の画面のものではない
- 世界作成の画面には本文の欄が無い。`add_text` は `AttributeError: 'InstantaleApp' object has no attribute 'to_save_texts'` で落ち、理由も画面に出なかった（`stall guard: add_text failed` が2回ずつ）
- 世界作成の画面（`app.world_generate_screen`）は自分の `finish_button_load(self)` と、文の欄を書き換える `update_world_generate_check_label_text(self, text)` を持つ。生成は `generate_world(self, world_name)` を別スレッドで回す
- 表に出ていない世界作成の画面で、部品を押せない形にしてから画面の `finish_button_load()` を呼ぶと、「生成する」だけが押せる形に戻った。「戻る」と自由施設の切り替えは押せないまま、文の欄はそのままだった（ゲーム内スクリプト `out\drive\worldgen_finish.py`。読んだ後に元へ戻した）。生成中にゲームがどの部品を押せなくしているかは測っていない

直し方: `generate_world` と `check_violation_thread` の死で、世界作成の画面の文の欄に理由を出し、画面の `finish_button_load()` を呼ぶ（TECH.md §5.12）。
世界作成の画面が出ているあいだの送信の失敗も文の欄に出す。
オフラインの検査（`tools\tests\test_stalls.py` の「世界作成の画面」8件）は通った。
実機でわざと失敗させた回はまだ無い。
次に起きたら、`out\modloader.log` の `ended the wait on the world screen (…)` と、その2秒後の `the world screen 2s later (…)` で、「生成する」が押せるか（`disabled=False`）と、文の欄が生成中の表示に書き戻されていないかが分かる
