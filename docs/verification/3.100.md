## 落ちたもの: 127 が足す `--checkpoint-every-n-tokens`

同梱の llama-server が b7054 から b10642 に替わり、`--checkpoint-every-n-tokens` が無くなった（近い旗は `--checkpoint-min-step`。チェックポイントの最小間隔で既定 8192）。
127 はこの旗を足すので、llama-server は `error: invalid argument: --checkpoint-every-n-tokens` で即座に終わり、
「開始する」で `AIManager.set_ai_models` が `同梱llama-serverが起動しませんでした` を投げてゲームが落ちた（2回とも同じ）。
ゲームが渡す引数は main_025 と同じで（`out\llm_speed.log` の `[LAUNCH]`）、同じモデルと同じ引数で直接起こすと `{"status":"ok"}` になった。

## b10642 での測り直し

ゲームの記録（`output_data\`）の頼みを時刻順に、Fenrir-X-26B-A4B（RTX 4070 Ti SUPER 16 GB）で流し直した。

区間は2つ。混ざった区間は、実プレイの頼み（作成・検査・`mod_verify_*` を除く）で種類が最も多い連続60件（語り・会話・依頼・MOD の頼みなど14種）。戦闘の区間は、審判（`referee_*`）が最も多い連続60件。

- 末尾に足していくだけの頼み（4種を6周）では、`-cms` はどの値でも変わらなかった

### 127 版4 で自動で付ける（自動で合わせる）

- 下書き役は、起動するモデルと同じフォルダの `mtp\` から探す
- 合うかは GGUF の先頭の情報で決める（`mtp_matches`）。下書き役の構造が「本体の構造 + `-assistant`」、MTP の層がある、出口の幅（`embedding_length_out`）が本体の `embedding_length` と同じ、注意の形と RoPE の10項目と語彙が同じ。読めない値が1つでもあれば付けない
- 実物で: Fenrir-X・Eclipsed-Phoenix・Shadow-Siren・Gemma QAT に付き、Qwen3.5-9B には「構造が合わない（qwen35 と gemma4-assistant）」で付かない。Eclipsed-Phoenix と Shadow-Siren も下書き役付きで起き、戦闘の頼み10件で採用は 43%（失敗0件）
- 情報を読むのは起動のときに1回（モデルと下書き役で 0.14 秒。2回目からは控えを使う）
- サーバが `--model-draft` と `draft-mtp` を知っているとき、設定欄に投機の旗が無いときだけ付ける
- 付けて起きなかったら、`AIManager.set_ai_models` の包みが外して1回だけ起こし直す（その組はプロセスの間は付けない）。この経路は検査だけで、実機では起きていない
- 設定: 「MTP の下書き役を自動で付ける」（既定 ON）、「MTP で一度に下書きするトークン」（既定 4）

直す途中で、さらに2つ分かった。

- 起動の約6秒後に走る遅れた当て直し（boot #2、約7秒かかる）と「開始する」が重なると、boot #2 の MOD の適用が作り直しの途中を包んでいた。途中では送り口がプロバイダの素の関数で、別名の張り替えでプロバイダの関数までローダの包みに替わった
- 言語の包みは `functools.wraps` で、包んだ関数の `__dict__`（ローダの印と `__original__`）を写す。写しがローダの層に見え、包み直しでは「別の対象に当てた包みの別名」と見なして飛ばしていた

直したこと（ローダ。TECH.md §5.3）:

- boot の始め（MOD の適用より前）に `set_ai_models` を包み、終わった直後に `watch_aliases` の登録を順に包み直す。登録は sys に置き、前の世代の仕掛けが残っている間も今の世代の登録を包み直す
- `set_ai_models` が走っている間は旗を立て、MOD の適用も見張りも送り口を包まない。boot が錠を持っていれば、終わってから包み直す
