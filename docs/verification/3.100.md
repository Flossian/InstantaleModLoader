## 落ちたもの: 127 が足す `--checkpoint-every-n-tokens`

同梱の llama-server が b7054 から b10642 に替わり、`--checkpoint-every-n-tokens` が無くなった（近い旗は `--checkpoint-min-step`。チェックポイントの最小間隔で既定 8192）。
127 はこの旗を足すので、llama-server は `error: invalid argument: --checkpoint-every-n-tokens` で即座に終わり、
「開始する」で `AIManager.set_ai_models` が `同梱llama-serverが起動しませんでした` を投げてゲームが落ちた（2回とも同じ）。
ゲームが渡す引数は main_025 と同じで（`out\llm_speed.log` の `[LAUNCH]`）、同じモデルと同じ引数で直接起こすと `{"status":"ok"}` になった。

## b10642 での測り直し

ゲームの記録（`output_data\`）の頼みを時刻順に、Fenrir-X-26B-A4B（RTX 4070 Ti SUPER 16 GB）で流し直した。
ゲームと同じ引数に条件の旗だけを足し、`timings` の `prompt_n`（計算し直したトークン）と `prompt_ms` を合計した。
区間は2つ。混ざった区間は、実プレイの頼み（作成・検査・`mod_verify_*` を除く）で種類が最も多い連続60件（語り・会話・依頼・MOD の頼みなど14種）。戦闘の区間は、審判（`referee_*`）が最も多い連続60件。

| 条件 | 混ざった区間 再計算 / 処理 | 戦闘の区間 再計算 / 処理 | RAM の最大 / VRAM |
| --- | --- | --- | --- |
| 統合（素のゲーム） | 90% / 32.5 秒 | 63% / 53.6 秒 | - |
| `--parallel 1` | 90% / 31.3 秒 | 67% / 53.4 秒 | 22728 / 15035 MiB |
| `--parallel 1 -cms 256` | 90% / 30.8 秒 | 66% / 52.9 秒 | 22816 / 15040 MiB |
| `--parallel 1 --cache-ram 0` | 99% / 29.6 秒 | 96% / 64.8 秒 | - |
| `--parallel 1 --cache-ram 16384` | 90% / 30.7 秒 | 67% / 53.2 秒 | - |
| `--parallel 1 --swa-full` | - | 59件で 471 秒 | VRAM 15812 MiB（あふれた） |

- b10642 は RAM のプロンプトキャッシュ（`--cache-ram`、既定 8192 MiB）が、追い出された頼みの状態を戻す。そのため `--parallel 1` でも統合と処理時間が変わらない。切ると戦闘の区間で 21% 遅くなり、これが旧版で旗が打ち消していた損に当たる（[§2.48](2.48.md)）
- `-cms 256` は戦闘の区間で 2021 トークン（1.2%）減らした（60件のうち1件が 4396 → 2375）。RAM は +88 MiB、VRAM は変わらない。`-cms 1024`・`-ctxcp 128` は `-cms 256` と同じ
- `--cache-ram` を 16384 に増やしても変わらない。1件が約 1.1 GB で、8192 MiB で押し出しは起きているが、押し出されたものを使う頼みは区間の中に無かった
- `--swa-full` は VRAM からあふれて約9倍遅い
- 末尾に足していくだけの頼み（4種を6周）では、`-cms` はどの値でも変わらなかった
- `--cache-reuse 256` は「この文脈では使えない」として llama-server が無効にしている（SWA のモデル）

## tools が llama-server を CPU で起こしていた

b10642 の CUDA 版のフォルダには `cudart64_12.dll` / `cublas64_12.dll` / `cublasLt64_12.dll` が無く、ゲームのフォルダ直下にだけある。

`popen_server` で起こすと GPU に載る（4842 t/s、VRAM 14765 MiB）。5本の道具そのものは流していない。

## recon の退避が同じ版でも注入のたびに2本増えた

起動直後の注入では `__main__` が組み上がっておらず、`get_game_version()` が取れずに `game_version` が None になる。
次の当て直しでは `014` が取れるので、`_same_build` が別のビルドと見なして退避していた。
1回の起動で2本ずつ増え、上限20本で古い版の控えが押し出された（main_024 の控えは残っていない。main_023 が1本、main_025 が17本）。
ローダ `recon`: `game_version`（`LATE_KEYS`）は、どちらかが None なら比べない。`app_version` が読めないときは従来どおり別のビルド扱い。
直した後の起動（22:13・22:23・22:50）では退避も刈り込みも起きていない。

刈り込みは版を問わず古い順に消していたので、同じ版の退避が溜まると前の版の控えが押し出された。
ローダ `recon`: 版ごとに1本（いちばん大きい zip。起動直後のダンプは中身が少ないので大きさで選ぶ）は消さず、上限 20 本は同じ版の2本目以降だけで数える。
残っていた控え（main_023 のフォルダ、main_025 の17本、main_026 の3本と今の `out\recon\`）は、2026-10-14 にリポジトリの外の `recon_history_safe\` へ写した。
main_024 は `out\` の外・git・ほかのフォルダのどこにも残っていない。

退避先を `out\recon_snapshots\` から配布フォルダ直下の `recon_history\` へ移した（`out\` は消してよい置き場のため。本人の判断）。
前の退避先の中身は注入のときに移る（`migrate_old_snapshots`）。手元の21件は直後に移した。

退避する条件を広げた（本人の依頼: 版が変わる・関数の変化・その他の特異な変化）。決まりは GAME.md §1.1。

広げた後の最初の起動（10-15 00:38）で、版が同じなのに2本退避した（`main_026_20261014_4.zip` と `main_026_20261015.zip`。理由は `exe_size: None -> 716359680`）。
