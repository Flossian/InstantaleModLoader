# 3.63 街に出資して施設を建てる（`331_`）: 実機で6種類とも成立・残るは2項目

決まりは `331_` の DOC.md。
開発中は `915_facility_investment` の名前で動かした。
土台は2つのフレームワーク。
建物は `modfacility`（TECH.md §5.8）、主人は `modnpc`（TECH.md §5.7）で、`modnpc` と組で使う最初の MOD。
ゲーム側の事実は GAME.md §2.7（施設と `area["size"]`）・§2.11（闘技場の相手とランク）・§2.17（宿泊の1単位と訓練の3年）・§2.28（素データの辞書）・§2.32（新しい主人公）。

**自分の宿屋での無料の滞在は前払い**（ゲームに引かせてから差を返す形をやめた。TECH.md §3.3.4）。ローダの窓口に聞いた部屋の額を先に足しておき、ゲームが引いて元に戻る。`stay: prepaid` が出て所持金が動かないことを**実機でやり直した**（同じ宿で2泊）。
2泊とも所持金は1Gも動いていない（`218_probe_vacation` の `gold_before` と `gold_after` が両方とも同額）。
ただし**1泊目だけ前払いと引き落としが食い違った**。

```text
1泊目  stay: prepaid 1000 for the room ('luxury_suite')
       WARN stay: the room cost 2000 but we prepaid 1000; corrected 1000
2泊目  stay: prepaid 1000 for the room ('luxury_suite')   （WARN 無し）
```

帳尻は合っている（どちらも最後は元の額）が、1泊目にゲームが引いたのは窓口の言う額の倍だった。
同じ宿・同じ部屋・同じ設定で2泊目は一致しているので、**額そのものではなく1泊目の区間に何かが混ざっている**。

**2点目**（版41 で月数を3にした回）。

```text
3ヵ月  stay: prepaid 1000 for the room ('luxury_suite')
       WARN stay: the room cost 5000 but we prepaid 1000; corrected 4000
```

部屋のボタンの値札は `高級個室(1000円)` で、月数は3。
引かれたのは 5000 で、1000×3 でも 1000×2 でもない。
1ヵ月のときが 2000、3ヵ月のときが 5000。所持金は両方とも最後は元の額に戻っている
（`218_` の `gold 4648470 -> 4648470 (moved 0)`）。
`327_inn_quality` には金を触るコードが1行も無く（`gold` も `price` も出てこない）、
315 はこの回も窓を開いていない。
**次に測ること**: よその宿屋で同じ部屋・同じ月数に**払って**泊まり、
ゲーム単独の引き落としが月数でどう動くかを見る（MOD の前払いが混ざらない条件）。
`327_inn_quality` に値段を触るコードは無く、`315_vacation_custom` はどちらの回も `price:` の行を出していない
（315 の窓は開いていない）。取った先は特定できていない。
`settle_room` の注記どおり、この区間で他の MOD が金を動かせば巻き込む作りなので、
**どの MOD がいつ引いたかを録る手立て**（所持金の変化をその場で記録する probe）が要る。

## 設計の根拠（実セーブ6世界）

語彙はゲームのもの。
種類は `facility_type`、等級は `tier`、規模は `area["size"]`。
実セーブ6世界の施設を数えると `inn` 52・`colosseum` 6・`training_facility` 4 で、`tier` は `basic` / `standard` / `advanced` の3語だけ。
`config` は `{"level_of_detail": 0}` だけで、`owner` は主の id、主の `job` は `facility_type` と同じ語（GAME.md §2.13.1）。

種類ごとの最低の規模は街を数えて決めた（56街。村19・町25・都市12）。

| | 村 | 町 | 都市 |
| --- | --- | --- | --- |
| `inn` の実数 | 0〜1 | 1〜2 | 0〜2 |
| `colosseum` の実数 | 0 | 0〜1 | 0〜1 |
| `training_facility` の実数 | 0 | 0〜1 | 0〜2 |
| `general_store` の実数 | 1 | 1〜2 | 1〜2 |
| `specialty_shop` の実数 | 0〜1 | 1〜3 | 1〜2 |
| `blacksmith` の実数 | 0〜1 | 1〜2 | 1〜2 |

闘技場は町にも2つあった（村には無い）ので、道場と闘技場の最低の規模は「町」にした。
辺鄙な田舎に闘技場ができるのはおかしいので、村を外せば足りる。
軒数のほうは種類ごとではなく、その街に建てられる合計（村1・町2・都市3）で、数えるのはこの MOD で建てた分だけ。
種類ごとに上限を持ち、ゲームが最初から置いた施設まで数えていた形では、宿屋も雑貨店も最初から1軒ある村に何も建たなかった。

## 作りに効いた分かったこと

**実行時に足した施設でも、中の選択肢はゲームが `facility_type` から出す。**
`inn` の `宿泊する` / `会話する`、`colosseum` の `試合に出る` / `観戦する`、店の `売買する`、道場の訓練。
版1が店と道場を伏せていた理由（`DisplayTrainingChoice` の語彙が読めない）は、こちらが組む場面が無いので消えた。
この MOD が足すのは `売上を受け取る` と `無料で泊まる` と出口だけ。

**素データを施設 id で引く経路は、中に立っている間だけ写しを置けば通る**（`modfacility` の `plain=True`）。
売買の `KeyError`（GAME.md §2.28）と闘技場の `ColosseumMatchStart.method` は同じ穴で、
写しを置く前は試合のワーカースレッドごと死んだ。
写しは保存の前に外れ、書き出しの直前にも網を張ってある。
宿屋は写しを置かない（`VacationStartManager` は実体で足りた）。

**画面の判定は足す側それぞれが持ってはいけない。**
部屋選び・会話の最中・会話相手の一覧の3回とも、同じ取りこぼしが別の場所から出た。
道を足す側には画面の判定が1つも無かった。
ローダの `can_add_here` の1か所へ寄せて決着した（TECH.md §5.8）。

**相手が触る値を見に行く形は順序に左右される。**
「会話の最中は中のまま保存しない」を `in_conversation` の旗で見ていたが、`modnpc` が先に旗を落としていた。
フレームワークどうしはどちらが先かを約束しない。

**痕跡を消す手当ては、素のゲームができることまで壊す。**
会話の途中の保存で相手の id と選択肢を落としていたので、ロードで会話も一覧も戻らなくなっていた。
画面と背景の副作用を3版ぶん追いかけた末に、消すのをやめて決着した（いま話している相手だけ掃除から外す）。
素のゲームならどう振る舞うかを先に確かめていれば1回で済んだ。

**背景は MOD が描かない。**
ゲームは施設の**名前**で絵を引き、無ければ生成して保存する。
借りた部屋の絵を描いて「描いた覚え」でゲームの描画口を止めたり通したりしていたことから、2回読み込み・入口へ移ったのに店の絵・闘技場で何も出ない・宿泊後に出ないの6件が出ていた。
描くのも頼むのもやめて全部消えた（TECH.md §5.8）。

**周回の鍵は世界×主人公**（`state.playthrough_key`。TECH.md §5.4）。
世界名だけで控えていたので、同じ世界で作り直した新しい主人公が前の主人公の4軒を受け取り、主人がその新しい主人公を出資者として迎えた。
建物の id は `<土地>-<番>` で周回をまたいで重なるので、`forget` は控えの写しも捨て、新築は写しを使わない。

**名前は鍵の hash で選ぶだけでは重なる。**
主人は候補6人から建物の id で選んでいたので4軒で2人が同じ名になり、施設の名前は別の世界の同じ id で同じ名になった。
どちらも生成 AI に作らせ、その世界で使っている名前を避ける形にした（落ちたときの表も使用中の名前を飛ばす）。

## まだ確かめていないこと（実機の手順）

先に `330_real_estate` 版20 の手順（VERIFICATION.md [§3.62](3.62.md)）を通す。
土台（`modfacility`）はあちらで確かまるので、ここで落ちたものはこの MOD か `modnpc` との組み合わせの問題に絞れる。
見るログは `out\facility_investment.log`（`modfacility:` / `modnpc:` の行もここに出る）と `out\modloader.log`。

## オフラインで確かめたこと

`tools\tests\test_facility_investment.py` 252件。
偽の `Facility` / `VacationStartManager` / `EntryColosseumMatchManager` / `ColosseumMatchStart` / `Character` / `Clock` を差し込んで、
表・種類ごとの設定・窓口・出資・上限・建物の中・売上・宿泊・闘技場・店と道場・保存・ロード・別の世界・新しい主人公・設定画面・例外の場面を通している。
実機で当てていない 14（別の世界を読む）はここで通っている。

検査の土台で1つ踏んだ。
`setup()` が `main.InstantaleApp` を新しい子クラスで差し替えるので、2回目以降の `setup()` が前回の子をさらに継承し、フックが世代のぶんだけ積み重なった。
3回目には5段になり、最初の世代の `apply()` が閉包に抱えていた古い控えから、新しい世界へ建物が生えた。
`330_` の検査が `BASES` に素の基底を別に持っているのはこのためで、同じ形にした。
閉包が控えを抱えたまま世代をまたぐと消したはずのものが戻る、という形は実機でも起きうる（ローダの世代管理が防いでいる。TECH.md §3.5）。
