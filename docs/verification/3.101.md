# 3.101 ゲームの更新の見張り（drift）をローダに入れた: 包みの外れ・引数の変化・書き換えの空振りを遊んでいる間に見つける・recon と役割を分けた・入れて最初の実機でローダの不具合を2つ見つけて直した・送り口の `timeout` が待ちを打ち切らないと分かり、`llm.ask` と 335 は打ち切らずにログに出すことにした・一括生成の住人の名前の重複を 120 で直した

2026-10-15。
main_026 で、送り口が「開始する」のたびに作り直されて MOD の包みが外れていたのを、名前の数え上げでは見つけられず、実機の確認の途中で見つけた（[§3.100](3.100.md)）。
公式が今後は積極的に更新すると告知しているので、名前の数え上げに頼らず、外れたことや変わったことを動いているゲームが自分で見つける仕組みをローダに入れた（TECH.md §5.13）。

## 何を見つけるか

起動時に「対象の名前が見つからない」と分かるもの（台帳の unresolved。GUI の警告の欄）は前からある。
名前は残っているのに効かなくなる道を3つ足した。

| 見張り | いつ | 見つけたら |
| --- | --- | --- |
| 包みの外れ | 5秒ごと。この世代で被せた包み（約1100）が対象の今の値の鎖に残っているか | 2回続けて同じ値で外れていたら付け直す（対象ごとに5回まで） |
| 引数の変化・対象の消失 | 起動のたび。recon の前の版からの関数の変化を、MOD が包んだ対象で絞る | 出すだけ（recon が版の変化を見つけてから7日） |
| 書き換えの空振り | `wrap_outgoing` の書き換えの当たり数を版ごとに控えて比べる | 前の版で当たっていたのに今の版で当たらなければ出す |

出す先は `modloader.log` の `drift:` の行、`status.json` の `drift`、GUI の警告の欄（デバッグモードのときだけ）。

## recon との分け方

最初は drift が包んだ対象の引数を自前で版ごとに控えていた（`hooks.json`）。
recon も全関数の引数を控えて比べていて、同じことを2か所でしていた。版の見分けの鍵も別々に持っていた。
次のように分け直した（GAME.md §1.1 の役割の表）。

- recon がゲーム側の事実を持つ。版の鍵（`recon.build_key`）と、前の版からの関数の変化（`recon_history\current\changes.json`）。
  版をまたいだ関数の比べは、前は recon でもしていなかった（版が替わったときは素性の違いだけを残していた）。
  基準を置き換えるときと、`changes.json` がまだ無いときに、前の版の zip の `targets.txt` と比べる
- drift は MOD との突き合わせと遊んでいる間の見張りだけを持つ。`changes.json` を包んだ対象で絞り、外れと書き換えの空振りを見る。
  書き換えの当たり数は `recon_history\drift\` に置く（recon は zip と `current\` 以外に触らない）

実物の控えで流すと、recon は main_025（`main_025_20261014_11.zip`）と比べて「消えた10・変わった13・増えた15」を出した。
drift が絞った MOD の包んでいる対象は11件。
[§3.100](3.100.md) の表の引数の変化に加え、4つの部品の送り口の引数（`model=None` が `max_tokens` の前に入った）が出た。
`max_tokens` を位置で渡す呼び出しはローダにも MOD にも無かった（`llm.ask` はキーワードで渡す）。

## 入れて最初の実機で見つけたローダの不具合

2026-10-15、ローカルで 検証ワールド2 を動かした（街の移動・ギルドの会話・題の画面との往復2回）。
見張りが2種類の外れを出し、どちらもローダ側の不具合だった。

- ローダの見張り（`stalls`）の送り口の包みが2枚に重なっていた。
  boot はローダの部品を `(loader)` の名で当て、`watch_aliases` の包み直しは `<loader>` の名で当てていたので、包みの鍵が食い違い、見回りが同じ包みを別物と見て付け直した。
  `watch_aliases` が呼ばれた時点の持ち主を控えて、包み直しでも同じ名で当てるようにした
- 計測の `205_` がプロバイダの関数を直に包んだ層が消えていた。
  [§3.100](3.100.md) で足した「`set_ai_models` に入るときにプロバイダの関数を素に戻す」処理が、ローダの層を全部剥がしていた。
  剥がすのを、送り口を包んだ層（印の対象が送り口のもの）が別名の張り替えで載ったものだけにした

直した後に同じ操作をすると、外れは0件、`stalls` の包みは1枚、`205_` の層も残った。
その後、宿（327 の部屋の選択・1週間の過ごし方）、依頼の掲示板、依頼の中の戦闘6手、ゲームオーバーまで通し、外れは0件だった。

## 検査

`tools/tests/test_drift.py`（新規）:
差し替えを2回目の見回りで見つけて付け直す、ゲームが `functools.wraps` や閉包で包み直しても外れと言わない、付け直しの上限と切ったとき、ローダ自身の見張りを包み直した後に二重にしない、`changes.json` を包んだ対象で絞る・7日を過ぎたら出さない、書き換えの空振りを見込みで判定する。
ローダの見張りの二重は、持ち主の名を控えない形に戻すと落ちることを確かめた。

`tools/tests/test_recon_archive.py`:
前の版のうち関数のいちばん多い記録と比べる（同じ秒に作った zip でも名前の日付で順を決める。更新時刻だけで決めた形は5回に1回ほど落ちた）、変わった・消えた・増えたを分ける、`detected_at` を引き継ぐ、基準を置き換えない回でも `changes.json` が無ければ書く。

`tools/tests/test_common_parts.py`:
プロバイダの関数から送り口の層だけを剥がし、直に包んだ層は残す。

全部の検査（CI と同じ形）と構文の検査は通った。

## 残りの確認（2026-10-15 夜。クラウドの Haiku 5.5 とローカルの両方）

| 確かめたこと | 結果 |
| --- | --- |
| 見張りの巡回（クラウド） | テストワールドで宿・依頼の生成・依頼（戦闘2回）を最後まで終え、外れは0件。控えに戻した |
| 知らせの点 | 点を立てると左下の MOD 用のボタンの右上に赤い点が出て、戦闘の画面でも同じ位置に出た。描けないエラーは出ない |
| 339 の組織（ローカル） | 検証ワールド3 をローカルで作り、構造の説明に勢力が3つ入った。144・145・132 も効いた |
| 143（ローカル） | ランダム作成で `[WORLD]` と `[BUILD]` が出た |
| 335 の待ちの上限 | 下の「送り口の `timeout`」を直した後、上限を 0.05 秒にして押すと `gave up` で取りやめ、ボタンが戻った（クラウド）。直す前は、ローカルで上限 0.05 秒でも外見の頼みを 1.3 秒待って描き直した。後に打ち切りをやめた（下の「打ち切りをやめ、ログに出すだけにした」） |

### 送り口の `timeout` は待ちを打ち切らない

長い返事になる頼みを `timeout=0.5` で送ると、クラウドは 7.86 秒、ローカルは 5.83 秒後に返事を最後まで返した（クラウドで送ったのは1回で、送り直しも無い）。
ローダの `llm.ask`（MOD 18本が使う）と `335_` は、待ちの打ち切りをこの `timeout` に任せていたので、LLM が返らなくなると呼んだ側が止まったままになる作りだった。

- ローダ `llm.ask`: 送り口を別のスレッドで呼び、`timeout` 秒だけ待つ。過ぎたら None と `TimeoutError`。実機（クラウド）で 0.5 秒で打ち切った
- `335_`: 外見の頼みを別のスレッドで呼び、`LOOK_TIMEOUT` 秒だけ待つ（DOC.md の「120秒返らなければ取りやめる」がこれで本当になった）
- 検査: `test_patch_registry`（ask の打ち切り）、`test_player_portrait_regenerate`（335 の打ち切り）。どちらも直す前の形では5秒待って落ちる

#### 打ち切りをやめ、ログに出すだけにした（2026-10-16、本人の判断）

MOD の上限は開発機（比較的速い環境）の実測から決めていて、遅い環境で打ち切りが頻発する懸念が出た。
開発機の `llm.ask` の記録 1,638 件では、95% の値は上限の 1/4〜1/20 だったが、`404_` で上限 120 秒に対して 102.6 秒の回が1件あった（2026-08-28、仲間2人の会話、プロンプト 3,817 字）。
ローカルの速さは GPU で何倍も違い、127 の1スロットでは MOD の頼みがゲームの頼みの後ろに並ぶので、待ちも延びる。
打ち切ると、遅い環境では MOD の働きが毎回黙って消える。返事が永久に来ない害より大きいので、打ち切らないことにした。
main_026 の v1.16.1 は、送り口が `timeout` を守らないので、実際には打ち切っていなかった（同じ動きに戻した）。

- ローダ `llm.ask`・`335_`: `timeout` 秒を過ぎたら WARN（`still waiting` / `slow:`）を出して待ち続け、返ったらかかった秒数をもう1行出す
- 335 の DOC.md は「120秒返らなければ取りやめる」を「遅くても最後まで待つ（120秒を過ぎたらログに出す）」にした
- 検査: 同じ2本を、上限を過ぎても返事を受け取ること・WARN を2行出すことに書き換えた
- 遅い環境の実際の速さは測っていない

### 一括生成で作られた住人の名前の重複

検証ワールド2 の一括生成の前（8人）と後（47人）の素データを比べると、重複2組（先に居た人と同じに読める名前）は、どちらも一括生成で生まれていた。
`120_` は人物を組み立てるところ（`World.generate_character`）で改名していて、一括生成では組み立てが起きず、次に読み込むと「既に居る人」として触らなかった。

- `120_` 版8: 一括生成の本体（`run_world_bulk_generation`）が走っている間の `write_area_data_to_world_dict` の書き込みで、新しく増えた住人をその世界の住人（先に居た人と、先に裁いた新しい人）と突き合わせて直す。並べて走るので1つずつ順に裁く。遊んでいる間の書き込みは今までどおり組み立てで裁く
- 検査: `test_npc_name_dedup` の「一括生成で書かれる住人」。直す前の形では落ちる

## 中身だけの更新に気づく（2026-10-16）

版の見分けは、Epic の版の名前・exe の大きさ・同梱の llama-server だった。
Epic 以外の入手経路（Steam など）では版の名前が取れず、大きさの変わらない更新は見分けられなかった。
また、版の変化に気づいても recon は記録を残すだけで、引数が変わらない更新（中身だけの直し）では drift の警告も出ず、遊ぶ側から更新が見えなかった。

- recon: 素性に exe の sha256（`exe_sha256`）を足した。版の鍵の末尾にも頭の12文字が付く。
  実物の exe（約700MB）で初回 0.47 秒、控え（`recon_history\exe_digest.json`）から読むと 0.005 秒
- recon: 基準にハッシュが無ければ、置き換えない回でも書き足す。
  最初の実機の起動で、基準（読み込み 5587）が起動直後の走査で置き換わらず、ハッシュを持たないままだった。
  書き足した後の起動で、基準にハッシュが入り、読み込みの数はそのまま、余分な退避も無かった
- recon: `changes.json` を初めて書くときの見つけた日時を、前の版を退避した時刻にした。
  実物の控えでは `main_025_20261014_11.zip` の 2026-10-14 15:34（main_026 を初めて起動した時）になる
- drift と GUI: 前の版からの変化が7日のうちにあれば、引数の変化が0件でも「ゲームが更新されました（前の版から。見つけた日）」を警告の欄に出す。
  実機の起動で、ログに `drift: the game was updated since main_025` が1回出て、GUI の警告の欄にも出た。
  GUI に出すのは、見張りの4つとも、デバッグモードのときだけにした（作る側が確かめるためのもの）
- 検査: `test_recon_archive`（ハッシュが違えば別のビルド・足す前の控えとは比べない・版の鍵の形・控えの使い回し・基準への書き足し・見つけた日時）、`test_drift`（関数の変化0件でも出す・7日を過ぎたら出さない）
