# 3.135 任意の OpenAI 互換サーバー（LM Studio など）での依頼の生成の暴走と、`139_` の OpenAI の経路への広げ: ゲーム抜きで上限なし 8 回中 5 回失敗・上限あり 8 回とも型どおり、ゲームの中でも1回成立

2026-11-24。
LM Studio を「任意の OpenAI 互換サーバー」に指定すると、依頼の生成で敵を書き足し続けてコンテキスト長を使い切る、と報告を受けた。
同じモデルをゲーム内蔵の llama.cpp で使うと通る、という報告だった。
`139_` 版1 は `LlamaCppClient.chat` だけをフックしていて、互換サーバーの経路は素通りしていた。

## 互換サーバーの送り方（exe の定数）

`request_llm_inference_any_server` は `openai.OpenAI(base_url=…)` の `beta.chat.completions.parse` に pydantic の型を `response_format` で渡す。
SDK が型を `response_format.json_schema.schema` に直して送るので、互換サーバーはその型から grammar を作る（GAME.md §2.12）。
プロンプトに型の文は埋め込まない（報告のログでも `prompt_tokens` は 3,675）。
ゲームの設定では、`llm_inference` は `cloud_api_key` のままで、`cloud_llm_provider` を `任意OpenAI互換サーバー` にする（`llm_inference` を `any_server` にすると内蔵の llama.cpp に落ちた）。

## ゲーム抜きの再現

この PC に LM Studio が無いので、ゲーム同梱の llama-server を別のポートで起こし、OpenAI 互換の `/v1/chat/completions` へ SDK と同じ形（`response_format` の `json_schema`・`strict`）で送った。
LM Studio も GGUF の構造化出力は llama.cpp の grammar で作る。
モデルは Eclipsed-Phoenix-26B-A4B（Gemma4 26B A4B 系）、起動引数は `tools\quest_gen_probe.py` と同じ（コンテキスト長 16,384）。
messages は型を埋め込まない形の記録（output_data の 109）、型は埋め込みのある記録（86）から取り、SDK と同じく object に `additionalProperties: false` と全欄必須を付けた。
上限は `139_` の `with_limited_response_format` で付けた。

| 条件 | 回数 | 型どおりに書き終えた | 時間 |
| --- | --- | --- | --- |
| 上限なし | 8 | 3（5回は `finish_reason: length`） | 成功 19〜23 秒、失敗 22〜45 秒 |
| 上限あり（敵 5 ほか `139_` の既定） | 8 | 8 | 18.7〜22.6 秒 |

- 失敗した5回は、敵の一覧に 32〜54 体を書き足している途中で約 14,100 トークンに達して切れていた。どの回も normal 2・miniboss 1〜2 の後に足し続ける形で、報告のログと同じ
- 上限ありは 8 回中 7 回が敵 5 体ちょうど、1回が 4 体。イベント 2 とボスは毎回そろった
- 上限なしで通った3回も敵は 5〜6 体（miniboss 3〜4）で、プロンプトの「normal 2〜3種、miniboss 1種」より多い

## `139_` 版2

openai の SDK の送信の1点（`openai._base_client:SyncAPIClient.post`。`136_` と同じ）もフックし、`response_format` の型が `QuestStructure` のときだけ写しに上限を付ける。
body と messages、ゲームの型は書き換えない。
記録の行に経路（`llama.cpp` / `openai`）を足した。
検査は `tools\tests\test_fix_quest_generation_runaway.py`。

| # | 確かめること | 合格 | 結果 |
| --- | --- | --- | --- |
| 1 | 互換サーバーの経路で上限が付く | `out\quest_generation_runaway.log` に `limited QuestStructure #N (openai)` | ✓ 2026-11-24。世界Fの裏の仕事の生成1回で `#1 (openai)`、8つの並びに上限。`modloader.log` は `any_server in use` |
| 2 | 送り直しが無い | 互換サーバーへのリクエストが依頼の生成1回につき1つで、`stop` で終わる | ✓ 2026-11-24。llama-server の記録はリクエスト1つ（入力 1,345・出力 2,902 トークン）。依頼は敵 5（normal 4・miniboss 1）・イベント 2・ボスあり。サーバが CPU で動いていたので 182 秒かかった |
| 3 | LM Studio そのもので効く | LM Studio を互換サーバーにして #1・#2 | 未（LM Studio が手元に無い） |
| 4 | OpenAI 本家・Alibaba が上限つきの型を断らない | 依頼の生成が 400 にならない | 未 |

試しの後、ゲームの設定と世界Fは控えへ戻した。

## ほかの MOD の同じ抜け

内蔵の llama.cpp に向けた手当てで、互換サーバーの経路から抜けている所を洗い出した。
調べたのは `runtime` の .py の `LlamaCppClient` へのフック、`is_local_runtime` など経路の判定の呼び出し、`maxItems` / `max_length`、型の `description` に置いた手引き。
互換サーバーの経路でゲームが型の文をプロンプトに書かないことは、output_data の記録で確かめた（同じ依頼の生成で、内蔵の経路の 110 は先頭に 8,250 字の型の system があり、互換サーバーの経路の 111 には無い）。

| MOD | 抜けていたこと | 直し方 |
| --- | --- | --- |
| `339_` 版10 | 抽出・判定・情勢の型の並びの件数の上限を、`is_local_runtime()`（内蔵の llama.cpp）のときだけ付けていた | ローダに `llm.is_grammar_runtime()`（内蔵の llama.cpp か互換サーバー）を足し、それで決める |
| `342_` 版5 | 演出の選び方の手引きを型の `vfx` の説明にだけ置いていた。互換サーバーの経路では届かない | 審判の system の `- vfx:` の行の次にも置く。審判の4種の記録とも、この行がある |
| `139_` の DOC | 困ったときに `216_` の `SLOW` の行を求めていたが、`216_` は内蔵の llama.cpp の経路しか数えない | 互換サーバーならサーバーのログの `finish_reason` と `completion_tokens` を求める |

抜けていなかったもの:

- `127_` の型の説明の圧縮は、内蔵の経路が埋め込む型の文を縮める。互換サーバーの経路には縮める文が無い。起動引数は同梱の llama-server のもの
- `102_` / `105_` は superseded
- `406_` は Gemini と Claude だけが対象
- `136_` は宛先が `api.openai.com` のときだけ差し替える
- 送る文の書き換え（`wrap_outgoing`）と MOD からの問い合わせ（`llm.ask`）は、互換サーバーでは `llm_manager` の `send_request` の側で当たる
- `128_` は件数の上限を経路によらず付ける。`347_`・`404_`・`921_`・`talk_summary` は指示をプロンプトの地の文に置く

検査は `test_town_factions.py`（上限の付き方）、`test_attack_animations.py`（手引きの置き場所）、`test_patch_registry.py`（判定）。
型を使う場面は pydantic が要るので、pydantic を入れた環境で通した。
ゲームの中では確かめていない。
