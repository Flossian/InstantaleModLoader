ただし**引いてから返す方式は支払い直後の所持金が「1000引かれた値」に見える**と分かり、

**距離補正（実装時点では実機未確認）。**
`325_road_opening` が開いた道は、ゲームには隣の街と同じに見えて
どれだけ離れていても徒歩90日・馬車1000Gのまま。
そこで「間に挟む街の数」（開いた時点に `325_` が控えの `roads` の `hops` に
記録した値。読みは `WorldStore(own=False)` で読むだけ）に応じて
日数と馬車代を加算/倍加できるようにした（既定は倍加×1.0。off 可）。
実装の要点は2つ:

- いまの接続で BFS し直さない（開いた道自体が辺なので必ず「隣」になる）。
  `hops` の記録が無い道（古い版の `325_` で開いた道）は補正なしに落ちる
- 日数を**増やす**方向は、`elapse_days` に来た数が素の値（90/14）そのものの
  ときだけ予算へ置き換える。素の値と違う数は外側（`307_` の予算）が減らした
  可能性があるので頭打ちだけ掛ける（オフラインで検証済み）

オフライン86件全通（倍加・加算・off・別区間・307_ の上限との共存・
実効額の拒否と前払いまで）。

**日数の上限（後から追加・実機で成立）。** 距離補正で増えた日数を
徒歩90日・馬車30日で頭打ちにする（設定で変更可）。素のゲームの移動が一律3ヵ月
なので、それを超えないのが既定。上限後の値がボタンに出て、上限で素の値と同じに
なれば「触らない」に落ちる（既定の徒歩は挟む街がいくつでも 90 日のまま＝
素の表示 `徒歩(3ヵ月)` に戻る）。オフラインで上限の内外・上限を上げた場合まで検証。
実機（挟む街4つの道 3→8、目視で確認）: 馬車は `馬車(5000G・30日)` に頭打ち、
徒歩は既定の上限で `徒歩(3ヵ月)`、上限を 60 / 88 に変えると `徒歩(60日)` /
`徒歩(88日)` に追随。「90日だけ `3ヵ月` 表記になる」揺れは把握のうえ現状維持。

**前払い調整の穴（記録のみ。実機の発生は0件）**

`settle_fare` は移動が終わった時点の所持金を読み、3つに振り分ける。

| 読んだ値 | 解釈 | 後始末 |
| --- | --- | --- |
| `before - 設定額` | 引き落とされた | 何もしない（正しい額） |
| `prepaid`（ずらしたまま） | 引き落としが起きなかった | `before` へ戻す |
| それ以外 | 想定外 | WARN を出して**そのまま** |

3つ目に落ちる組み合わせが理屈のうえで1つある。
**運賃を変更していて、かつ引き落としが起きず、かつ移動の窓の中で
所持金が別の理由で動いた**とき。
このときずらした差額（素の運賃 − 設定額）が戻らないまま残る。

移動の窓は短くないので所持金が動く余地はある
（実際 `out/area_move_custom.log.1` には、移動の窓の中で同行者が
同行を断る会話が挟まった記録がある）。
ただし3条件が同時に要るうえ、引き落とし自体は実機13行すべてで起きているので、
`WARN fare:` は一度も出ていない。

直すなら「ずらした事実」ではなく「ずらした額」を基準にして、
どの分岐でも最後に差額を打ち消す形にする。
**今は直さない**。実機で一度も踏んでおらず、
所持金に触る処理を増やすほうが危ない（前払いへ作り替えた経緯そのものが、
所持金の見え方を触ると事故るという話だった）。
`WARN fare:` が1行でも出たらここへ戻ること。

確かめるならデバッグモードで `217_probe_area_move` を入れて普通に遊ぶだけ
（probe は `314_` / `307_` より外側なので、ゲームの生の値が録れる）。
