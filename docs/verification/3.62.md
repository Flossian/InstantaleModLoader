# 3.62 家を借りる・買う（`330_`）: 管理人まで実機で成立・残るは4件と別件1つ

決まりと設定は `330_` の DOC.md。
開発中は `914_real_estate` の名前で動かした。
建物そのものは版20 でローダの `modfacility` へ移してあり（TECH.md §5.8）、
この MOD に残るのは契約（家賃・期限・預かり）と、建物の中でできること（滞在・保管庫）と、役場の窓口。

## 設計の根拠

施設の形は実セーブ7本の全施設を数えて決めた。
足す `location` の素データは実データの `location` と同じ8項目・同じ並びにしてある。

| `facility_type` | `tier` | `config` |
| --- | --- | --- |
| `location`（77件） | 全件 `null` | `level_of_detail` だけ |
| `ward`（120件） | 全件 `null` | 同じ |
| `entrance` / `exit`（各51件） | 項目そのものが無い | 同じ |

実データの街は `entrance` から `ward` へ入り、宿・ギルド・役場・自由生成施設はすべてその `ward` から枝分かれしている。
建物を繋ぐ先はノード自身が名乗っている入口（`Node.entrance_facility`）で、引けなければ種類（`entrance` → `ward`）で探す。
組み立ては `__main__:Facility.__init__(self, app, parent_node, facility_data)`、
移動のボタンは `MovePhaseManager(app, connected_node_id, facility_move_to_id, area_id)`（GAME.md §2.2）、
滞在は `VacationStartManager(app, months, quality)`（GAME.md §2.17）。
保管庫は `toggle_twin_inventory_window(左, 右, 左の見出し, 場面名)` を、ゲームに無い場面名（`real_estate_storage`）で借りる（`402_` と同じ借り方）。

## 実機で成立したこと

| | |
| --- | --- |
| 契約 | 賃貸・建売・別の土地に2軒目。窓口から結べて、控えに残る |
| 建つ | 契約した土地の入口に1軒。ロードのたびに控えから建ち直る |
| 入る | 建物の中で「滞在する」「保管庫をあける」「家から出る」が出て、押せる |
| 滞在 | 宿代は前払いで打ち消され、活動を1つ終えると滞在が終わって建物の選択肢へ戻る |
| 保管庫 | 預ける → 開き直す → 取り出すの往復。移した時点で保存が走る |
| 共有倉庫 | 「世界で1つ」に切り替えると各建物の中身が共有へ寄り、別の土地の建物から同じ中身が開く |
| 解約・預かり・引き取り | 解約で建物が消え、中身は役場の預かりへ。どこの役場でも引き取り料で戻る |
| 家賃 | 暦が進んだときに精算する（自分の家の滞在でなくても引かれる） |
| 期限切れ | 払えない額で借りると契約が切れ、建物が消える |
| 別のノードに建った家 | 繋ぎ先をプレイヤーの居るノードから選び直す修正の後、当て直しでプレイヤーの側へ移る |
| 滞在の描写 | 宿屋でも自分の家でも、頼み文に泊まり先を1文添えると描写がその場所になる |
| 管理人 | 建物ごとに1人立ち、その人が主として滞在を通す。`会話する` には出さず、セーブにも残さない |

## 作りに効いた分かったこと

- ロードの後にログが静かでも異常とは限らない。
  滞在の活動の画面でセーブしたセーブを読むと、`where:` も `to_display_buttons` も1行も出ない（実機で確認）。理由は2つで、どちらも正しい動き。`where:` は前回と同じ token（エリア・施設・種類・中に居るか・ボタンの数）なら書かず、その覚えはプロセスに残るので**世界を読み直しても揃ったまま**になる。活動の画面は下位の画面なので `modfacility` はそもそも選択肢を足さない。出ているかどうかで見るなら層の積み直し（`330_real_estate registered ...`）のほうで、こちらはロードのたびに必ず出る
- ゲームは実行時に足した施設の `connections` を読まない。
  繋ぎ先の移動の一覧にも、建物の中の選択肢にも現れない。入ること自体は `MovePhaseManager` でできて、落ちもしない。GAME.md §2.28 の「遊んでいる最中に生まれた施設で売買を選ぶと `KeyError`」と同じ側面で、ゲームは施設を素データから引き直す。だから道も、中の選択肢も、出口も MOD 側が出す
- 宿泊には主が要る。
  主のいない施設（`owner` が `null`）で `VacationStartManager` を起こすと、暦・宿代・文まで通った後に名簿の引き当てで落ちる。滞在のあいだだけ主を据える。据える相手は物件を貸した役場の役人で、役人が引けない土地ではその建物・その土地の住人へ落ちる。プレイヤー自身は `world.characters` に居ない世界があるので使えない
- 名簿に居る人物は保存が居場所を読む。
  `save_game` は名簿の全員の `.id` を書き出すので、`会話する` に出したくないからと居場所を据えないまま名簿へ足すと、滞在が始まった直後の保存が `AttributeError: 'NoneType' object has no attribute 'id'` で落ちる。保存の直前に名簿から引き上げる仕掛けはローダが持っている（`modnpc` の `hide` / `restore`。TECH.md §5.7）ので、MOD 側で同じものを作らず預ける。一覧に出さないのは `place(listed=False)` で足りる
- `spawn` / `place` の手前にガードを置かない。
  どちらも何度呼んでもよく、名簿に実体だけ在れば `spawn` がそれを拾って記録に繋ぎ直す。「名簿に居るなら呼ばない」「`owner` が合っているなら呼ばない」と手前で飛ばすと、記録が歯抜けのまま残って `modnpc.get` が空を返し、`placed` が空なので保存の直前の `unplace` も効かない
- 注入し直しは画面を組み直すまで効かない。
  `modfacility` の層は選択肢を組むときに積み直す作りなので、建物の中に立ったまま注入しても、押せるボタンは前の版のまま。実機で「直したはずの版が動かない」を1周やった（ログに `where:` が1行も無い区間があれば、それが証拠）。確かめるときは建物から出て入り直してから押す
- ゲーム側が落ちても操作は返す。
  `execute` の例外をそのまま通すと、ワーカースレッドが終わるだけで画面が「…」のまま戻らない。宿代を返し、待機表示を解いて建物の選択肢へ戻す
- 窓はメインスレッド（Clock）から開く。
  自前のフェーズの `execute` は別スレッドで走る（GAME.md §2.1）ので、そこから Kivy に触ると窓が半端に開いたまま固まる。`402_party_inventory_transfer` がこれを踏まないのは、あちらが `on_button_press` から直接開いているため
- 宿代の返しは差額から家賃を除く。
  暦が進むのは宿泊の `execute` の中なので、同じ `execute` で家賃も引かれる。前後の差をそのまま返すと家賃まで返る
- 滞在の最中は自前の選択肢を出さない。
  並んでいるのはゲームの活動の選択肢で、そこへ「滞在する」を足すと同じ画面から滞在が二重に始まる。判断は MOD の旗ではなくローダの `is_top_screen` に任せる（同じ作りを 331 が別に持っていて、旗を落とす順の違いで片方だけ穴になった。[§3.63](3.63.md)）
- 1泊＝活動1回に固定した。
  活動の `execute` が返ったら、画面が落ち着いてから `VacationEndManager` を起こす。社交だけは2段（`VacationSocializeManager` → `...ResolveManager`）なので後段で締める。前段で締めると相手との場面が来ない
- 自分の家の滞在からは「他者と交流」と「アイテム作成」を出さない。
  見分けるのは spec のクラス名で、文言で見ると同じ言葉のゲーム側のボタンを巻き込む。宿屋の側には触らない
- 背景は MOD が描かない。
  ゲームが施設の名前で絵を引き、無ければ生成して保存する。自分で描いて「描いた覚え」を持つ作りは、ゲームの経路と二重に描く・移動の描画と重なるといった形で 331 と合わせて6回直すことになった（TECH.md §5.8）
- 自前の画面から戻す道は、塗り直しの1回を落とす。
  `maintain_buttons` は本文が流れている間は何もしない（GAME.md §2.6）が、戻す塗り直しはいつも `screen.say` の直後に走る。見送ると次の出番はゲームが選択肢を組み直したときで、役場に立ったままではそれが来ない。足せなかった回を覚えて手が空いてから1度だけやり直す（`retry_when_idle`）
- 「立っているか」と「自分の家か」は別の問い。
  契約が切れた瞬間は、中に居ても「自分の家」ではないので False になり、中に居るのに取り壊してしまった。取り壊しの判定は `standing_in`、滞在と保管庫は `inside_home`。切れた建物の中では出口だけを出す。街から引けない施設に立っているときの逃げ道（`stranded`）も別に持つ
- 立ち位置を動かすときは、その場所の選択肢も一緒に置く。
  ロードは選択肢を組み直さず、`game_variables["buttons"]` に焼かれているものを戻すだけ（GAME.md §2.3 と同じ話がロードにも当てはまる）。空のまま焼かれていると、開けても動けない。自分が建てた建物への道は入れない（MOD の無い環境で押せてしまう）
- 保管庫を開いたまま保存するときは売買中の旗を下ろす。
  品を移した直後の保存が窓を開いたままの形を焼き、ロードで窓は開かないので旗だけ残る
- 宿泊の長さは宿屋から覚える。
  素のゲームは3ヵ月から年齢で伸びる変動式だが、`315_vacation_custom` のような MOD が入っていればそちらが効く。覚えるものは2つに分ける。月数は宿屋の**部屋の選択肢**の spec（`args[0]`）から取り、日数は宿屋の宿泊で実際に進んだ差から取る。315 の週単位は渡す月数を1のままにして日数だけを縮めるので、月数×30 で数えると賃貸の1期が実際の4倍になる
- MOD が建てた建物の中の宿泊は数えない。
  `VacationStartManager.__init__` で数えると、よその MOD が自分で起こす滞在まで「宿屋の値」として拾う。滞在の最中の画面に並ぶ連泊のボタンも同じ spec なので、自分の家で拾うと見積もりの月数を「実測」として覚え直してそのまま固まる。まだ宿屋を見ていない世界ではローダの窓口に聞く（`durations.inn_stay`。TECH.md §3.3.2）。式はローダが持ち、この MOD は写しも、変える MOD の名前も持たない
- 契約の周期は結んだ時点の長さで固定する。
  年を取って宿泊が伸びても、いま借りている契約の期限は動かない。日数には「どの月数で測ったか」を添え、月数が変わったら前に測った日数は使わない
- 滞在の描写に泊まり先を1文添える。
  ゲームは頼み文にどこに泊まったかを渡さず、エリアの一覧だけを渡す（GAME.md §2.17）。家を足すと読み手は一覧の中の自宅を選ぶ。足すのは自分の家がある街の滞在の頼み文だけで、本文は1文字も削らない。家での訓練はゲームが固定の文を出すだけで AI に頼まないので、この1文は乗らない
- 控えの鍵は世界×主人公。
  世界名だけで控えると、主人公が死んで同じ世界で作り直したときに前の主人公の家が建つ（TECH.md §5.4）。ロードの間は `World.__init__` の引数のセーブから鍵を決めて持ち回る
- 自前のボタンは無害な既存クラスを spec に持たせ、押下は印で横取りする。
  `MovePhaseManager` を spec に書くと、そのボタンがセーブに焼かれた後、MOD を外した環境で押せてしまう（GAME.md §2.2）

## 別件で見えたこと（まだ直していない）
