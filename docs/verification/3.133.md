2026-11-20。
[§3.113](3.113.md) の続き。
全 MOD の関数を AST で正規化して同じ中身の関数を数え、同じゲーム関数を直にラップしている MOD の数を数えた（probe の 2xx と開発中の 9xx を除く）。

## 移さなかったもの

- `125_` の依頼の終わり（評価を処理の間だけ保つ。スレッドごとの印を使う）と、`306_` の `add_text`（ゲームの1行の後ろへ仲間の話を足す）は、前後の形が違うので自分でラップしたまま。この2つの対象は `check_mods.py` の窓口の対象に載せていない
- ローダ自身の保存の関所（`choices` / `modfacility` / `modnpc`）は、それぞれの決まりがあるので自分でラップしたまま
- `105_` と `127_` の `schema_compact` の同じ関数（10個）は、105 が取り込み済みで止めてある MOD なのでそのまま
- `taken_names`（320 と 336）は中身が違う

## 振る舞いの確かめ

- 依頼の生成は、前の重なり（適用順 301 → 307 → 325 → 336 → 338 → 328 → 318 で、後から適用した MOD ほど外側）を `load_order.json` で確かめ、窓口の当てる順（生成ごとの書き換え → 1回だけの書き換え → 指示と難易度）が同じ結果になることを確かめた。`318_` の上乗せは前も道・裏の仕事・脱出の明示の難易度に上書きされていて、`318_` の説明にもそう書いてあった
- 振る舞いを変えたのは1か所。`339_` の `area_notes` は土地の説明が文字列のとき空を返していたが、ほかの2本と同じく文字列をそのまま返す
- 前後の処理の例外は窓口が捕捉して記録する（前は MOD ごとに `safe=True` の有無と `try` の範囲が違った）

## レビューで直したこと（2026-11-20）

- 窓口のラッパーを、最初に登録した MOD の位置ではなく、全 MOD の適用の後にローダが一番外側に立てるようにした（`gates.defer_outermost`・`_install_outer_windows`）。
  最初の形では、`saving` は最初に登録する `134_` の位置に立ち、最初の注入では `336_` の適用の時に立つ `modnpc` の保存の関所より内側になっていた。
  `330_` が保管庫の管理人の手元を空にする処理と、`410_` / `329_` が保存の間だけ値を戻す処理が `modnpc` の写しの後に走り、写しに伏せる前の値が残る（`330_` は預けた品がロードの後に二重になりうる）。
  2回目以降の注入ではローダが `modnpc` の関所を適用の前に立て直すので内側になり、注入の何回目かで並びが変わっていた。
  `text_filters` と `quest_ends` も同じで、`306_` と probe から見える文や、前後の処理の順が変わっていた
- `330_` の保存の前の処理と、`318_` の依頼の終わりの前の処理は、2つの値を1つの式で返していたので、後ろが投げると先に読んだ値ごと失っていた（`330_` は下ろした売買中の旗が戻らない）。1つずつ読むように直した
- `321_` は依頼の土地を `after`（`orig` の後）で読んでいた。前と同じく `before` で読んで渡すように直した
- 「`325_` / `336_` の明示の難易度が `318_` の上乗せを消す」という指摘は当たらなかった。2026-11-19 の注入の `modloader.log` で、`318_` は `325_` / `336_` より後に適用されていて（`applied:` の行の順）、前から `318_` が外側で先に上乗せし、`325_` / `336_` が内側で上書きしていた

## 検査

- 窓口ごとに `test_quest_generation.py` / `test_quest_ends.py` / `test_text_filters.py` / `test_saving.py` を足した。外側に立てる動き（適用の間は包まない・ローダが立てる・`modnpc` の関所より外側）は `test_saving.py` の「外側に立てる」の節で、前の形では落ちることも確かめた。共有部品は `test_common_parts.py` の「npcs の項目を均す部品」の節
- 偽の ctx を作り直して `apply()` し直す検査のうち、ctx に世代の番号が無かった6本（133 / 134 / 142 / 304 / 334 / 344 の検査）に番号を持たせた。窓口のラッパーは世代ごとに1枚なので、番号が同じだと作り直した ctx にラッパーが渡らない（`test_road_opening.py` などと同じ手当て）
- 移した MOD の既存の検査は全部通った。依頼の終わりは6本、本文は4本の検査が窓口のラッパーを通って呼んでいる

## 実機（2026-11-20。テストワールド、ゲームの LLM は Claude）

- 起動: 注入4回とも、4つの窓口は全 MOD の適用の後に立った（最初の注入でも `modnpc` の関所の後）。フックの登録簿で `QuestEndManager.execute <- 237_probe_affinity, 240_probe_stamina, (loader)` と、窓口が probe より外側にある。WARN と ERROR は前日の注入と比べて増えず、Traceback は0件

- 依頼の終わり（道の依頼の踏破）: `325_` が道を開いてエテルナへ移り、`318_` が1回目のクリアを数え（+3、掲示板の依頼の難易度も上がった）、`344_` は別の土地へ移る依頼として帰りの日数を進めず、`142_` がスタミナを清算し、`321_` が編纂のリクエストを送り、`301_` が依頼の終わりを控えた
