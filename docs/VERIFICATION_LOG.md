### 2.5 戦闘BGM（原因確定と注入時掃除）

原因は `BattleEndInFreeAction`（会話・自由入力から入った戦闘）が
`instantale.py:7993` で曲の持ち主に **app ではなく自分自身**を渡すこと。
渡された曲は誰にも止められない「迷子」になり、プロセスが終わるまで鳴り続ける。
通常の `BattleEndManager` は `:7958` で正しく app を渡す。
症状が「会話から入った戦闘」に限られていた理由がこれで説明できる。
12戦の後、町に立っているだけで `mixer = 8/8 channel(s) busy` になっていた。

3つの起点（注入時の掃除・`refresh_choice_buttons` の保険・戦闘終了）すべてが実機で発火し、
終了後のチャンネルは 1/8 でその1本は app が握っている。

> 判定は耳ではなく `mixer = n/8` で行う。
> 一度「聞いて正常」で誤判定している（そのときチャンネルは 2/8 に増えていた）。

派生症状のうち「タイトルに戻っても街の BGM が鳴り続ける」も迷子で説明が付く
（`return_to_title` の `stop_music(app)` は `app.music` しか止めない）。

### 2.14 `OSError: [WinError 123]`: 名前が原因で画像が生成できない（2026-07-28、新種）

`crash_log.txt` の114件には無い新種。
キャラクタ名 `試験人形「テストダミー"` の ASCII `"` が Windows のパスに使えず、
`os.makedirs` が失敗して画像が生成されないまま無言で終わる（2回・同一人物）。
バックグラウンドスレッドなのでゲームは落ちない。

調査結果:

- `worlds/<世界>/characters/` のディレクトリ名はキャラクタ名そのもの
- 名前の唯一の入口は `scripts.characters:Character.__init__`
  （LLM 生成・プリセット・プレイヤー・ロードが全部ここを通る）
- 名前からパスを組む箇所は5つある。
  書き込みと削除で消毒がずれると別の不整合を生むので、**入口で正すほうが安全**
- 不正文字を含むディレクトリは作成できない ＝ 旧名のディレクトリは存在し得ないので、
  既存キャラクタを改名しても迷子は出ない
- 残る懸念: セーブ側 JSON には次の保存まで旧名が残る。
  名前で突き合わせる処理があると食い違う（実測では id で突き合わせているように見えるが未確証）

実装（`110_`）は入口ひとつで消毒する。
`< > : " / \ | ? *` → `＜ ＞ ： ” ／ ＼ ｜ ？ ＊`（消さずに全角へ写す）、
末尾の空白・ピリオドと制御文字を落とす。
予約デバイス名と、消毒すると空になる名前は触らず記録だけ残す。
旧名を必ずログへ残すのは上の懸念のため。

オフライン36件の最後の2件は実地で、落ちた名前そのものでこの OS 上の
`os.makedirs` を叩いている（生の名前では今でも `winerror == 123`）。

### 2.16 `108_` 売買画面の `IndexError`（2026-07-27、原因確定・救済は未発火）

> 2026-08-09、`superseded: main_024` で降ろした（§3.8.1）。この節は原因の記録として残す。

`place_existing_item` が `is_valid_placement()` を通さずに `occupy_slots` を呼ぶ。

`grid_x` / `grid_y` / `slot_size` はアイテム側の属性としては存在せず、`current_slots` の添字で持つ。

### 2.24 `111_` プロンプトの置換（2026-07-30 移植、2026-08-08 に全プロバイダで決着）

#### 移植で効いた差: プロキシは JSON にした後のボディを見ていた

| プロキシが見ていたもの | プロセス内で見えるもの | 対応 |
|---|---|---|
| `\n`（2文字）／`\uXXXX` | 本物の改行／生の文字 | 置換後は必ず復号。置換前は素の形と復号形の両方を登録 |
| .NET の `$1` / `${名}` / `$&` / `$$` | Python の後方参照 | 読み替える。存在しない番号は警告して文字列扱い |
| 1秒の正規表現タイムアウト | Python の `re` に無い | 1秒以上かかったルールを以後捨てる |

#### 実データでの照合（2026-07-30）

`output_data/` の 13,461 ファイル・51,897 メッセージ。
読み込み時の警告 0 件、26/27 グループが発火、置換が起きたメッセージ 16,636 件、
置換後も `105_` のスキーマ圧縮は素の状態と同数（8,859/8,859）。
残る1グループは `\n` 入りルールの素の形で、復号形の双子が当たっている
＝**復号が無ければ死んでいたルール**。

#### 仕掛け先が5版で変わった（クラウド対応）

落とし穴は毎回同じ。
送信の入口を名指しで包むと、プロバイダが変わった瞬間に素通りする
（ローカルとクラウドはどちらか片方しか import されない。GAME.md §2.12）。

v1 はローカル3点 → v2 `any_server` → v3 gemini → **v4 `llm_manager:send_request*`**
（使われる送信モジュールからの from-import 別名）→
v5 で「無かった別名を5秒ごとに見張り、生えたら包む」を追加。
v4 が今の形で、`alias_scan` が同じ関数を持つ全モジュールを張り替えるので、
モジュール名を知らないまま全プロバイダに届く。

実機で4経路とも発火（2026-08-08）。
Gemini / OpenAI / Claude はそれぞれのプロバイダ名で `[REPLACE]` が出て、
**名指ししていないモジュールにも自動で届いた**。
ローカルは `chat` のみ ＝ 二重抽選の歯止めが実機で機能。
同じ回で v5 の見張りも発火し（注入の25秒後に late-armed）、
**別名の後生えはローカルでも起こる**ことが確定した。
未実測は Alibaba と任意 OpenAI 互換だけで、設計上は同じ別名を通る。

運用で2度踏んでいる。
**プロバイダを切り替えたら再注入**、
**注入の版は armed 行の形でしか見分けられない**。

残る限界は、境界で見えるのが呼び出し側の渡した `message` だけで、
`send_request` の中で足される部分（Gemini の `_schema_instruction`）には当たらないこと。

手元のファイルには順序の罠が1つある。
`発言者名は不要です。【現在の状況】` の控えのリテラルは、
個人ルールより前に置かないと見出しの正規表現が当たらなくなる（`#memo:` に残した）。

### 2.25 `112_` 本文の行間（2026-07-31、画面から採寸）

起点は実機のスクリーンショット1枚。
文字 31px 前後・行間 70px・段落間 138px（＝行間のちょうど2倍）から、
**段落の間に空行が1行入っている**ことと、
本来の行間そのものが広い（既定 1.0 なら 42px 前後のはず）ことが読めた。

実機で確定した値は採寸の推定より1つ広く、
`hud.text_display` の `line_height` は 1.8（推定は 1.6）、`font_size` 27（推定 31）。
既定 0.8 倍で 1.44 になり、750文字の本文の高さが 3738 → 1776（約 2.1 倍縮んだ）。

一致は完全一致では取れなかった。
当たったのは `match=2`（ラベルの `text` が `display_text` で終わる）で、
**ゲームは塗るときに前へ何かを足している**。
完全一致だけを条件にしていたら、このラベルは1回も見つからなかった。

倍率は絶対値ではなくゲームの値に対する比で持ち、設計値はラベル自身に控える
（注入し直すたびに掛け直して縮み続けるのを防ぐ）。

### 2.26 `113_` 本文の表示域の拡張（2026-08-01）

広げる相手は本文のラベルではなく、それを載せている入れ物
（高さはゲームの `update_label_height()` が決めるので、ラベルを広げても次の1文字で戻る）。
入れ物は型ではなく `scroll_y` / `do_scroll_y` を持つ最初の親として探す。
元の寸法一式は**入れ物のウィジェット自身に控える**
（MOD 側の変数に持つと、注入し直したときに広げた後の寸法を設計値として控える）。

実機で6回外している。

| 回 | 外したこと | 直し方 |
|---|---|---|
| 1 | 枠線が付いてこない | 今その枠と同じ場所に同じ大きさで置かれているものを仲間とみなし、寸法ではなく倍率を配る |
| 2 | 上下（中心から）に伸びて入力欄にかぶる | 位置を一切入れない。Kivy の `y` は下端なので、`y` 据え置きで `height` だけ増やす |
| 2 | ボタンが画面の上端に貼り付く | `frames.MISSING` は文字列。存在確認は `is` で、値そのものを照合するなら既定を `None` にする |
| 3 | 会話に入るとボタンが左へ飛ぶ | 絵（`source`）で立ち絵を探さない。置き場所は位置で決める（枠の右隣に並ぶいちばん大きい入れ物） |
| 4 | 幅倍率 1.0 でも少し横に広がる | 触る軸だけ触る（`size_hint` を丸ごと外さない）。戻すときも触った軸だけ |
| 6 | **アイテムを持ち物へ移せない・装備できない** | HUD の子を1枚増やしたため。`get_current_screen_root()` が返す「最初の子」がこちらのボタンにすり替わっていた。ボタンは HUD 直下ではなくその中の `FloatLayout` へ（`host_of`） |

5回目は窓の大きさを変えたときの追従。
塗り直しは本文や選択肢が変わったときしか来ないので `Window.on_resize` を直に拾う。
順番が要点で、
`stale を立てる → 次のフレームで畳んで控えを捨てる → さらに次のフレームで控え直して当てる →
0.3秒後にもう一度` を外すと、広げた後の寸法を設計値として控えて二度と戻せなくなる。
安全弁として、広がっている枠からは絶対に控え直さない。

> 他人の画面に物を足すときは、**その画面の子の並びを変えない**。
> 並びを手がかりにしている処理はこちらからは見えず、確かめようもない。

実機で成立。

### 2.31 残骸の掃除が他の MOD のボタンを消していた（2026-08-03、コードで確定）

### 2.33 HUD への置き場所を「先頭の子」で選んでいた（2026-08-03、コードで確定）

`113_` / `116_` はどちらも HUD 直下ではなく、その中の `FloatLayout` へボタンを足す
（HUD の子を増やすとアイテムの移動・装備が壊れる。§2.26）。
その `FloatLayout` を `children` の**先頭**から探していた。
Kivy の `children` は新しい順なので、HUD 直下に何かが載っている瞬間はそちらを掴む。
除外していたのは自分のボタンだけで、2本目（`116_`）が入った時点で相互に掴み合える状態だった。

規則を `ui.overlay_host` へ移し（同じ発見を2箇所に書かない。TECH.md §6.1）、2点を変えた。

1. `children` の**最後尾**から探す（ゲームの `FloatLayout` はいちばん古い子）
2. 除外を `_instantale_` で始まる属性を持つウィジェット全部へ広げる（どの MOD が足したものも）

1 だけでは、ゲームが後に作る子が居るビルドで再発する。
2 だけでは、ゲームの一時的な窓（印を持たない）を掴む穴が残る。
先頭走査に戻すと両方の検査が落ちることを確認済み。

同じ点検で `107_` の `hasattr` を `frames.attr(...) is not frames.MISSING` へ置き換えた
（TECH.md §6.3）。
同梱 MOD の `hasattr` はこれで 0 件。

### 2.34 本文の表示速度（2026-08-03、決着・修正まで確認）

報告は「表示速度の設定を変えても速さが変わらない」。

設定は届いていた（`211_` の実測）。
`text_speed=0.04` で 48〜50ms（20文字/秒）、`0.08` で 80〜83ms（12文字/秒）。
ゲーム内で変えた瞬間に届くので再起動も再注入も要らない。
差はフレーム境界への丸めで説明が付き（60fps＝16.7ms 刻み）、
**最速でも「1フレーム1文字」＝60文字/秒が下限**（GAME.md §2.3）。

#### ただしワールドによって 1.6 倍遅い: こちらは MOD が原因だった

`kivy.uix.label:Label.texture_update` を包んで数えたら決着した。
1文字ごとにラベルを約3回、1回 15ms かけて作り直していた
（`112_` と `117_` の `settle()`）。
どちらも「ゲームが `texture_size` を見るから先に作り直させる」つもりだったが、
Kivy の作り直しのほうが先に走る（テキストを変えた時点で予約される）ので不要。

| | 前 | 後 |
|---|---|---|
| 作り直し | 2.86 回/文字 | 0.97 回/文字（Kivy のぶんだけ） |
| 1文字あたりの代金 | 42.6ms（間隔の 67%） | 8.1ms（21%） |
| 打ち出し | 15.7 文字/秒 | 25.7 文字/秒 |
| フレームレートの下限 | 17.3fps | 54.0fps |

ワールドで差が出ていたのは代金がテクスチャの大きさに比例するため。
直した後はテクスチャがむしろ大きいのに設定値どおり回っているので、
大きさではなく回数の問題だったことが裏側からも確かめられた。

> テクスチャの作り直しは `update_display_text` の中ではなく次のフレームで走る。
> フックの中で測っている限り出てこない（TECH.md §6.2）。

体感が変わらなく見える理由として残るのは総量のほう。
750文字なら 0.04 でも 1メッセージに 37 秒かかる。
そこは速度設定ではなく `118_` の路線（1文字ずつ送るのをやめる）の話。

### 2.35 NPC の名前が重複する（2026-08-05、オフライン検証済・実機未確認）

小さい LLM ほど同じ語を繰り返し引く。
完全一致より表記ゆれのほうが多い。

| 形 | 例 | 見分け方 |
|---|---|---|
| 表記ゆれ | バルガス / ヴァルガス | 拗音の綴り・長音・濁点を落とした鍵で比べる |
| 修飾語付き | 「隻眼の」バルガス | 括弧とその中身、先頭の `〜の` を落とす |
| 姓名の片方だけ一致 | バルガス・ドレイク | 姓名に割って、片方が姓名だけの名前に含まれるかを見る |

付け直しは**名簿から選ぶ**。
版1（元の名前の末尾の音を機械的に差し替える）は綴り間違いのような名前になり、
版2（LLM に書かせる）は検算を厚くしても「使えるが良くはない名前」を落とせなかった。
名簿方式なら名前の質が入力で決まり、乱数も推論も要らない。
名簿は `male` / `female` / `epithets` の3つだけ読む（他の鍵は在っても無視）。
男女はセーブの `category`（実データ8種）で決め、
`woman` は `man` を含むので**女性を先に見ないと全員が男になる**。

オフライン111件で確かめたことのうち、肝は2つ。
**別人を巻き込まないこと**（`アレン・スミス` と `アレン・ジョーンズ`、`ジル` と `ジン`、
`ナナシ` と `ナシ` を分ける）と、
**改名が素データ（`npcs`）まで届くこと**（届かないと次の保存で古い名前が戻る）。
乱数は MOD 専用の `random.Random` から引く。
名簿が読めない・使い切ったときは名前を発明せず元のまま通し、`WARN` で名指しする。

`ALWAYS_RENAME`（名づけを丸ごと引き取る側。既定 切）で要ったのは2つ。
**同じ NPC を二度裁かない番人**（`generate_character` で付けた名前を
`Character.__init__` がもう一度付け直す。重複を見る既定側では「衝突なし」が歯止めになっていた）と、
控えに素データの `npcs` も全部登録すること
（`world.characters` だけだと後から組み立てられた古参が新顔に見える。GAME.md §2.23）。

分かっていないこと: 名前で NPC を突き合わせている処理があるか（`110_` から引き継いだ未確証）。
改名した NPC の立ち絵は名前のフォルダに入るので、
既存 NPC を改名すると古い画像が取り残される（`FIX_EXISTING` を既定で切ってある理由）。

### 2.36 新規キャラが最初からレベル60（2026-08-09、本体が main_025 で修正して決着）

セーブを復号した実測で、7月までの新規開始は全て `lvl 1`、
2026-08-08 の新規は `lvl 60`（`experience_point=0`）。
後から生えた壊れ方。

|---|---|---|
| `max_physical_integrity` | 10 | レベル1 |
| `max_hp` | 832 | レベル60（耐久 16 × 52） |
| `experience_level` | 60 | - |

原因は `instantale.py:876` が `Character(..., experience_level=60, ...)` を渡していたこと。
同じ関数の883〜885行は `get_max_physical_integrity(1)` を呼んでいる。
`levelup` / `gain_exp` は作成中に一度も呼ばれておらず、
属性の違う2体がどちらもちょうど 60 ＝ 計算結果ではなく定数。

### 2.37 ミニイベントの判定に能力値が入っていない（2026-08-08、実データで確定）

### 2.48 `127_` ローカルLLMの速度と VRAM（2026-08-12〜14、実測）

環境は RTX 4070 Ti SUPER（16376 MiB）。

#### 崖がある。超えるとエラーではなく激遅になる

gemma-4-26B-A4B Q4_K_XXL（重み 13650.92 MiB）で `--ctx-size` を振った実測
（同一プロンプト 4402 トークン、生成 128）:

| 起動引数 | 窓 | KV | VRAM | 処理 t/s | 生成 t/s |
|---|---|---|---|---|---|
| `--ctx-size 16384`（素のゲーム） | 16384 | 1220 | 15977 | 4226 | 94 |
| `--ctx-size 16384 --parallel 1` | 16384 | 620 | 15378 | 5712 | 133 |
| `--ctx-size 32768 --parallel 1` | 32768 | 940 | 15744 | 5911 | 130 |
| `--ctx-size 32768`（統合） | 32768 | 1540 | 15937 | 4088 | 93 |
| `--ctx-size 65536 --parallel 2` | 32768 | 1880 | 15938 | 294 | 44 |
| `--ctx-size 65536 --parallel 4` | 16384 | 2480 | 15938 | 496 | 29 |

崖は 15744（正常）と 15938（崩壊）の間。
超えるとドライバがシステムメモリへ退避して PCIe 越しになり、
処理が約17倍・生成が約3倍遅くなる。
Windows は失敗を返さないので、症状は「エラー」ではなく「異様に遅い」になる。

> **飽和後の `nvidia-smi` は当てにならない**（溢れた分は表示に出ない）。
> 15977 の素ゲームより 15938 の 65536×4 のほうが3倍遅い。
> 判定は起動ログの `KV buffer size` と `compute buffer size` の合計で行う。

KV の実寸は 20 KiB/token（全文脈層）＋ 300 MiB/スロット（SWA 層・`n_ctx` に依存しない固定）。
窓を 24576 から 32768 へ広げても速度は落ちないので、
窓を選ぶときは VRAM の余白だけ見ればよい。

予算の内訳（総量 16376 − デスクトップ 350 − ゲーム描画 260 − 重み 13651 −
計算バッファ 533 − CUDA コンテキスト 275 ＝ **KV に使えるのは 1307**）。

#### `--parallel 1` が速い理由は SWA だった

VRAM に余裕のあるモデルで切り分けた。
**全文脈層の KV は統合と専用で同じ**（12B は 256 MiB、9B は 512 MiB で不変）。
差が出るのは SWA 層の確保量で、統合では余分に取られる（4スロットで3倍）。
gemma4 は層の大半が SWA なので効く。

| 要因 | 効果 | 条件 |
|---|---|---|
| SWA キャッシュの縮小 | 生成 +11% / 処理 +16% | SWA を持つモデル。VRAM の余裕は不問 |
| 崖から遠ざかる | 残り（26B では合計 +40%） | VRAM がぎりぎりの環境だけ |
| SWA 無し・余裕あり | 0%（害も無い） | Qwen3.5-9B で確認 |

単価はモデルごとに測る（SWA の無い 9B は 32 KiB/token と 26B より高い）。

#### 窓を超えた要求は HTTP 400

`exceed_context_size_error`。
黙って遅くなるのではなく、ゲームは同じプロンプトを送り直すので必ず同じ所で止まる。

#### `--parallel` を明示すると SWA のチェックポイント復元が要る

スロットを絞るとプロンプトが同じスロットを奪い合い、
`n_swa` の制約でチェックポイントが無効化されて**4件に1件がフル再計算**になる。
`--checkpoint-every-n-tokens 256` を併せて渡すと素のゲームと同等に戻る（VRAM は増えない）。

| 起動引数 | 再計算（定常・4件） | プロンプト処理 |
|---|---|---|
| 素のゲーム | 3332 | 1405 ms |
| `--parallel 1` | 4653 | 1683 ms |
| `--parallel 1 --checkpoint-every-n-tokens 256` | 3332 | 1408 ms |

`--cache-reuse 256` では回避できない（**効果ゼロ**。再計算・処理・生成のすべてで差が無い。
そもそもゲーム既定の欄には含まれず、手で書き足したもの）。
`--parallel 2` でも回避できない（スロット数の問題ではない）。

#### スロットを増やす方向は成立しない

`--ctx-size` は合計値なので `--parallel N` を明示すると窓が N 分割される。
2本以上は窓が縮んだうえに素のゲームより VRAM を食い、
窓を保つには `--ctx-size` をスロット数倍する必要があって KV はさらに増える。
「並列を保ちつつ節約」は原理的に成立しない。

#### llama.cpp 本体の版は関係ない

同梱 b8954 と b10369（1400ビルド差）を A/B して ±0〜-2%。
遅いときに疑う先はエンジンではなく文脈長と KV。

### 2.65 店の在庫はその土地の依頼の難易度だった（2026-08-26、実セーブ6世界、`318_` / `221_`）

「その土地の依頼の難易度を上げれば、店の品揃えも上がるか」を、
ゲームを起動せずに `world_data.json` を復号して確かめた

対象は `%LOCALAPPDATA%\Darmabeko\Instantale\worlds\` の6世界。
持ち物を持っている主の居る施設は23軒、品物は190個。

**190個のうち 186個が、その土地の依頼の難易度そのものだった。**

| 世界 / 土地 | 依頼の難易度 | 施設（tier） | 在庫の `value` |
| --- | --- | --- | --- |
| ペルディション 2 | 27 / 30 / 31（3件とも完了済み） | general_store（standard） | 5,5,27,27,30,30,31,31,31 |
| ペルディション 2 | 〃 | medical_facility（basic） | 27,27,27,27,27,30,30,31 |
| ペルディション 3 | 48 / 54 / 55（3件とも完了済み） | specialty_shop（advanced） | 48,48,48,54,54,54,54,54,55,55 |

外れた4個は2軒に集まっていて、どれもその土地には無い難易度だった
（上表の 5,5 を含む）。
プレイヤーが売った品が主の持ち物へ積まれる経路（GAME.md §2.13.1）で
入ったものと読める。

**2. 完了済みの依頼も母数に入る。**
ペルディションのエリア 2 / 3 / 8 は依頼3件とも
`config['status'] == 'completed'` だが、在庫はその難易度で並んでいた。
`get_quest_difficulties(area, world, include_completed=True)` の既定そのまま。

**3. 施設の `tier` は在庫の段を1つに絞っていない。**
`basic` の店にもその土地の最高難度の品が並ぶ。

（`entrance` / `ward` / `dungeon_location` など主の居ない施設は `None`）。
**誰が `get_area_quest_difficulty_for_tier` の `tier` に何を渡しているかは未実測**
（→ §2.67 で判明。整数で、品揃えを作るのは `generate_item_in_shopping`。
決め方はまだ出ていない）。

**4. 依頼は土地ごとに3件ずつ、難易度が固まって置かれている。**
世界を作った時点で 0..76 を9つの土地へ割り振る形で、
最初の町が 2〜5、最果てが 67〜75。
`206_` の記録では、新しく作られる依頼の難易度もこの帯の中に落ちる
（帯 `[5,4,3]` の町から 3 と 5、帯 `[9,3,7,8,7]` の町から 9）。

これで `318_area_difficulty_growth` は在庫にもクラフトにも触らずに済む。

実引数と戻り値の型）で、`221_probe_item_level` がそこだけを録る。

#### 1. 新しい依頼は「いまの帯」ではなく素の帯で生まれる

```
18:54:53  board: 土地 0 依頼 0 難易度 5 -> 15 / 依頼 1 4 -> 14 / 依頼 2 3 -> 13
18:56:21  random_quest_generator(settlement='始まりの泥濘', difficulty=4)   ← 206_
19:08:09  clear: 土地 0 依頼 0 難易度 15 -> 25 / 依頼 1 14 -> 24 / 依頼 2 13 -> 23
19:08:49  random_quest_generator(settlement='始まりの泥濘', difficulty=3)   ← 206_
```

土地の依頼を 13〜15、次いで 23〜25 まで上げた状態で作らせて、
**生まれた依頼は 4 と 3**。ゲームは今の難易度を見ていない。

初版は「ゲームは土地の依頼の帯から新しい依頼の難易度を選ぶ」を前提にして、
生成には手を出さず、初見の素の値を「いまの難易度 - いま乗せている量」で控えていた。
前提が逆だったので、**作りたての依頼だけ素の難易度のまま差し出され**、
控えた素の値も 4 - 20 = 0 まで沈んでいた（実データで2件）。

直した形は、生成のたびに上げ直す（`generate_random_quest` を包む）ことと、
初見の素の値をそのまま控えること。
頼み文へ渡す難易度も同じだけ上げるので、文章と数が食い違わない。

> 帯の中で生まれた過去の観測（`[5,4,3]` の町から 3 と 5）は、
> **たまたま素の帯と一致していただけ**だった。
> 素の帯を動かした状態で採っていれば、その時点で分かっていた。

#### 2. `world_dict['quests']` はセーブの中身ではなく世界の雛形

同じ瞬間の2つのファイル:

| | 依頼の数 | 依頼 0 の難易度 | 依頼 0 の状態 |
| --- | --- | --- | --- |
| `worlds\テストワールド\world_data.json` | 12 | **25**（MOD が書いた値） | incomplete |
| `saves\テストワールド\savedata.json` | 22 | 5（素の値） | completed |

- 掲示板で作られた依頼（id 13 / 19 / 20 / 21）は**雛形の側に無い**。
  `206_` の記録でも `app.world_dict['quests'] = 12 entries`
- 状態も食い違う（雛形 incomplete / セーブ completed）＝
  雛形は遊びに追随していない
- MOD が雛形へ書いた難易度は `world_data.json` に焼かれた。
  **同じ世界で新しく始めた別のキャラクタにまで乗る**

GAME.md §2.9 の「`world_dict['quests']` がセーブに出るほう」「書くときは必ず両方」は
これで否定された（§2.9.1 に訂正を書いた）。
`318_` は生きた一覧（`app.world.quests`）にだけ書く形へ直し、
雛形に焼けた3件は控えの `base` から戻した。

#### 3. ゲーム自身の読み手は生きた一覧を読んでいる

これが「セーブに残らなくてよい」と決められた根拠。
同じ 18:54:51 の記録:

```
get_quest_difficulties(area, world) -> list(len=5) [5, 4, 3, 4, 5]
```

土地0の依頼は、雛形（`world_data.json`）には 3件（id 0 / 1 / 2）しか無い。
5件返ったということは、**雛形に無い id 13 / 19 まで数に入っている** ＝
この関数は生きた一覧を読んでいる。

`get_quest_difficulties` は店の品揃え・値付け・敵の強さの源（§2.65 / GAME.md §2.13.1.1）。
つまり `318_` が書いている側を、ゲーム自身の読み手がそのまま読む。
セーブに残らなくても遊びは成り立つ。

そのうえで `318_` は **`World.__init__` でロードの1回に世界じゅうを寄せ直す**形にした。
掲示板を開いた土地だけ直していると、
掲示板を通らない読み手（店がその筆頭）が素の値を見る。

#### 6. クラフトの式（一度も測れていなかった1箇所）

`ItemCraftManager.calculate_modification(item_type, item_price)` は
**float の倍率**を返す。成果物の値段は素材の合計値段にそれを掛けた値:

```
素材 value 2 + 8（合計の値段 30.75）
  get_equipment_level_from_price(30.75) -> 2
  calculate_modification("weapon", 30.75) -> 24.375
  30.75 × 24.375 = 749.53125
  get_equipment_level_from_price(749.53125) -> 27
  成果物: 使い古された鉄の短剣  value 27  攻撃力 116
```

副産物（`material`）は**その 1/5**。2例とも合う:

```
  calculate_modification("material", 30.75) -> 9.512195…
  30.75 × 9.512195… = 292.5   →  292.5 / 5 = 58.5
  get_other_item_level_from_price(58.5) -> 14      成果物: 研磨屑 value 14

  （もう1例）合計 1.25 × 24.375 = 30.46875 -> value 8
             副産物 30.46875 / 5 = 6.09375 -> value 2
```

**「素材が高いほど成果物が良い」が実測で成立**した。
`318_` が在庫を上げれば素材が上がり、クラフトも自動で追随する。
倍率は種別と値段で変わる（`weapon@30.75` は 24.375、`material@30.75` は 9.5122）が、
**式の形は2点では出ない**。
