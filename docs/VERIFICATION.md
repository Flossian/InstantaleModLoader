### 3.17 ミニイベントの判定（`215_`）: 負の差の正体だけが残っている

### 3.18 自由入力の能力値補正（`313_`）: 経路も加点も実機で成立

### 3.21 会話ログの窓が空（`122_`）: Label 1枚に入れすぎていた（2026-08-10）

### 3.29 長い本文の載せ替え（`117_`）: `prefix` を控える理由と、その穴

`117_` は `hud.text_display` に「前置き + 省略通知 + 末尾 `DISPLAY_CHARS` 文字」を
入れ直す。ここで言う前置き（`state["prefix"]`）が何のためにあるのかが、
コードにも docs にも書かれていなかったので残す。

**なぜ2行で済まないか**

module docstring だけを読むと `label.text = 通知 + value[-N:]` の2行に見えるが、
塗る相手は `hud.display_text`（ゲームが持っている本文そのもの）ではなく
`hud.text_display.text`（画面に出ている文字列）で、この2つは一致しない
（GAME.md §2.3 が「完全一致しない」と断言している）。
ラベル側に本文より前の部分が乗っていることがあり、そこを落とすと画面から消える。
そこで「ラベルの末尾が本文と一致するなら、その手前が前置き」として切り出している。

**なぜ一度切り出したら持ち越すのか**

この MOD が載せ替えた後のラベルは `前置き + 通知 + 末尾N文字` になる。
`value`（本文）はそこに丸ごとは現れないので、**次からは `endswith` が
二度と成立しない**。つまり前置きを切り出せる機会は載せ替えの前の1回しかなく、
持ち越さないと以後ずっと前置きが落ちる。
`state["prefix"]` が `value` の空を経由するまで再代入されないのは、そのため。

**残る穴（未検証）**

`prefix` が空へ戻る唯一の道は `display_text` が空になること。
だから「本文が空を経由せずに、ラベルだけ**別の前置きを持つ画面へ丸ごと差し替わる**」
経路があると、古い前置きが新しい画面に貼り付いたまま残る。
そういう差し替えが実際にあるかは未確認。

確かめ方: `out/` にこの MOD のログは無いので、
デバッグモードで `211_probe_text_speed` を入れ、
`text_display.text` の先頭が本文の先頭と食い違ったまま増えていないかを見る。
出たら「前置きは HUD ごとに1回だけ切り出して、
画面が組み直されたら捨てる」形（`113_` の `DESIGN_ATTR` と同じ持ち方）に変える。

### 3.30 NPC 名の誤検出（`120_`）: 別人を改名していた（2026-08-20 修正）

`out/npc_name.log` に、**別人どうしを重複と判定して改名していた行が3件**あった。

```
'バルガス・グラトル' -> 'トリスタン'  (clashed with id='7' '“黒蜥蜴”アルカス')
'“黒蜥蜴”アルカス'  -> 'カゲロウ'    (clashed with id='__player__' 'ヴァルガス・ヴォルフレイン')
'“黒蜥蜴”アルカス'  -> '影を纏うシキ' (clashed with id='__player__' 'ヴァルガス・グレイヴ')
```

2件目と3件目は**プレイヤー名との衝突**で NPC が改名されている。

**原因: 濁点落としと編集距離が二重に効いていた**

鍵を作る段階で濁点を落としていた（`バルガス` → `ハルカス`）ところへ、
`SIMILARITY="normal"` の許容（4文字以上で1文字違いまで）が乗る。
結果として「濁点で1文字寄せて、さらに1文字違ってもよい」＝
実質2文字違いが同一人物になり、`ハルカス` と `アルカス` が重なっていた。

**直し方: 判定を2段に分けた**

濁点は鍵に残し、比べるときだけ落とす（`_near`）。

1. 濁点を残したまま近いか（`SIMILARITY` の許容まで）
2. 濁点を落として**完全に一致**するか（`FOLD_VOICING`）

`バルド` / `バルト` は 2 で拾い、`バルガス` / `アルカス` はどちらでも拾わない。

**あわせて `_strip_epithet` の助詞判定を絞った**

`rfind("の")` で最後の「の」以降だけ残していたので、
`たけのうち` の鍵が `ウチ` に化けていた。
`の` の手前が仮名だけなら切らないことにした
（二つ名は `隻眼の` `重鉄の` `元傭兵の` のように漢字を含む）。
仮名だけの二つ名は取りこぼすが、名前を壊すよりはよい。

**検算**

`tools/tests/test_npc_name_dedup.py` に、ログに出た12件を回帰として入れた
（捕まえたい9件・別人の3件）。既存の期待16件と合わせて全件通る。
切り分けの比較は次のとおりで、**`rfind("の")` の除去だけでは誤検出は1件も減らない**
（原因が濁点落としの側にあるため）。

| 案 | 取りこぼし | 誤検出 |
| --- | --- | --- |
| 修正前 | 0 | 3 |
| `rfind("の")` 除去のみ | 2 | 3 |
| `FOLD_VOICING=False` | 2 | 0 |

### 3.33 注入がゲームの `__main__` を汚していた（2026-08-21 修正）

本体のクラッシュ記録が、記録を書く前に自分で落ちていた。

```
File "instantale.py", line 288, in report_crash
File "instantale.py", line 200, in make_crash_log
AttributeError: module 'datetime' has no attribute 'now'
```

`make_crash_log` は文字列を組んで返すだけで、`crash_log.txt` への書き込みも
送信もその後段にある。落ちている間はどちらも走らない。

**素の不具合ではなかった**

| 走らせ方 | 本体の `crash_log.txt` |
| --- | --- |
| MOD 無し（`MOD を外す`）で同じクラッシュ | 書けた（10件 → 11件、11157 → 11818 バイト） |
| 注入した状態で同じクラッシュ | 書けない |

`001_crash_recorder` が拾った14件（MAIN 6 / THREAD 8）は、
どれも本体の `crash_log.txt` に無い。
逆に本体が書けている10件は、どれも 001 が拾っていない＝注入前の回だった。
8/8 以降の14件を「素の不具合」として数えていたが、全部こちらが壊していた。

**原因: 流し込むコードがモジュール階層で import していた**

`PyRun_SimpleString` は**ゲームの `__main__` の辞書で**流し込んだ文字列を実行する。
`tools/injector.py` の `BOOTSTRAP_TEMPLATE` は1行目がこうだった。

```python
import sys, os, datetime, traceback
```

本体は `from datetime import datetime`（クラス束縛）で持っているので、
この行がモジュールを被せていた。`datetime.now()` はクラスにしか無い。

```
素の __main__.datetime = <class 'datetime.datetime'>
流し込んだ後           = <module 'datetime' ...>
```

`sys` / `os` / `traceback` も同じように上書きしていた。
表に出たのが `datetime` だけだったのは、本体がそこだけクラスで束縛していたため。

**直し方: 全体を関数で包んだ**

`import` も一時変数も関数の中に閉じ込め、モジュール階層に残るのは包みひとつだけ。
それも最後に `del` する。

**検算**

`tools/tests/test_injector_bootstrap.py` が `make_bootstrap()` の出力を
`ast` で解いて、モジュール階層に `import` も代入も無いことを見る（boot / unload の両方）。
踏んだ形（平らに書いた場合に束縛が消えること）も回帰として入れてある。

**切り分けに使った道具**

`219_probe_crash_log`。`make_crash_log` を包んで、落ちた呼び出しごとに
`title`・例外の連鎖・そのときの `__main__.datetime`・呼び出し元の経路を控え、
`datetime` を差し替えてもう一度組ませた結果まで記録する（結果は捨てて元の例外を投げ直す）。
実機1回で `RETRY with the shim -> OK, 1635 chars` が出て、
「差し替えれば本体と同じ書式の記録が出来る」ところまでは即決した。
`mods in path = yes` が出ていたのでこちら側を疑い、上の突き合わせに繋がった。

**直った後の実機（2026-08-21 10:46:38、同じ店で1回）**


## 4. 運用上の取り決め

### プロキシとの併用（2026-07-25）

InstantaleLLMProxy は `schema_compact` を ON のまま動かし続ける。
mod が先に圧縮するとマーカーが消えるので、正常に効いていればプロキシ側は何もしない。
裏を返すと:

> `llm_proxy.log` に `[COMPACT]` / `[DEDUP]` / `[EVENTLOG]` が出たら、
> それは mod が取りこぼした経路。

二重に適用しても結果が変わらないので無害で、漏れの検出器として使えるという判断。

多重起動抑止だけは所有者調停が競合する。
main_023 で `LlamaCppSidecar` の所有者調停が入り、
ゲーム自身の修正とプロキシを合わせた三者が同じことを見る状態になっている
（GAME.md §1.8 / §2.12）。
併用するならプロキシ側を `singleton_enabled=0` にすること。

### CI だけで落ちるもの（2026-08-09、`test_npc_profile_memory`）

CI が赤くなったが手元では再現しない
（作業ツリーでも綺麗なクローンでも、Python 3.13 / 3.14 でも、25回連続でも落ちない）。

原因は特定できていない。
**当時の CI は落ちた本の出力を捨てていた**ので、どの `check` が落ちたのか残っていなかった。

打った手は2つ。
`ci.yml` を**落ちた本のぶんだけ折り畳みで吐く**形に変えた。
`WAIT_SECONDS`（背景スレッドの完了待ちの上限）を 2.0 → 15.0 にした。
手元では1件 1ms 未満で終わる待ちに 2 秒を割り当てていたが、
ランナーはディスクもスレッドの立ち上がりも遅い。
時間切れは `ctx.errors` に積まれて「例外が記録された」として落ちるので、症状の見え方とも合う。
同じ形の待ちが他に無いことは `grep "monotonic() +\|deadline"` で確認済み。

> 上限を伸ばすことに実害は無い。
> どちらの待ちも「揃ったら即座に抜ける」作りなので、通る回の所要時間は変わらない。

時間切れのときは待った秒数と件数を残すようにした
（`background extraction timed out: 15.0s 待って finished 0/1` の形）。
「本当に不発」なのか「間に合わなかっただけ」なのかが1行で分かる。
