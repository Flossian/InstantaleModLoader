# `127_llm_response_speed`: ローカル LLM の応答を速くする

ローカル（llama.cpp）で遊んでいるときの応答を速くする。
設定は既定のままでよい。

ゲームは `llama-server` を「4スロットで1つの KV を共有する」形で起こす。
だが実際には並列でほとんど走らない（実測でリクエストの94%が逐次）。
この MOD は専用の1スロットで起こし直す。
窓の広さは変えないまま KV の確保量が減り、そのぶん速くなる。

効き方はモデルと環境による。

| モデル | VRAM に余裕あり | VRAM がぎりぎり |
| --- | --- | --- |
| gemma 系（SWA あり） | 生成 +3〜11% | さらに大きい（実測で最大 +40%） |
| SWA を持たないモデル | 変化なし（害も無い） | KV は減るので余裕が生まれる |

生成が長いほど、また会話が長く続くほど利得が大きくなる。

VRAM がぎりぎりの環境ほど大きく効く。
溢れた分は Windows が共有メモリへ逃がすため、
エラーにならず「異様に遅い」状態になる。
KV が減ればそもそも溢れなくなる。

クラウド（APIキー）で遊んでいる場合は何もしない。

llama-server は版によって受け付ける起動引数が違う。
ゲームの更新で llama-server が入れ替わっても、起こすサーバが受け付けるものだけを渡す。

## MTP を使う（さらに速くする）

MTP（複数トークン予測）を使えるモデルでは、生成がかなり速くなる。
使えるかどうかはこの MOD がモデルを見て決めるので、何もしなくてよい。
設定の「MTP を自動で使う」で切ることもできる。

モデル自身に MTP の層があるもの（Qwen3.8-27B など）は、そのまま使う。
Qwen3.8-27B では生成が約 1.7 倍になり、VRAM を約 1.1GB 余分に使った（ゲームの外で、ゲームと同じ温度で測った値）。
16GB の VRAM では、待っている間の残りが約 600MB だった。

モデル自身に無いものは、別の下書き役のファイルを添えると使える。
Gemma 4 26B A4B 系（Gemma 4 本体と、それを調整したモデル）では、戦闘の文の生成が約 1.5 倍になった（測り方は同じ）。

使い方は、下書き役のファイルをモデルのフォルダの中の `mtp` フォルダに置くだけ。

```
runtime\models\llama_cpp\<モデル>.gguf
runtime\models\llama_cpp\mtp\mtp-gemma-4-26B-A4B-it.gguf
```

起動するモデルに合う下書き役があれば自動で使い、合わなければ使わない。
下書き役を直に `llama_cpp` に置くと、ゲームのモデルの一覧に並んでしまうので `mtp` に置くこと。
Gemma 4 26B A4B の下書き役は unsloth の `gemma-4-26B-A4B-it-qat-GGUF` にある。
VRAM を約 300MB 余分に使う。
モデル自身に MTP の層があるときは、`mtp` フォルダの下書き役は使わない（Qwen3.8 で別に配られている下書き役を添えると、かえって遅くなった）。

足りずに起動できなかったときは、MTP を外して起動し直す。
使ったかどうかは `out\llm_speed.log` の `MTP` の行で分かる。

MTP を使うときは、プロンプトやそれまでに書いた分の繰り返しを写す下書き（ngram-mod）も重ねる。
戦闘の文の生成が、MTP だけよりさらに約 5% 速くなる。
VRAM は増えない。

> 効くのは次にサーバが起きるときから。
> 既に走っている `llama-server` の引数は変えられない。
> 注入してからゲームを起動するか、ゲーム側で LLM を開き直すこと。
> 効いたかどうかは `out\llm_speed.log` に `[REWRITE]` が出ることで分かる。

## 窓を広げたいとき（上級者向け）

育った `life_log` を持つ NPC と会話すると、
『リクエストを再実行』の表示が出たまま進まなくなる。
プロンプトが窓（既定 16384 トークン、日本語でおよそ26,000字）を超えてサーバに撥ねられている状態で、
再実行しても同じ文章を送り直すだけなので必ず同じ所で止まる。
ゲームの設定画面からは変えられない（ゲームが `--ctx-size` だけを取り除く）。

「1リクエストが使えるトークン」を上げれば窓は広がる。
それでも既定の 0 のままにしておくことを勧める。
窓に比例して VRAM を余分に使い、
足りなくなると上に書いた「異様に遅い」状態へ落ちるため。
必要な量はモデルの構造で変わるので、勘で上げないこと。

上げる場合は `tools\llm_ctx_probe.bat` を実行する。
ゲームを終了した状態で走らせると、
候補を順に試して**そのマシンで安全に使える最大値**を出す。
数分かかる。

| 設定 | 意味 |
| --- | --- |
| 同時に持つスロット数 | 既定 1（この MOD の本体）。変える理由はほぼ無い。0 にすると素のゲームと同じ共有4本に戻す。2 以上は窓を保つために VRAM を余分に使い、既定より重くなる |
| 1リクエストが使えるトークン | 既定 0（ゲームの値のまま触らない）。上げるときは `llm_ctx_probe.bat` の出す値を使う |
| MTP を自動で使う | 既定 ON。モデル自身に MTP の層が無く、合う下書き役も `mtp` フォルダに無ければ何もしない |
| MTP で一度に下書きするトークン | 既定 4（下書き役の配布元の推奨） |
| MTP に ngram-mod を重ねる | 既定 ON。MTP を使わないときは何もしない |
| 書き換えず記録だけする | 既定 OFF。ON にすると実際の起動引数を記録するだけで何も変えない |
