## 1. 遊び方（`docs\MODS.md` 相当）

### `921_fix_prompt_errors`: ゲームのプロンプトの誤りを直し、街の必須施設の欠けを補う

ゲームが LLM に送るプロンプトには、ゲームが受け取る形（型）と食い違う書き方がいくつもある。
型に無い値や欄を名指ししたり、件数や上限の数が合わなかったり、どの街でも同じ決め打ちの文が入っていたりする。
読み違えた LLM は、型に許された別の値へ流れる。
いちばん大きいのは街の生成で、Claude（Haiku 5.5）で世界を作ると、宿屋もギルドも店も無い街が多く出た（9街中7街）。
この MOD は、食い違う文を型に合わせて直して送り、街の生成では返ってきた街を確かめて、欠けた分だけを頼み直して足す。

ローカル LLM でもクラウドでも同じように効く。
効くのはこの MOD を入れた後に作られるもの（新しく入る街、これからの依頼・品・会話の要約など）で、もう作られたものは変わらない。

#### 何が変わるか

| 直すもの | 遊んでいて変わること |
|---|---|
| 街の生成 | 新しく入る街に、宿屋・ギルド・役所・診療所・雑貨屋が必ずある。住人や冒険者が0人の街も出ない。欠けていたときだけ、作り直しのぶん街に入るのが10〜15秒ほど遅れる |
| 依頼中の出来事の結末 | 何も起こらない結末に、型に無い値の代わりの効果（ダメージや品）が付きにくくなる |
| 依頼中の移動 | 移動しようとしたとき、行き先へ移ったうえで戦闘や出来事になる（111 の同梱ルールと同じ直し。111 が無くても効く） |
| 液状の素材 | 液状の生き物の素材が、生き物の素材として分類される |
| 依頼と品の強さの目安 | 「難易度は N/70」「最高が70」を、ゲームの本当の上限 76 に合わせる。上限を上げる MOD で 76 を超えた依頼は、超えた分は敵だけが強いと添える（ゲームは報酬や品の値段を 76 で止める）。敵のレベルや品の値段の数字そのものは変わらない |
| 街の依頼の段階 | どの街でも「ゲーム序盤」と書かれていたのを、難易度に合わせて序盤・中盤・終盤にする。中盤・終盤の街の依頼が、その段階らしい依頼として書かれる |
| 法廷の求刑 | 検察官の台詞に求刑の中身（懲役何年など）が入りやすくなる（「休憩内容」の誤字を直す） |
| 敵の特性・NPC のスキル | 書けない欄を求める文を、型に合わせた指示にする |
| 衛兵 | 衛兵の説明に、行動方針と外見が入る。体の大きさの選び方が伝わる |
| 会話の要約 | NPC の記録に「今日の現在ログ」の見出しが混ざらなくなる |
| 自由生成施設の中身 | 施設でもらう品の外見が英語で書かれ、品に合った絵が選ばれる。買い取りの施設で、選ぶたびに時間も使わず金がもらえる作りになりにくい。料金を取った後の返金で作り直しを繰り返し、ただの場所に格下げされることが減る |
| 作った品 | 作った品の出来（weak・normal・strong）が、素材の質と組み合わせに沿って選ばれる |
| スキルを作る・習う | 名前・属性・説明は頼んだものがそのまま使われると伝え、効果と使用回数をそれに合わせて作らせる。能力を上げ下げする技は、状態異常として書く |
| エンディング | 結末の起こりやすさと難易度、人生の幸福度が、決められた値の中から選ばれる |
| 会話の進行 | 不適切な入力として扱う回の書き方を型に合わせる。雇うときの値段の交渉の欄の使いどころを伝える |

したことは `out\prompt_errors.log` に出る。頼みの直しは頼みと直したものの組み合わせごとに初回と100回ごとに1行（`fixed …`）、街の生成は街ごとに1行（`checked: complete` か `repaired [...]`）。
頼み直しは `output_data` に `create_settlement_detail_repair` の名前で残る。

#### 困ったとき

| 症状 | やること |
|---|---|
| 新しく入った街に宿屋やギルドが無い | `out\prompt_errors.log` の、その街を作った時刻の行を見る。`repair failed` なら頼み直しが失敗した。`WARN the structure block was not found` や `WARN no facility type` なら、ゲームの更新で頼みや型の形が変わり、この MOD が手を出せていない |
| 足された施設が街の入口に並んでいる | 頼み直しで LLM が区画の名前を書き間違えると、入口から直接行ける所に置かれる。ログの `top (no ward …)` で分かる |
| ゲームを更新した後、`fixed` の行が出なくなった | ゲームがプロンプトの文を変えた。誤りが直ったのか、言い回しが変わって当たらなくなったのかを、`output_data` の新しい記録で確かめる |

## 2. 設計の根拠（`docs\GAME.md` §2.9 へ戻す）

#### 街の詳細の生成は、必須の施設がそろったかを確かめない

`create_settlement_detail` の返却型 `Area` の `settlement_structure` は、区画（`Ward`。`type` は `ward` の1択）・施設（`Facility`）・ただの場所（`NonFunctionalLocation`。`type` は `location` の1択）の並び。
区画の `locations` も施設とただの場所の並び。
施設の `type` は inn・guild・administrative_office・medical_facility・general_store・blacksmith・specialty_shop・training_facility・underworld_office・slave_market・colosseum から選ぶ。
自由生成施設を有効にした世界（`include_free_facility=True`）では `free` と、施設の `concept` の欄が加わる。

頼み文の【構造の生成要素】は次のように書く。

- 「ロケーションには[ward, facility, location]の3つの大枠がある」と書く。`facility` は型の `type` に書けない値
- 「必須facility: [inn, guild, administrative_office, medical_facility, general_store]の6種は、必ずそれぞれ一つずつが存在する」と書く。並んでいるのは5種

型には必須の施設の決まりも件数の上限も無く、ゲームは返事を確かめずに街を組む。
区画の中にただの場所しか書かない返事でも、そのまま施設の無い街になる。
ギルドが無いときは、主のいない「〇〇 - ギルド」と出口を入口に足すだけ。

- Claude（Haiku 5.5・思考なし・構造化出力）では、`type` を `facility` と書けない分を `location` に流し、区画の中を場所だけで埋める回が多い。10-29 の一括生成では9街中7街で5種とも欠けた。構造化出力を外すと、区画の中に施設を書いたうえで `type` を `facility` と書く
- 住人も冒険者も0人の返事も出る（10-29 の9街中2街）
- ローカル LLM（Fenrir-X-26B-A4B・Qwen3.5-9B）では欠けなかった。grammar が5種を強制しているのではなく、モデルが頼みを読み違えなかった。大きな都市で施設を作りすぎる回がある（施設43件のうち同じ名前が9件）
- Haiku でも思考ありや Sonnet 5.5 では、1回ずつの試しで5種がそろった

#### ゲームの頼みは型と食い違う書き方をしている（10-31 の洗い直し）

どれも 10-14 の更新の後のゲームの頼みと型で確かめた（型の記録がそれより前の頼みは exe の中の定義と突き合わせた）。

- `quest_referee_event_resolve`: 「失敗した結果何も起こらないものは'miss', 成功した結果何も起こらないのは'escaped'とすること」と書くが、効果の種類は damage / heal / get_item / text_status_effect / start_battle / no_effect で、どちらも無い。同じ頼みの効果の一覧は `no_effect` を挙げる
- `quest_referee_with_free_action`: 「battleよりもmove_and_battle, field_eventよりもmove_and_event」と書くが、`turn_resolution` に無い。型には `move_to` がある
- 品を作る頼み（random_quest_generator・settlement_quest_generator・shop_item_generator_ordinary・master_ai_item_generate）: 「液状の生物の一部はliquid_material」と書くが、素材の種類（`Material.sub_type`）に無い
- 難易度と価値: 頼みは「難易度は N/70」「この世界における最低が1で最高が70」と書くが、ゲームの上限の定数（`QUEST_DIFFICULTY_VALUE_MAX`）は 76 で、終盤の街の難易度は 76 まで出る（§2.9 の表）。`318_` で上限を上げると 76 を超えた難易度も使われるが、強くなるのは敵だけで、報酬・才能点・品の値段と強さは 76 の値で止まる（VERIFICATION.md §3.112）。そのとき店の品の頼みは「価値として「83」を指定」のように 76 を超える値を頼む
- `settlement_quest_generator`: 「想定段階: ゲーム序盤」は exe の中の決め打ちの文字列で、どの街でも同じ。同じ頼みの「難易度は70/70」「現在の段階: 4/5」と食い違う
- `get_sentence_sought`: 「具体的な休憩内容を含む」は「求刑」の誤字。求刑の数字は型の `sentencing_request` に入る
- 敵を作る頼み（random_quest_generator・settlement_quest_generator・colosseum_enemy_generator）: `trait` を「無いこともある」と書くが、型では必須の object
- スキルを作る頼み（npc_detail_generater・master_ai_npc_generater・skill_train_manager・skill_learn_manager）: 「usefulness: スキルの総合的な有用性を1～30で評価」と書くが、スキルの型に欄は無い。有用性はゲームが計算する（品のデータに `skill_usefulness: 21.6` の形で出る。exe に `get_item_skill_usefulness`・`new_skill_usefulness` があり、セーブの技は781件中780件が usefulness を持たない）
- `create_skill`: 型は `effects`・`skill_type`・`max_uses`・`usefulness` だけで、頼みが求める `name`・`element`・`description` は無い（名前・属性・説明は頼んだ文のまま保存される）。効果の枝は instant_damage / instant_heal / text_status で、頼みが挙げるバフ/デバフは無い（同じ exe の skill_learn_manager の型にはある）
- `epilogue_pre_evaluator`: 頼みは `weight` と書くが、型は `weights`（critical_success / partial_success / partial_failure / failure）。`difficulty` の値（very_easy / easy / normal / hard / very_hard / impossible）を書かない
- `epilogue_generator`: 幸福度の値（fulfilled / content / ordinary / unfulfilled / miserable）を書かない
- `free_facility_generate`: 「item_appearance = one short ENGLISH sentence」と、同じ頼みの最後の「プレイヤーに見える全てのテキスト…は日本語で書くこと」が並び、10-29 の8件では品を渡す4手順の外見がすべて日本語だった。DSL にプレイヤーから品を受け取る手順が無く、買い取りの施設は費用も elapse も無い労働の支払いとして書かれる（1・3・4・5.json）。料金を取った後に返金を書いて検査で戻され、頼み直し3回とも同じ program を返した回がある
- `item_craft_generator`: 頼みは `'byproduct'` と書くが、型は `byproducts`。型の必須の `performance`（weak / normal / strong）・`description` を説明しない。「現在の場所、…を考慮し」と書くが、場所を渡していない
- `conversation_facilitator_after_retrieval`: 「Trueを指定し、残りの出力は全て無とする」と書くが、`type` は必須の enum。型の `new_offer`（10-14 の更新で加わった）を【出力要素】が書かない
- `guard_npc_generator`: 【出力要素】が型に無い `personality`・`look_description` を求め、型の `race`・`size`（tiny / small / medium / large / huge）を説明しない。`category` を「老若男女」と書くが、型は monster / human_female / human_male
- `life_detail_setter`: 「npcs: …それ以外では空のリストでも構わない」と書くが、型は `npc`（1人・必須）
- `conversation_resolver`: 「「今日の現在ログ」に続きとして書き足す形で」が、見出しまで書き写すとも読める
- `create_settlement_detail`: 上の節
- ローカルの経路の前置き「必ず日本語で、以下のjson形式で出力すること」は、英語で書く欄の指定と食い違う。英語の欄 1,695件で日本語は0件

## 4. 未確認項目と確認手順（`docs\VERIFICATION.md` §3 へ戻す）

### ゲームのプロンプトの誤りと街の必須施設の欠け: 街の生成はゲーム抜きで成立・ほかの直しは記録の文で確かめた・実機は未

2026-10-31 に作った。
きっかけは、Claude（Haiku 5.5・思考なし・effort high）で一括生成した世界で、9街中7街に宿屋・ギルド・役所・診療所・雑貨屋が1つも無かったこと。
区画の中はどれも桟橋・記録庫・見張り台のようなただの場所（`location`）だけだった。

#### 測ったこと（ゲーム抜き。頼みは `output_data` の `create_settlement_detail` の記録をそのまま使う）

ローカル LLM（Fenrir-X-26B-A4B、ゲームと同じ起動の引数・型・サンプリング）と Haiku 5.5（`136_` の送信口経由）に、崩れた回の頼み（記録 59・55・52）と前の世界の頼み（43）を送り直した。
型は記録 41（自由生成施設なしの世界）から取った。

| 送り方 | Haiku 5.5 で5種がそろった回 | ローカルで5種がそろった回 |
|---|---|---|
| ゲームと同じ | 16回中4回 | 23回中23回 |
| 型の説明をプロンプトの本文にも書く（ローカルと同じ見せ方） | 12回中3回 | （ローカルの形） |
| 構造化出力なし・型の説明は本文だけ | 12回中2回（ほかの9回は `type` を `facility` と書いた） | - |
| 種類の書き方の1文をプロンプトに足す | 12回中9回 | - |

- 構造化出力を外すと、Haiku は区画の中に施設を5〜10件書くが、`type` を `facility` にする。プロンプトの「ロケーションには[ward, facility, location]の3つの大枠がある」を欄の値と読んでいる
- 構造化出力では `facility` が書けないので、施設のつもりの物を `location` に流し、その後も場所を書き続けると見ている
- `144_` が【共通世界観】に足した「施設の種類（type）は guild など決められた値をそのまま使う」では足りなかった（VERIFICATION.md §3.95 で Claude の `facility` の検証エラーに対して足した文）
- ローカルの崩れは逆向きで、大きな都市（59）で8回中1回は施設43件・同じ名前9件まで作りすぎた。型に件数の上限が無い
- 試しの型は自由生成施設なしの世界のものだった。10-29 の世界は自由生成施設ありで、施設に `free` と `concept` が加わる（返事で確かめた）。下の版1 の試しは `free` と `concept` 入りの型で行った
- 住人も冒険者も0人の返事: Haiku のゲームと同じ形で17回中3回・本文にも型の形で12回中3回・1文を足した形で12回中0回。ローカルは46回とも0回（冒険者は全回3人）

#### 版1 で直したこと

- 送信の境目（`llm_manager_world_generate:send_request`）で、頼みの名前が `create_settlement_detail` のときだけ型とプロンプトを差し替える。型は送信の中で `structure` から作られるので、ローカル・クラウドのどちらにもこの1か所で効く
- 型: `settlement_structure` の直後に `required_facilities` を足す。5種が1つずつで、各々は置く区画の名前（`ward`）と施設の欄（`type` を除く。`free` の世界なら `concept` も）。説明（description）を付ける
- プロンプト: 「ロケーション種別」の行を、`type` に `facility` と書かず種類の値を書く形に、「必須facility」の行（「6種」と書いて5種を並べている）を `required_facilities` に書く決まりにする
- 返事: 5つを名前の合う区画へ、無ければ最上位（入口直結）へ移す。同じ種類が構造の中に既にあれば足さない。来た形（モデル・辞書・JSON）のまま元の型に戻して返す
- 足した形が例外で失敗したら、元の頼みで1回だけ送り直す
- 検査: `tools\tests\test_wip_settlement_facilities.py`（今は `test_wip_prompt_errors.py`。型の形・選べない種類・プロンプトの置き換えと足し・戻しの3つの形・素通し・送り直し）

#### 版1 の試し（ゲーム抜き。ゲームと同じ形の pydantic の型に `widen` / `rewrite_prompt` / `restore` を通す）

| 送り方 | 回数 | 5種がそろった | 出力トークン | 時間 |
|---|---|---|---|---|
| ローカル・ゲームと同じ（`free` 入りの型） | 2（記録 55） | 2 | 3,218〜3,275 | 25〜26秒 |
| ローカル・版1 | 12（記録 59・55・52・43 を3回ずつ） | 12 | 4,223〜5,302 | 32〜41秒 |

- ローカルは12回とも、5施設を `settlement_structure` の中にも書いたうえで `required_facilities` にも書いた（「settlement_structure には書かない」を守らない）。版1 は構造の中の5つを残し、足した欄の5つを捨てた。足した欄のぶん、1街あたり出力が約1,300トークン、時間が約10秒延びる
- 型の差し替えで JSON が崩れた回・型に合わない回は無かった

小さいモデル（Qwen3.5-9B-IQ4_XS、ゲームの設定と同じサンプリング）でも試した（記録 59 を2回、55・52・43 を1回ずつ）。
このモデルのチャットテンプレートは system を先頭に1つしか受け付けず、ゲームのローカルの形（型の system と指示の system の2つ）では10回とも HTTP 500 で断られた。
試しでは2つをつないで1つの system にした。

#### 版2（10-31）: 崩れの元を層ごとに直す

1. 頼みの文が型と食い違っている（ゲームの作りの誤り）
2. 型が頼みの決まり（必須の5種・件数）を持っていない

#### 9種の洗い直し（10-31）

型つきの記録が無かった9種を、記録の返事の欄（構造化出力が強いた形）と exe の定数（`<頼み>.<locals>.<クラス>` の名前・欄名・enum の並び）で突き合わせた。記録は9種とも全件（1〜12件）読んだ。exe の `ge` / `le` / `max_length` の数は読めず、数の範囲と件数の上限を型が縛っているかは9種とも分からない。
