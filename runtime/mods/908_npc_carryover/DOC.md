## 1. 何をする機能か（要件）

遊び終えた世界のNPCをエクスポートしておき、別の世界にインポートして登場させる。
再会したときに同じ人物として話せるよう、見た目・人物像・好感度に加えて、
`311_` / `403_` が `state\` に持つ記憶も引き継げる。

決定事項（2026-08-28 の要件確認）:

| 論点 | 決定 |
| --- | --- |
| 実現形態 | ゲーム内MOD（ModLoader の新規 MOD） |
| 取り込み元 | 他世界のセーブ（`saves\<世界名>\savedata.json`）を直接読む。対象のセーブとNPCは GUI で指定 |
| エクスポートの持ち方 | 指定したNPCを世界ごとに zip 化して `state\` に保持。一覧のチェックで複数選び、一括でエクスポートできる |
| インポートの指定 | どの zip をどの世界に置くかも GUI で予約する。置き先は世界名で指定（`saves\` に在る世界から選ぶ） |
| GUI の開き方 | ローダの設定画面（`tools/gui.py`）から開く。MOD が独自 GUI を持てる基盤をローダに足す（§4） |
| 配置の発動 | 対象世界のロード時に自動 |
| 配置先 | ダンジョン以外のランダムな街のギルド、無ければ宿。旅の者がこの土地に流れて来た、という位置づけで冒険者として登録する |
| 同名NPCが既に居たら | 予約の時点で GUI が置き先のセーブと突き合わせて表示する（ゲームを起動する前に分かれば手戻りが無い）。予約後に生まれた衝突だけゲーム内で見送り、メッセージで通知する（黙って出てこないとバグに見えるため） |
| 記憶（`311_` / `403_`）の引き継ぎ | 設定で選べる（§7・§8） |

## 2. 全体の構成

部品は4つ。GUI はゲームの外（別プロセス）、取り込みはゲームの中で行う。

```
(1) ローダ基盤          mod.json の "tool" 宣言 → gui.py がボタンを出し、
                        MOD 同梱の tool.py をサブプロセスで起動する（§4）
(2) エクスポート (tool.py) 他世界のセーブを復号して NPC を一覧 → チェックした
                        NPCを1体1zipで state\npc_carryover\<元の世界名>\ へ（§5）
(3) インポート予約 (同上)  zip と置き先の世界名を選んで pending.json に書く（§5）
(4) 取り込み (apply)     予約された世界のロード時に、NPC をセーブへ入れて配置し、
                        記憶を state\ の新世界側へ写す（§6〜§7）
```

ゲーム内で完結させず GUI を外に出すのは、元の世界のセーブを読むのが
プレイ中のゲームと無関係な作業だから。ゲーム内 UI（`320_` の方式）だと
「どの世界の誰を」の指定が会話ボタンの語彙に収まらない。

## 3. エクスポートの形式（SaveEditor 互換の zip）

SaveEditor の NPC 移植（`Tools/NpcPortability.cs`、format = `instantale_npc`）と
同じ形式にする。エディタでエクスポートした zip をこの MOD の置き場に
置いても読めるし、逆も読める。

```
<名前>.zip
├─ npc.json          {"format": "instantale_npc", "version": 1,
│                     "source_world": 元の世界名, "original_id": 元のid,
│                     "original_name": 名前, "npc": {33項目のNPCレコード}}
├─ images/*.png      saves\<元の世界>\characters\<名前>\ の画像
└─ carryover.json    この MOD だけが読む追加分（§7）。SaveEditor は
                     npc.json と images/ しか読まないので互換を壊さない
```

- 置き場所は `state\npc_carryover\<元の世界名>\<名前>.zip`（`state\` の規約は TECH.md）
- エクスポート時に `display_position_in_battle` を null にする（エディタと同じ）。
  `relationship` / `life_log` は保持したまま出し、引き継ぐかは取り込み時に決める
- 名前はそのままファイルパスになる（GAME.md §2.15）ので、
  エディタの `SafeFileName` と同じ字を落としてから zip 名・画像フォルダ名に使う

## 4. ローダ基盤: MOD が設定画面から自分の道具を開く

`gui.py` は「MOD のコードを一切 import しない」（`gui.py` 冒頭の原則）。
これを守ったまま MOD に GUI を持たせるため、宣言＋サブプロセスにする。

- `mod.json` に `"tool"` を足す:
  `{"entry": "tool.py", "label": {"ja": "...", "en": "..."}, "note": {...}}`
- `gui.py` は `tool` を宣言した MOD の行に「道具を開く」の操作を出し、
  `[sys.executable, <mod_dir>\tool.py]` をサブプロセスで起動する
- 渡すものは環境変数（引数だと tool 側の書式を縛る）:

| 変数 | 中身 |
| --- | --- |
| `IML_ROOT` | 配布フォルダの根（`runtime\` と `state\` の親） |
| `IML_STATE_DIR` | `ml.state_dir(RUNTIME_DIR)` の値 |
| `IML_GAME_DIR` | `settings\gui.json` が覚えているゲームの場所。未設定なら空 |
| `IML_MOD_SETTINGS` | `settings\mod_settings.json` のパス（tool が既定値の解決に使う） |

- tool 側は tkinter で自前の窓を持つ普通のスクリプト。ローダ本体は
  `sys.path` に在る（`runtime\` 直下）ので `instantale_modloader.state` の
  世界名の均し方をそのまま使える

## 5. エクスポートとインポート予約の GUI（tool.py）

##### 世界とNPCの一覧

- 世界一覧は `<ゲーム>\saves\` のフォルダ名
- `savedata.json` の復号は XOR（`cipher[i] = plain[i] ^ b"Instantale_Save_Key_2026"[i % 24]`。
  GAME.md §2.16）。読むだけで書き戻さないので、エディタが課している
  ラウンドトリップ検査は要らない
- NPC 一覧に出す列は 名前 / 職（job） / 分類（category） / レベル
  （experience_level） / 親密度（`relationship` の player の affinity と
  affinity_text）。`characters\<名前>\face_image.png` があれば顔も出す
- 1世界のNPCは100体を超えることがあるので、列ごとのフィルターを必須にする。
  名前は部分一致、職・分類・親密度は選択、レベルは下限。
  フィルター中は「何人中何人を表示しているか」と、いま効いている条件を一覧の下に出す
- 一覧の先頭はチェック列。チェックした全員を一括でエクスポートする
  （1人ずつのボタンは持たない。見出しのチェックで表示中の全員に入り切りできる）

##### 予約（pending.json）

`state\npc_carryover\pending.json` に1件1予約で持つ:

```json
{"zip": "<元の世界名>/<名前>.zip", "target_world": "置き先の世界名",
 "status": "pending",
 "inherit": {"memory": true, "relationship": true, "life_log": true}}
```

- `status` は `pending` → `placed`（+ 新id・配置先・日時） / `skipped`（+ 理由）。
  取り込み済みの判定はこのファイルだけで行い、セーブには独自キーを足さない
- `inherit` の既定値は MOD 設定（§8）から写す。予約ごとに変えられる
- 同じ zip を複数の世界へ予約するのは可（インポートは読むだけで zip を消さない）
- エクスポート済みのNPCの一覧もNPC一覧と同じフィルター付きの表にする
  （zip は溜まる一方なので数十〜百を超えうる）。列は 名前 / 元の世界 /
  職 / レベル / 親密度 で、元の世界は木の階層ではなく列＝フィルター条件として持つ

##### 予約時の名前検査

重複の検査はここが主役。置き先は世界名で指定するので、予約の時点で
置き先の `savedata.json` を読み、`npcs` の name と突き合わせられる。
ゲームを起動する前に分かれば手戻りが無い。

- 重複していたら予約の画面にその場で出し、そのままでは予約を確定させない
  （先住側をエディタで改名する・置き先を変える、のどちらかを選んでから）
- GUI を開き直したときも `pending` の全件を検査し直す。
  予約してから置き先の世界を遊ぶと、その間にゲームや `320_` が
  新しいNPCを作って衝突が生まれることがあるため。
  引っかかった予約には一覧で印を出す
- 判定はエディタの `NameExists` と同じ完全一致

## 6. ゲーム内の取り込み（apply）

発動は「予約された世界のロードが済んだとき」に1回。
世界名は `instantale_modloader.state.world_key(app)` で見分ける。
ロード完了のフック地点は未確認（§9）。

手順（1予約ぶん）:

| # | やること | 根拠・注意 |
| --- | --- | --- |
| 1 | 名前衝突の最終弁。`npcs` の name と完全一致が居たら見送り、`status: skipped` にして通知（§6.1） | 検査の主役は予約時の GUI（§5）。ここに残すのは、予約からロードまでの間に生まれた衝突（プレイ中のNPC生成）を黙って通さないため。インポートするNPCは固有の人物なので勝手に改名しない |
| 2 | id の採番。**辞書の最大+1 ではなく `index.npc` で採番し、`index` を進める** | 最大+1 だとゲームが次に払い出す id と衝突して上書きされる（SaveEditor `WorldTab.cs` の教訓と、アイテムで実際に踏んだクラッシュ）。ローダの `npcs.free_id`（最大+1）をそのまま使えるかは §9 |
| 3 | インベントリの item id を `index.item` で採番し直し、`equipments` の参照も付け替える | エディタの `ReassignItemIds` と同じ。inventory の鍵だけ変えて equipments を忘れると装備が宙に浮く |
| 4 | 33項目を `NEW_NPC_TEMPLATE` の並びに合わせ直し、`current_area` / `current_location` / `initial_location` / `location` を配置先で書き直す | 並び順はセーブエディタの表示を崩さないため（`npcs.py` 冒頭）。`location` はエディタと同じく全て null に戻す |
| 5 | `npcs.make_npc` 相当で素データ書き込み・`Character` 組み立て・施設配置 | `make_npc` は id を自前採番するので、id を外から渡せる形に手を入れるか、手順を並べ直す |
| 6 | 配置先の決定: ダンジョン以外のエリアから1つ引き、`guild` があればそこ、無ければ `inn`。どちらも無ければ別のエリアを引き直す | 施設種別の語彙は `ui.py`（guild / inn は実セーブで確認済みの `facility_type`） |
| 7 | そのエリアの `adventurer_npcs` へ id を登録（実行時とセーブ側の両方） | `320_` の `enroll` と同じ。旅の冒険者として一覧に出る |
| 8 | zip の画像を `saves\<世界名>\characters\<名前>\` へ展開し、`image_src` の各値を貼り替える | エディタの `PlaceImages` / `RewriteImageSrc` と同じ。パスの形式は §9 |
| 9 | 記憶を `state\` の新世界側へ写す（§7） | |
| 10 | `status: placed` を書き、ゲーム内メッセージで到着を知らせる | 例:「〈名前〉が旅の末にこの地へ流れて来たらしい。」 |

繰り返しロードしても増えない（`status` で1回きり）。
配置したNPCはゲーム自身の `npcs` 項目としてセーブに残り、
MOD を外しても消えない。`320_` と同じ性質で、消したいときはセーブエディタで消せる。

### 6.1 見送りの通知

ここに来るのは、予約時の検査（§5）を通った後にゲーム側で衝突が生まれた場合だけ。
稀だが、見送ったときに黙っていると「予約したのに出てこない」がバグに見える。

- その世界のロード直後に1回、ゲーム内メッセージで理由を出す
  （例:「〈名前〉はこの世界に同名の人物が居るため現れなかった。」）
- 予約は `skipped` として残す。手で対処（エディタで先住側を改名するなど）して
  `pending` に戻せば次のロードで再試行される
- 2回目以降のロードでは通知せず、`out\npc_carryover.log` にだけ書く

## 7. 記憶の引き継ぎ

`311_`（人物像・あなたについての記録・判明した事実）と `403_`（社会関係）は
セーブではなく `state\npc_profiles\<世界名>.json` / `state\npc_social_memory\<世界名>.json` に
NPC id を鍵として入っている。世界も id も変わるので、両方を付け替えて写す。

- エクスポート時に、元の世界の該当 id の項を `carryover.json` へ同梱する。
  zip を自己完結にするためで、後から元の世界の `state\` が消えても効く
- 取り込み時（`inherit.memory` が真のとき）、置き先の世界のファイルへ新 id で書く。
  書き方は `311_` と同じ「隣に作ってから差し替え」
- `403_` の社会関係は相手の id が並ぶ形なので、そのまま写しても相手が居ない。
  同じ世界へインポートしたNPC同士の間だけ id を付け替えて残し、それ以外の相手の項は落とす
- `relationship` / `life_log`（セーブ内の項目）は `inherit` の指定に従い、
  引き継がない場合はエディタの既定値と同じ形（player のみ・好感度0・初対面）に戻す

## 8. 設定（mod.json の settings 案）

| 設定 | 既定 | 意味 |
| --- | --- | --- |
| 記憶を引き継ぐ | ON | `311_` / `403_` の記録を新世界へ写す。予約ごとの `inherit.memory` の既定値 |
| 好感度・関係を引き継ぐ | ON | セーブ内 `relationship`。切ると初対面から |
| 経歴を引き継ぐ | ON | セーブ内 `life_log`。切ると空でインポートする |

素のゲームに無い機能なので「素の値」という基準は無いが、
番人値は使わず ON/OFF で持つ（settings の規約どおり）。
