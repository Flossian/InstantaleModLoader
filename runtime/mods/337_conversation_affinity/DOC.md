## 1. 遊び方（`docs\MODS.md` 相当）

### `912_conversation_affinity`: 会話による好感度の変動

素のゲームでは、NPC の好感度は依頼のクリアで同行者に +20 されるだけで、会話ではほとんど動かない。
この MOD を入れると、会話を閉じるたびに相手の気持ちがどう動いたかを LLM が判定し、好感度が上下する。
判定はゲーム自身の会話の要約の頼みに相乗りするので、LLM を呼ぶ回数は増えない。
画面には何も出ない。
好感度の段が変わると、次に話したときの相手の態度（ゲームの感情の文）に表れる。

### 決まり

- 判定は会話を閉じたときに1回だけ。要約と同じ返答の中で -3〜+3 を答えさせる（0 は変わらない。用件だけのやり取りや普通の雑談はほぼ 0）
- 材料は要約の頼みにもともと載っている相手の人物像・プレイヤーへの今の感情・会話の全文。おだてたり媚びたりしただけでは上げないよう、書き足す決まりで断っている
- 判定の答えはゲームへ渡す前に抜く。要約の文・会話の記憶・セーブには混ざらない
- 判定を足した形で要約が失敗したら、元の頼みのまま送り直す（要約を落とさない。そのときは判定なし）
- 上がるときは1段 +2（最大 +6）、下がるときは1段 -4（最大 -12）
- 会話だけで上がるのは好感度 60（「仲間だと感じている」）まで。それより上は依頼に同行して上げる。60 より上の相手でも下がる方は効く
- 他の MOD がその相手の上限を狭めていれば、そちらで止まる（ローダの窓口 `talk_affinity`。TECH.md §3.3.8）。911 のライバルは 30 まで
- 同じ相手から上がるのは1日1回まで。日数は宿泊・街の移動でしか進まないので、同じ街で話し続けても稼げない
- 下がる方は会話のたびに毎回効き、1日の回数も幅も制限しない。失礼な会話を繰り返せばそのぶん嫌われる
- 話しかけてすぐ閉じただけの会話は判定を足さない。
  プレイヤーが何か言ったか、開け閉め（話しかける・会話を終了する・取引を終了する）以外の行動があれば判定する。
  贈り物のような行動だけの会話も、店での売り買い（「〜を購入した」）も判定に入る（用件だけなら判定はほぼ 0）
- 動いても本文には何も出さない。動きは `out\conversation_affinity.log` にだけ残る
- MOD の NPC（330 の管理人・331 の主人）は対象にしない
- 会話を正規の経路で閉じなかったとき（会話の途中でタイトルへ戻ったなど）は、ゲームの要約と同じく判定も走らない（GAME.md §2.25）

感情の文（「興味がある」など）は、ゲームが会話の始まりと終わり、依頼のクリアのときに好感度から作り直す（GAME.md §2.25.1）。
この MOD が書くのは好感度の数だけ。

## 2. 設計の根拠

### 2.1 好感度はクリアで +20、会話ではほぼ動かない

`237_probe_affinity` の1回目（2026-10-01）で、依頼のクリア1回で同行者16人の全員が一律 +20 になった（同行していない人は動かない）。
`213_probe_npc_memory` のログ（2026-08-22〜10-01）では、会話を閉じた192回のうち好感度が動いたのは1回だった。
会話の LLM の返答と要約に好感度の欄は無い（GAME.md §2.25.1）。
会話1回の幅はクリアより十分小さくし（最大 +6）、会話だけで届くのは「仲間だと感じている」までにした。

### 2.2 判定を会話の要約の頼みに相乗りさせる

版1の最初の形は、要約の前に判定の LLM を別に1回呼んでいた。
要約は別スレッドで回るので画面は固まらないが、ゲームは要約が終わるまで会話を閉じきらない（GAME.md §2.5。最大120秒ほど）。
そのため、判定の時間がそのまま会話を閉じる待ちに足されていた。
ローカルの LLM は 127 で1本ずつ順に受けているので、裏へ回しても次の行動の頼みが判定の後ろに並ぶ。
そこで、要約の頼みそのものに判定を足すことにした。

要約の頼み（`output_data\…\conversation_resolver\N.json` の実物）:

- 返却型は `Result{summary: str}` の1項目
- 本文は system 2件（スキーマ文と GM の指示）、続いて会話の全文
- GM の指示には相手の人物像（経歴・性格・職業）、「プレイヤーに対する感情」、ライフログが載っている。判定の材料はすべてそろっている

要約は `llm_manager:send_request(manager_name, message, structure, ...)` を、要約の関数と同じスレッドで通る（`213_` の記録。ローカルでも同じ別名）。
スキーマ文は `send_request` の中で型から作られる（入口では4件、`output_data` では5件）。
だから型を差し替えれば、足した項目もスキーマ文と grammar の両方に出る。

- 要約の関数を包み、判定を足す会話ならスレッドに印を付ける
- `send_request` で `manager_name` が `conversation_resolver` のときだけ、型を「元の型＋`affinity_change: int`＋`affinity_reason: str`」の子の型（`create_model(__base__=元の型)`）に差し替える。summary が先に来るので、要約を書いてから判定する順になる
- 判定の決まりは先頭の system に書き足す。新しい system を末尾に足さないのは、system を先頭にしか置けないチャットテンプレートがあるため
- 返ってきたら判定の2項目を抜き、元の型（または辞書・JSON 文字列。来た形のまま）に戻してゲームへ返す
- 好感度を書くのは要約の関数が返った直後。ゲームは同じ `resolve_conversation` の中で感情の文を作り直す（GAME.md §2.25.1）。作り直しはこの後だった（§4 #3）ので、その会話の文にもう新しい値が出る

### 2.3 判定する会話・上限・下がる方（2026-10-02 に決めた）

- 判定する会話：最初は「プレイヤーが一言でも話したか」で分けていた。
  これだと贈り物のような行動だけの会話が外れるので、開け閉めの印以外の行動も数えるようにした。
  開け閉めの印は、実際の要約の記録（`output_data`）の user の行に出たものから選んだ（話しかける 72件・会話を終了する 64件・取引を終了する 10件）。
  ほかに出ていたのは、ゲームが入れる売り買い（「〜を購入した。」「〜を売却した。」）と、仲間との別れ（「〜と別れ、パーティから外れてもらった」）。
  どちらも判定に入れる（売り買いは用件なので判定はほぼ 0、別れは気持ちが動いてよい場面）
- ライバルの上限：911 は好感度30ごとに態度を1段和らげる。会話で 60 まで上がると、張り合いを一度もせずに「認める」まで進んでしまう。
  そこで 911 がローダの窓口 `talk_affinity`（TECH.md §3.3.8）でライバルの上限を 30 に狭める。
  この MOD は特定の MOD を知らずに、窓口に聞くだけにした
- 下がる方には回数の制限を付けない。怒らせ続ければ嫌われるのが自然なため
- 404 で同席した仲間は判定しない。判定を広げるには要約とは別に LLM を呼ぶことになり、§2.2 でやめた待ちの延びがまた出るため
