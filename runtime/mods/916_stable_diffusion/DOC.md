## 1. 遊び方（`docs\MODS.md` 相当）

### `916_stable_diffusion`: Stable Diffusion の解像度・サンプラー・モデル・プロンプトを差し替える

ゲームは立ち絵を 256x512 で下描きしてから 512x1024 で描き直し、背景を 1024x512 で、
敵・モンスターを 512x512 で描く（敵だけは1段）。
サンプラーも段ごとに決め打ちで、どちらも設定画面からは変えられない。

この MOD は、**どのバックエンドでも通る1つの出口**でその値を書き換える。
縦横比は保つので絵は歪まない。

種類と段で分けて指定する。

| 分け方 | 何が分かるか | どこで分かるか |
|---|---|---|
| 立ち絵 / 敵・モンスター / 背景 | 解像度をそれぞれに指定できる | 入口の関数（敵は `generate_enemy_image` を通る） |
| 1段目 / 2段目 / LCM の段 | サンプラーを段ごとに指定できる | 上の層の関数（`generate_image_anime` なら1段目、`generate_image_real_lcm` なら LCM の段） |

立ち絵と敵は同じ生成関数を通るので、**サンプラーは段の設定が両方に効く**。
解像度だけは入口で分かるので別々に指定できる。

| 設定 | 既定（ゲームのまま） | 意味 |
| --- | --- | --- |
| 立ち絵の短辺の目標 / 長辺の上限 | 512 / 1024 | 縦横比を保ったまま拡大する。短辺の目標より先に長辺の上限へ当たればそこで止まる |
| 敵・モンスターの短辺の目標 / 長辺の上限 | 512 / 512 | 敵は**正方形 512x512 を1段**で描く（立ち絵とは別物）。立ち絵と別に指定できる |
| 背景の短辺の目標 / 長辺の上限 | 512 / 1024 | 背景はゲームでは 1024x512 |
| 1段目の方法 / steps / cfg / スケジューラ | euler_a / 20 / 8.0 / default | 立ち絵と敵の下描き |
| 2段目の方法 / steps / cfg / スケジューラ | dpmpp2m / 15 / 7.0 / karras | 立ち絵と敵の描き直し。この段だけスケジューラが karras |
| LCM の段の方法 / steps / cfg / スケジューラ | lcm / 5 / 1.0 / default | **背景と敵・モンスターが通る段**。速さ優先の設定なので、方法を変えるなら steps と cfg も上げる |
| チェックポイント / TAESD / VAE / LoRA の置き場 | 空（ゲームのまま） | SDXL のモデルへ移るときに指す。系統は揃えること |
| プロンプトの LoRA タグを外す | 切 | **ゲームが入れた**タグだけ外す。規則で付け替えた先や足したタグは残る。SDXL へ移るときに入にする |
| VAE を渡さずに建てる | 切 | TAESD を差し替えても色が合わないときの逃げ道 |
| モデルの系統に合わせて直す | `auto` | チェックポイントの中身から SD1.5 / SDXL を見分け、壊れる組み合わせだけ直す（§3） |
| diffusers 系でも寸法を変える | 切 | `diffusers_openvino` のような変換済みモデルの一族。入にするとモデルの作り直しで RAM を使い切ることがある。使うなら**寸法は1通りに絞る**（種類ごとに別の寸法を指定しない） |
| TAESD を使わずに建てる | 切 | VAE で復号する。遅いが絵は出る |

**既定値はすべて実測したゲームの値**で、既定のままの項目はゲームへ1つも書き込まない。
ゲームが更新で値を変えたときに、こちらの古い既定を焼き付けないため。

短辺の目標を上げても、長辺の上限に先に当たればそこで止まる。
例えば立ち絵の短辺を 832 にしても、長辺の上限が 1024 のままなら何も変わらない。
実際に伸ばすなら上限も比例して上げる（832 / 1664）。
寸法は 64 の倍数へ四捨五入し、片辺 2048 で止める。

効くのはこれから作られる絵だけで、既にある絵は再生成で作り直せる。
書き換えた値は `out\stable_diffusion.log` に1行ずつ出る。

寸法・サンプラー・安全弁・規則は**生成のたびに読み直す**ので、道具画面で保存すれば次の絵から効く。
注入し直しは要らない（版17。元 MOD のホットリロードと同じ）。
モデルの置き場だけは**ゲームを起動し直してから注入する**。
パイプラインが建つ瞬間にしか書けず、ゲームは1プロセスに1回しか建てない。
**タイトルへ戻ってワールドを選び直しても建て直らない**
（実測: `set_ai_models` に入った時点で `txt2img_pipe` が在る回は `load_sd_pipeline` を呼ばない。7回とも）。
差し替えが届いていないときは、ログに1度だけ警告が出る。

```text
sdcpp_cuda.stable_diffusion:StableDiffusion.generate_image [portrait/stage1] width: 256->448 height: 512->832
```

### なぜモデルの指定を MOD が持つのか

ゲーム内にもモデルの選択はあるが、**選べるのはゲームフォルダの中だけ**。
`config.json` に入るのは `model_name: "sotemix_v30"` という名前で、
パイプラインへ渡るのは `runtime/models/sd15/checkpoints/<名前>.safetensors`（実測）。

| やりたいこと | ゲーム内の選択で足りるか |
| --- | --- |
| 同梱の SD1.5 モデルを切り替える | 足りる |
| 外に置いた SDXL（数GB）を使う | 足りない。ゲームフォルダへコピーが要る |
| TAESDXL を使う | 足りない。同梱の TAESD を上書きするしかない |
| SDXL 用の LoRA を別フォルダに置く | 足りない |

DLL 版はこの3つを「ゲームフォルダへ置く・上書きする」で解決していた。
**ゲームのファイルを触らないことがこの MOD の眼目**なので、
チェックポイント・TAESD・VAE・LoRA 置き場の指定は補助ではなく核にあたる。
既定は空（ゲームのまま）で、指したときだけ効く。

ゲーム内の選択がパイプラインまで届くのかは未計測
（選んだと聞いた回も `config.json` は元の名前のままで、建ったのも元のモデルだった）。
届いていても、上の表の3つは変わらない。

### モデルの置き場（`state\models\`）

ゲームのフォルダを触らずに済ませるため、外へ置くモデルの場所を決めてある。

```text
state\models\sd15\checkpoints\  taesd\  vae\  lora\
state\models\sdxl\checkpoints\  taesd\  vae\  lora\
```

**系統を先に切る。**
壊れ方（プロセスごと落ちる）は系統の食い違いで起きるので、
1つのフォルダの中身が常に揃った組になる形にした。
中の名前はゲームの `runtime\models\sd15\...` と同じにして、説明を減らしてある。
`state\` の下に置くのは、利用者が用意する大きなファイルの前例（`state\musics\battle\`）に合わせたもの。
MOD のフォルダ名では切らない（正式化で番号が変わると行方不明になるため）。

道具画面の「状態 / モデル」から、置き場を開く・中身を数える・
**TAESD デコーダをダウンロードする**ことができる。
ダウンロード元は HuggingFace の `madebyollin/taesdxl`（SDXL 用）と `madebyollin/taesd`（SD1.5 用。
ゲーム同梱と同じもの）で、どちらも MIT・約 9.8MB。
取れない環境では URL と置き場と名前を画面に出す（手で入れられる）。
書き途中のファイルは `.part` に書いてから置き換えるので、失敗しても置き場は汚れない。

### SDXL のモデルへ移る

実機で通った組み合わせ（2026-09-18）。**上の4つが要る**（寸法は好み）。

| 設定 | 値 | なぜ要るか |
| --- | --- | --- |
| チェックポイントの差し替え | SDXL の `.safetensors` | ゲーム内のモデル選択でも選べるが、こちらで指せば確実 |
| TAESD デコーダの差し替え | TAESDXL の `.safetensors` | 系統が違うと復号できない。**ゲームフォルダの外の絶対パスでよい** |
| プロンプトの LoRA タグを外す | 入 | ゲームが入れる SD1.5 用の LCM LoRA が当たると**プロセスごと落ちる** |
| LCM の段の方法 / steps / cfg | `euler_a` / 24 / 5.0 | ゲームの `lcm` / 5 / 1.0 のままだと**マゼンタに潰れる** |
| 立ち絵の短辺 / 長辺 | 1024 / 2048（好みで） | SDXL は 1 メガピクセル前後で学習されているので大きめが向く。**必須ではない**（0.52 メガピクセルでも正しく出る） |

VAE は SD1.5 のままでよい（復号は TAESD を通る）。
ゲーム同梱のファイルは1つも書き換えない。

> SD1.5 のモデルに SDXL 用の LoRA を当てても**ゲームごと落ちる**。系統は必ず揃えること。

## 3. 検証の記録（`docs\VERIFICATION.md` §3.65 相当）

### 当てる先と、名指ししない理由

出口は一族につき1つで、実機で4つ確かめてある（GAME.md §2.33）。

| `sd_backend.name` | 出口 | 当たる項目 |
| --- | --- | --- |
| `sdcpp_cuda` / `sdcpp_vulkan` / `sdcpp_cpu` | `<sdcpp_*>.stable_diffusion:StableDiffusion.generate_image` | 寸法・方法・steps・cfg・スケジューラ |
| `diffusers_openvino` | `optimum.intel.openvino.modeling_diffusion:OVStableDiffusionPipeline.__call__` | 寸法・steps・cfg（方法とスケジューラは同じ口が無いので落とす） |

モジュール名は `config.json` から組み立てられない。
`sdcpp_cuda` は `image_generation.sdcppcuda`（下線が落ちる）、
`diffusers_openvino` は `image_generation.diffusers_openvino`（下線が残る）。
そのため出口は `sys.modules` と生きたパイプラインの型から引く。

材料（チェックポイント・TAESD・VAE・LoRA の置き場）はパイプラインが建つ前にしか書けない。
建てる関数 `load_sd_pipeline` を包み、その直前に書く（版15）。
最初の1回は import から構築の開始までが 0.27〜0.62 秒しかなく、5秒ごとの見張りでは包みが間に合わないので、
`sys.meta_path` の先頭に観測者を置き、モジュールの本体が走り終えた直後に包みと書き込みを済ませる。
**この観測者は本来ローダの語彙**（TECH.md §3.2.3）で、試作の間だけ MOD が持っている。
正式化のときは `instantale_modloader` 側（`sd.py`）へ移す。

版14 までは観測者だけで書いていた。
観測者は import の瞬間にしか効かず、同じプロセスで2回目のワールド選択をしても
import は走らない（Python が sys.modules に持っている）ので、
注入し直して設定を変えても構築には前の値が残る作りだった。
230 の記録では `load_sd_pipeline` は全プロセスで `#1` しか無く、
**同じプロセスでの2回目の構築は一度も測っていない**。版15 の経路もまだ実機で当てていない。

### 実機で確かめたこと

| # | 確かめること | 見るところ |
| --- | --- | --- |
| 1 | 建つ前の差し替えが構築に届く | **決着（2026-09-18）。届く。** import の直後に書いた `taesd_path=''` が `StableDiffusion.__init__` にそのまま渡り、VAE 復号で背景が出た（2.8 秒。TAESD 有りは 2.7 秒で、この寸法では復号は律速ではない）。チェックポイント・VAE・LoRA の置き場も同じ経路なので、SDXL 化にゲームのファイルを触る必要は無い |
| 2 | 寸法を上げた絵が下流を通る | **決着（2026-09-18）。通る。** 832x1664 のまま背景抜き・保存・立ち絵・顔まで到達し、`131_` の切り直しは実寸で扱うので顔もずれない（切り出した 256x256 の中で顔が再検出できる）。外れた1体は寸法に依らず検出できない個体だった（同じ絵を 512x1024 や 416x832 に縮めても素の箱が0件） |
| 3 | 一族で結果が割れないか | **割れる（2026-09-18）。刻み次第。** `diffusers_openvino` で背景を 1536x768（画素 x2.25）にすると 64GB の RAM を使い切って SSD へページングを始めたので中止。1152x576（画素 x1.27）なら **15.1 秒で通った**（素の 1024x512 は 10.5 秒）。ただし**通った回も RAM は伸び、ゲームを閉じるまで戻らなかった**。形を固定して変換したモデルなので、寸法ごとに作り直したものが常駐する。**版3 でこの一族の寸法は既定で触らない**（設定で入にできる）。sdcpp 系は 1.625 倍でも素直に受ける |
| 4 | サンプラーの上書きが通るか | **決着（2026-09-18）。通る。** 2段目を `dpmpp2mv2` / cfg 5.0 に差し替えて立ち絵を2体作り、4.4 秒と 4.2 秒で出た（steps は 15 のまま）。方法名の差し替えも cfg の変更も効く。`SAMPLE_METHOD_MAP` に無い名前は設定が choice なので渡せない。**速さの比較には使えない**（素の 10.4 秒はモデルを読んだ直後の回で、こちらは温まった後） |
| 5 | 敵・モンスターの素の値 | **決着（2026-09-18）。立ち絵と全く違う。** `generate_enemy_image` から `generate_image_real_lcm` へ入り、**正方形 512x512 を1段**で描く（lcm / 5 / cfg 1、1.5 秒）。立ち絵の2段（256x512 と 512x1024、euler_a と dpmpp2m）とは寸法もサンプラーも別物。**版5 でこれに合わせた**（敵の既定を 512x512 に、段の名前を「背景」から「LCM の段」へ） |
| 6 | SDXL 一式 | **決着（2026-09-18）。MOD だけで成立。** チェックポイントと TAESDXL を指し、LoRA タグを外し、サンプラーを `euler_a` / 24 / cfg 5.0 にして、寸法を 1024x2048 にしたら人物として成立した絵が 21.7 秒で出た。ゲームのファイルは1つも触っていない（TAESDXL はゲームフォルダの外の絶対パスで読めた）。途中で2回外した経緯は下の「SDXL で踏んだ順序」 |

### DLL 版の機能一覧と移植の状況

元の `InstantaleStableDiffusionMod`（プロキシ DLL 版）の全機能に対する現在地。
仕様は同梱の `sd_upscale.sd15.ini` のコメントと `mod_src/proxy.c` の処理順から読んだ。

| DLL 版 | 状況 | 備考 |
| --- | --- | --- |
| `[upscale]` `goal_short` / `max_long` / `round` | **済** | 種類別に持つ。種類は縦横比ではなく Python の実体（立ち絵 / 敵 / 背景） |
| `[upscale]` `goal_short_landscape` / `max_long_landscape` | **済** | 背景の設定として独立 |
| `[upscale]` `enabled` / `enabled_<種類>` | **不要** | 既定がゲームの値なので、素の値のままにすれば触らない |
| `[upscale]` `skip_if` / `skip_if_<種類>` | **済** | 「拡大しない条件」の表。条件の書式は追加の行と共通 |
| img2img の init / mask バッファの拡大 | **不要** | ゲームの Python 層（`_format_init_image`）が寸法を合わせる。実測で 512x1024 の init が 832x1664 の生成に通った |
| `[sampler]` 種類別の method / steps / cfg / scheduler | **済** | 段別（1段目 / 2段目 / LCM の段）に持つ |
| `[lora_map]` LoRA の付け替え・無効化 | **済** | 名前ごとの付け替えと `off`。道具画面の表で編む |
| `[lora_add]` 種類別の追加 | **済** | `state\stable_diffusion\prompt_rules.json` と道具画面の表 |
| `[lora_add_if]` 条件付きの追加 | **済** | `/` 区切りでどれか1つ、`!` 付きは不含有、単語境界つき・大小不問 |
| `[negative_add]` | **済** | 追加の行で対象を `negative` にする |
| `[prompt_remove]` / `[negative_remove]` | **済** | カンマ区切りの1区画単位・大小不問の完全一致。版21 から重みの括弧の中でも当たる（`(nsfw, worst quality:1.4)` から `nsfw` だけ消せる。ゲームのネガティブがこの形で来るため。元 MOD は当たらない） |
| `[prompt_replace]` / `[negative_replace]` | **済** | `{prompt}` の位置に元のプロンプトを埋める |
| 書き換えの順序（除去 → 置換 → 付け替え → 追加） | **済** | 条件は書き換え前の本文で判定する（`rules.py`） |
| プロンプトのポインタ検証 | **不要** | Python では引数。構造体のオフセットを当てる必要が無い |
| SD1.5 / SDXL のモード切替 | **済**（別の形） | ゲームのファイルを触らず、チェックポイントと TAESD のパスを建つ前に差し替える。系統違いのクラッシュは安全弁が自動で避ける |

### 実測した時間（1.625 倍、`sdcpp_cuda`、2026-09-18）

| 段 | 素のゲーム | 1.625 倍 |
| --- | --- | --- |
| 立ち絵の1段目（256x512 から 448x832） | 4.8 秒 | 5.1 / 11.8 / 126.5 秒 |
| 立ち絵の2段目（512x1024 から 832x1664） | 10.4 秒 | 49.2 / 53.0 / 50.2 秒 |
| 背景（1024x512。設定は既定） | 2.4 秒 | 2.7 秒 |

SDXL（`waiIllustriousSDXL_v170`）で 1024x2048・`euler_a` / 24 / cfg 5.0 のときは、
立ち絵1体が **21.7 / 21.8 / 22.2 秒**（3体。構築は 4.2〜5.8 秒）。
SD1.5 の素（512x1024・LCM 5 steps）が 3 秒前後なので、7 倍前後の費用になる。

素の値はモデルを読んだ直後に測ったもので、温まった後は同じ設定でも 4 秒台まで下がる。
**倍率どうしの比較にだけ使い、速くなった遅くなったの根拠にはしない。**

安定して効くのは2段目の約5倍で、立ち絵1体が 15 秒から 60 秒前後になる。
1段目の 126.5 秒は **VRAM が溢れた回**で、寸法ではなく載っているものの合計で決まる
（同じ寸法の他の回は 5〜12 秒）。
拡大はその余裕を削るので、LLM を載せたまま上げると桁で遅くなる。

### 段は関数では決まらない（版4 で直した）

`diffusers_openvino` では**キャラの絵も `generate_image_real_lcm` を通る**
（実機 2026-09-18。画質が `highres_faster` のとき、512x1024 を 10.5 秒で1枚）。
版3 まではこの関数を「背景の段」と決め打ちしていたので、
この一族ではキャラにサンプラーの背景設定が当たる作りだった。
版4 から段は**種類と関数の組**で決める（背景は種類で決まり、
立ち絵と敵は `image_to_image_anime` なら2段目、それ以外は1段目）。

### モデルの系統に合わせる安全弁（版8）

今日踏んだ壊れ方は2つとも「モデルの系統と設定の食い違い」だった。
同じ踏み方をしないよう、**チェックポイントの中身から系統を見分けて**必要なぶんだけ直す
（設定「モデルの系統に合わせて直す」。既定は `auto`）。

見分け方は safetensors のヘッダ。
先頭8バイトがヘッダ（JSON）の長さで、その鍵がテンソルの名前。
本体は読まないので実測 0.00 秒（ヘッダは SD1.5 が 150KB、SDXL が 365KB）。

| 系統 | ヘッダに在る印 |
| --- | --- |
| SD1.5 | `cond_stage_model.*` |
| SDXL | `conditioner.embedders.1.*`（2つ目のテキスト符号化器）と `model.diffusion_model.label_emb.*` |

**名前でもファイルの大きさでも判定しない。**
名前は当てにならず（手元の `AnythingXL_inkBase` は XL と付くが SD1.5）、
大きさは量子化や差分で動く。

直すのは壊れると分かっている組み合わせだけ。

| 状況 | すること | なぜ |
| --- | --- | --- |
| SDXL のプロンプトに SD1.5 用の LoRA タグ | **ゲームが入れたタグだけ**外す | **プロセスごと落ちる**（実測）。規則で付け替えた先や足したタグ（SDXL 用）は残す。版14 までは全部外していたので、付け替えで SDXL 用にしたタグまで消えていた |

| 学習の寸法から離れた指定 | **警告だけ。値は動かさない** | 壊れるとは限らない（下を参照） |

設定で明示した項目は動かさない（素のままの項目だけ寄せる）。

**寸法を自動で動かすのはやめた。**
版8 では「SDXL に 0.9 メガピクセル未満は絵にならない」と読んで引き上げていたが、
**実測で否定された**。
安全弁なしの 1024x512（0.52 メガピクセル）の背景が SDXL で正しく出ている
（サンプラーだけは `euler_a` / 24 / cfg 5.0 になっていた）。
マゼンタに潰れていた回の原因は寸法ではなく**サンプラー**で、
壊れ方を寸法のせいにしたのがこちらの読み違いだった。

### 版20 で直した2つ（実機 2026-09-20 で見つかった）

SDXL プリセットを当てて立ち絵を3体作った回のログから。

**包みが二重に当たっていた。**
1段目が 256x512 から 512x1024 へ、そのすぐ後に **512x1024 から 1024x2048 へ**もう一度拡大され、
ゲームが 256x512 を頼んだ段を **1024x2048**（16倍の画素）で描いていた（22.5 秒。`230_` の実測）。
916 のログに同じミリ秒で2行出る形が印で、2行目の段が `None` になる。

| 段 | ゲームが頼んだ | 実際に描いた | あるべき |
| --- | --- | --- | --- |
| 1段目 | 256x512 | 1024x2048 | 512x1024 |
| 2段目 | 512x1024 | 1024x2048 | 1024x2048 |

原因は**用済みの `apply()` が当て直していた**こと。
`load_sd_pipeline` の包みと5秒ごとの見張りは、注入し直した後も生きている。
そこから `attach()` が走ると、ローダは「いまの世代」として入れるので前の層を剥がさず、
新しい世代の包みの**外側に**古い層が重なる。
古い層は自分のモジュールの印を読むので段が `None` になり（注入し直しで MOD は読み直され、
`MARKS` は別インスタンスになる）、寸法だけが素の計算でもう一度掛かる。
版20 は `attach()` の先頭と `load_sd_pipeline` の包みで `ctx.superseded()` を見る。

**規則が0行でもプロンプトを書き換えていた。**
`rewrite()` が当たる規則の有無に関わらず最後に `tidy()` を通していたため、
ゲームの `masterpiece,high quality`（カンマの後に空白が無い）が `masterpiece, high quality` に均され、
毎回 227字 -> 231字 の書き換えとしてログに出ていた。
版20 は**当たった規則が1つも無ければ本文に触らない**。
付け替えで空いた区画を塞ぐ `tidy()` は、当たった回だけ通る。

### SDXL で踏んだ順序（2026-09-18）

素のまま SDXL のチェックポイントだけ差し替えても使えない。
実機では2回外してから通った。

| 回 | 何をした | 結果 |
| --- | --- | --- |
| 1 | チェックポイントと TAESDXL を差し替え、寸法を 640x1216 に | **プロセスごと落ちた**。ゲームが立ち絵のプロンプトに入れる SD1.5 用の LCM LoRA が SDXL に当たったため |
| 2 | LoRA タグを外す（版6） | 落ちずに 8.1 秒で出たが、**マゼンタに潰れた絵**。LCM 用の 5 steps / cfg 1.0 のまま回していた |
| 3 | サンプラーを `euler_a` / 24 / cfg 5.0、寸法を 1024x2048 に | **人物として成立**。21.7 秒 |

3 でサンプラーと寸法を同時に変えたので、この時点ではどちらが効いたのか分かっていなかった。
後から**寸法は関係ない**と分かった。
安全弁なしの背景（1024x512 = 0.52 メガピクセル、サンプラーだけ `euler_a` / 24 / cfg 5.0）が
正しく出ている。
つまり SDXL に要るのは**チェックポイント・TAESDXL・LoRA の除去・サンプラー**の4つで、
寸法は画質の好みの話。

復号（TAESDXL）は最初から効いていた。
色が壊れて見えたのは**サンプラーと寸法**で、DLL 版の SDXL プリセットも同じ値
（`portrait_method = euler_a` / `portrait_steps = 24` / `portrait_cfg = 5.0`、
`goal_short = 1024` / `max_long = 2048`）を当てている。
VAE は SD1.5 のままでよい（DLL 版の手順書も「復号は TAESDXL が使われるので実害なし」と書いている）。

画質の設定で経路が変わる点にも注意が要る。
`highres_faster` だと立ち絵も **LCM の段**（`generate_image_real_lcm`）を通るので、
立ち絵に効かせたいサンプラーは「2段目」ではなく「LCM の段」の設定になる。

### ゲーム側の不具合を1つ踏んだ（`diffusers_openvino` + `highres_upscale`）

バックエンドを `diffusers_openvino` にしたまま、画質が `highres_upscale`（2段で描く指定）だと、
立ち絵の生成でゲーム自身が落ちる。

UnboundLocalError: local variable 'generated_image' referenced before assignment

同梱の初期テンプレートは `diffusers_openvino` に `lowres_faster` を組み合わせている。
バックエンドを切り替えても画質の設定は付いてこない。

| 症状 | やること |

| 絵が変わらない | `out\stable_diffusion.log` に `wrapped` の行が出ているか。短辺の目標だけ上げて長辺の上限がゲームのままだと、計算上どこも変わらない |
