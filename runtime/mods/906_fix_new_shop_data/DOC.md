## 0. なぜ配らないか

**未確認だからでも作りかけだからでもない。** 実機で決着している（§3）。
`app.save_data_dict` から `app.world_dict` へ施設1件と主1人を写した瞬間に、
同じ店がその場で開いた。

配らないのは、**素のゲームだけでは踏めない**から。
実セーブを復号して突き合わせた結果（GAME.md §2.28、ヴェスティア、2026-08-21）、
2つの素データの差は3種類あって、売買を壊すのはそのうち1種類だけだった。

| 差 | 件数 | 出どころ | 売買を壊すか |
|---|---|---|---|
| エリア | 13個 | 依頼で生成されるダンジョン。**仕様** | 壊さない |
| NPC | 8人 | ゲームが遊んでいる最中に作った分 | 壊さない（施設の主が欠けた例は出ていない） |
| 施設 | **2件** | **セーブエディタで足したもの**（§3 で特定） | **壊す** |

素のゲームが遊んでいる最中に施設を増やす経路は、いまのところ1つも見つかっていない
（`free_facility` も世界生成のときに集落ごと1つ置かれるだけ。GAME.md §2.21）。
つまりこの MOD が要るのは、**外の道具で施設を足したセーブ**だけになる。

そして §3 のとおり、その道具の側でも直せることが確定している
（施設を足すときに両方の辞書へ書けば、不整合はそもそも生まれない）。
この MOD は**既に壊れてしまったセーブを開けるようにする手当て**として残る。

### 配ると決める条件

**素のゲームで施設が増える経路が、実機で1つでも見つかったとき。**
そのときは 1xx の空き番号へ振り直して、下の各節を元の場所へ戻す。
逆に、セーブエディタ側が両方の辞書へ書くようになり、
壊れたセーブがもう残っていないと判断できたら、`discontinued\` へ出す（TECH.md §2.6.1）。

## 1. 遊び方（`docs\MODS.md` 相当）

### `906_fix_new_shop_data`: 遊んでいる最中に生まれた店で売買できるようにする

世界を作った後に生まれた店で「売買する」を選ぶと、画面が変わらないまま止まるのを直す。
裏ではスレッドが落ちている。

```
File "instantale.py", line 3080, in shopping_start_method_1
KeyError: '229'
```

ゲームは素データの辞書を2つ持っていて（`world_data.json` の側と `savedata.json` の側）、
遊んでいる最中に作られた施設・NPC・エリアは savedata の側にしか足されない。
それなのに採番だけは両方で進む。
実セーブでは施設が 228 対 230、NPC が 92 対 100、エリアが 40 対 53 で、
採番はどちらも 230 / 100 / 53 まで来ていた（GAME.md §2.28）。
世界生成のときからある店はどちらの辞書にも在るので、この症状は出ない。

セーブエディタで足した店も同じ症状になる（足した先が savedata の側だけのため）。

この MOD は、ゲームが引き損なって落ちたところで、
そのキーを持っているほうの辞書から写して、もう一度だけやり直す。

```
KeyError のキー → 持っている辞書を探す → 欠けている段を写す → もう一度開く

  エリアが無い  → そのエリアを丸ごと
  ノードが無い  → そのノードを丸ごと
  施設が無い    → その施設1件
  NPC が無い    → その1人
```

キーがエリア・ノード・施設・NPC のどれなのかは決めつけない
（採番が種類ごとに分かれていて、同じ番号が別の種類に居る。
実際、ノードごと欠けている店ではノードの id で落ちた）。
4つとも試して、当たったものを全部写す。
施設を写したときは、その主も続けて揃える。
写すのはゲーム自身が作った値をそのままで、項目を整えたり足したりはしない
（ゲーム自身が項目の不揃いを持っているため。GAME.md §2.28）。
既に在れば何もしないので、本体が両方の辞書へ書くようになった版ではこの MOD は動かない。

記録は `out\new_shop_data.log`。
正常に開ける店では何も書かない。写したときだけ1行増える。

```
[...] copied the facility into app.world_dict from app.save_data_dict
      (key read as a facility; area=8 node=32 facility=229): 1 facility/facilities, 1 owner(s) 99
```

写したのに開かなかったときは、そこで見えていたものが続けて出る
（どの辞書がそのキーを持っていたか、`app` が持っている辞書の一覧、
組み上がった側の名簿と現在地）。
1つのキーにつき1度だけで、同じ店を開き直しても増えない。

#### セーブに残る

写した施設と NPC は次の保存で `world_data.json` に落ちるので、
この MOD を外しても世界に残る
（実測: 施設1件と主1人を写した後、`world_data.json` の施設が 228→229、
NPC が 92→93 に増えた。裏返せば、一度開いた店は以後この MOD 抜きでも開く）。
足すのはゲーム自身が作った実体で、MOD 独自の項目は1つも書かないが、
「MOD を消せば完全に元通り」からは外れる
（`902_` の NPC 生成と同じ性質）。
採番のほうは既にそこまで進んでいるので、整合する方向のずれではある。

#### 困ったとき

| 症状 | やること |
|---|---|
| 店を開いても何も起きない | `out\new_shop_data.log` に `did not open` で始まる塊が出る。どの辞書が施設を持っていたか、`app` が持っている辞書の一覧、組み上がった側の様子が続くので、その塊を添えて報告してほしい |
| 別の場所で同じ `KeyError` が出る | 欠けているのは施設だけではない（実セーブではエリアも13個欠けていた）。この MOD が直すのは売買の入口だけなので、落ちた場所を添えて報告してほしい |
| `not a table` が出る | 素データの形が想定と違う。その段は触らずに素の動作へ渡している |
| 写したものを消したい | セーブから消す道具は無い。`world_data.json` を編集する |

## 3. 検証の記録（`docs\VERIFICATION.md` §3 相当）

### 遊んでいる最中に生まれた店（`906_`）: 決着（2026-08-21）

版3の1行で開いた。

```
copied the facility into app.world_dict from app.save_data_dict
  (key read as a facility; area=8 node=32 facility=229): 1 facility/facilities, 1 owner(s) 99
```

| 確定したこと | 根拠 |
| --- | --- |
| ゲームが施設を引くのは `app.world_dict` | そこへ写した瞬間に同じ店が開いた |
| 写した内容は保存される | `world_data.json` が NPC 92→93、施設 228→229 に増えた |
| 品揃えはその後ゲーム自身が作る | 主ガルドの `inventory` が 0→7 |
| やり直しは1回で足りる | `did not open` の塊は出ていない。以後クラッシュ記録も増えていない（最後は 11:20:58、成功は 11:21:50） |
| 主の `job` の食い違いは単独の原因ではない | `other` → `general_store` に直しただけでは症状が変わらなかった |

#### 読み違えを2回した

| 版 | 何をしたか | 実機の結果 |
| --- | --- | --- |
| 版1 | 引数から `(area_id, node_id, facility_id)` を拾って埋める | 不発。**記録が1行も出ない** |
| 版2 | 版1に記録を足す。素データの判定を `areas` だけに緩める | 不発。ただし理由が1行で出た |
| 版3 | `KeyError` のキーを起点にする | 成立 |

版2が出した1行がすべてだった:

```
skip: could not read the ids from the arguments: args=() kwargs=[]
```

`shopping_start_method_1` は `self` 以外の引数を取らない。
クラッシュ記録に出ていた3つは**関数の中で作られたローカル変数**で、
版1も版2もそれを引数と読んでいた。

> クラッシュ記録の locals は引数とローカル変数を区別して出さない。
> 「3つだけ生えている＝引数」と読んだのが誤り。
> 数が少ないのは、そこまでしか実行が進んでいないからでしかない。

版1が黙って抜ける道は3本あり、どれを通ったのかが残らなかった。
そこが分からないこと自体が最初の不具合で、実機1回をまるごと捨てている。

> 直す MOD は、直せなかったときに何が見えていたかを**残す**こと。
> 版2で記録を足した次の1回で決着している。

#### この不具合の出どころ

| 欠けていたもの | 出どころ |
| --- | --- |
| 施設 228 / 229 と主のエデル・ガルド | セーブエディタで足したもの |
| NPC 92〜97 | 未確認（形はゲームが作るものと同じ） |
| エリア13個（37〜52 のうち） | ゲームが依頼で作ったダンジョン。**仕様**。そのセーブ限りのエリアは savedata にだけ入り、world 側に無くても正常に動く |

「savedata にしか無い」こと自体は不具合ではない。
実害を出していたのは、エディタで足した施設が `world_data.json` 側に無かったこと。

> **セーブエディタ側でも直せることが、これで確定した。**
> `world_data.json` へ書けば開くのだから、
> エディタが施設や NPC を足すときに両方へ書けば、この不整合はそもそも生まれない。
> `906_` は既にできてしまったセーブを開けるようにする手当てとして残る。

#### 残っていること

- キーが施設 id 以外（ノード id・エリア id）で来る経路は**実機では通っていない**。
  オフラインでは再現していて（ノードごと欠けている店ではノード id で落ちる）、
  4つの見立てを全部試すのはそのため
- `job` を `other` に戻したまま素データだけ揃えたらどうなるかは試していない。
  だから「`job` は完全に無関係」とまでは言えない（GAME.md §2.13.1）

オフラインは `tools/tests/test_wip_new_shop_data.py` の53件が全通。
