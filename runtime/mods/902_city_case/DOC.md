## 1. 遊び方（`docs\MODS.md` 相当）

### `902_city_case`: 街の事件を調べる

ギルドに「気になる噂を聞く」が出る。押すと町で起きている盗みの調査が始まり、
事件のために作られた4人の容疑者が町に現れる。

依頼を受けると容疑者の一覧が出る。特徴と一緒にどこに居るかも書いてある
ので、話を聞きに行く相手はすぐ分かる（居場所はその都度いまの位置を見ているので、
相手が動いても正しい）。

施設の主に普通に話しかけて、事件のことを尋ねると、その人物が見聞きした
ことを話す。専用の選択肢は無い ― いつもの「会話する」でよい。
入って即抜けるだけでは何も手に入らない（相手は何か言いたげな素振りを
見せるだけ）。容疑者に居場所を尋ねるときも同じ。分かるのは犯人についての事実
で、「犯人は片腕だった」「犯人は大柄だった」のように容疑者を絞り込んでいく。

#### 証言は必ずしも正しくない

聞いた話の1つが思い違いのことがある。そのときは、集めた話をすべて信じると
誰ひとり当てはまらなくなる。「調べの進み具合を確かめる」で気づけるように
なっているが、どれが嘘かは教えてくれない。

1つずつ「これが間違いだとしたら」と外してみて、ちょうど1人が残る外し方を
探すことになる。残り方が一意に決まらない事件は出さないので、当てずっぽうに
なることはない。

嘘が混じらない事件もある（既定で半々）。混ぜたくなければ設定を 0 にする。

順番は無く、どこから調べてもよい。そしていつでも告発できる ―
2つで1人に絞れたなら、残りは聞かなくてよい。当てれば報酬が出る。
外したらそこで終わり（新しい事件は受けられる）。

告発はギルドで「犯人を告発する」を押す。告発だけの画面になり、容疑者が
特徴付きで並ぶので、集めた事実と見比べて1人を選ぶ。ここには施設の選択肢は
出ない（選んでいる最中に「出る」や「会話する」が並んでいると紛らわしいため）。

その画面には2つの降り方がある。

| ボタン | どうなるか |
|---|---|
| やめる（もう少し考える） | 告発だけをやめる。事件は続くので、聞き込みの続きから再開できる |
| 諦める（調べを打ち切る） | 事件そのものを終わりにする。容疑者は町を去り、報酬は無い。真相も分からないままになる。ギルドで新しい噂を聞くところからやり直せる |

既にあるセーブでそのまま遊べる。新しい世界を作る必要は無い ― 容疑者は
依頼を受けた時点で作られるし、事件の記録はセーブの外（`state\`）に置いている。
必要なのはその町にギルドと、聞き込みできる施設がいくつかあることだけ。

事件ごとに題材も顔ぶれも変わる。受けるたびに「何が起きたか」（盗み・付け火・
毒盛り・家畜殺し・贋金・墓荒らし…16種）と「目撃される特徴」（髪・体格・服の色・持ち物・足取り・声・
におい…）を抽選して組み合わせるので、同じ形の推理が続かない。

候補は MOD フォルダの JSON にある。
`runtime\mods\902_city_case\patterns\` の4つを開いて足せば、それだけで
事件の幅が増える（コードは触らない）。

| ファイル | 何の候補か |
|---|---|
| `incidents.json` | 何が起きたか。文言と、AI に渡す説明 |
| `traits.json` | 目撃される特徴の軸（8軸・多くは3値）。引かれる本数は容疑者の数から決まる（4人なら3本）。全部が手がかりになるとは限らず、余った軸は赤鰊になる |
| `whereabouts.json` | その晩どこに居たか（裏の取れる場所／取れない場所） |
| `cast.json` | 下地の人物（AI を切ったときの顔ぶれ） |

書き方は各ファイルの先頭の `_note` にある。書き損じても壊れない ―
読めない項目は飛ばし、その束が空になったら同梱の既定値に戻る。

事件ごとに登場人物と文章が作られる。依頼を受けると AI がその世界に合った
容疑者を書き起こすので、顔ぶれも盗まれた品も毎回変わる。書いているあいだは
「（噂の出どころを当たっている……）」と出て、ゲームが AI を待つときと同じように
選択肢が `...` になって押せなくなる。書き上がると元に戻る。

待っても返ってこないときは、必ず操作が戻る（「今日は誰も口を割らなかった」と
出る）。押せない画面のまま取り残されることはない。

謎そのものは AI が作っていない。誰が犯人か・どの手がかりが誰を消すかは
MOD 側が先に決めていて、AI が書くのは人物像と言い回しだけ。だから AI の調子に
関わらず、必ず解ける事件になる。AI が呼べないときや返事がおかしいときは
同梱の8人と定型の文章に戻り、事件はそのまま始まる。

| 設定 | 意味 |
|---|---|
| 依頼を受ける施設 | 既定「ギルド」。告発もここで行う |
| 解決したときの報酬 | 既定 500 |
| 事件の文章を AI に書かせる | 既定 ON。切ると同梱の8人と定型の文章になる（謎の作りは変わらない） |
| AI の返事を待つ秒数 | 既定 120。超えたら定型で始める。さらに待っても返らなければ操作だけ返す |
| 犯人を退場させる | 既定 ON。切ると真相が分かるだけで犯人だけ町に残る（無実の者は設定に関わらず引き上げる） |
| 容疑者の人数 | 既定 4。3人が最小 |
| 思い違いの証言が混じる割合（％） | 既定 50。0 にすると聞いた話はすべて正しくなる |
| 会話の経路を計測する | 既定 OFF。聞き込みで何も聞けないときだけ入れる |

#### セーブに残らない

この MOD は事件のあいだだけセーブに NPC を足す。容疑者4人はゲーム自身の
NPC としてその町に立つ（既にいる NPC を犯人に仕立てないための作り）。
そして決着したら4人とも世界から消える ― 当てても外しても同じで、
セーブは事件の前の状態に戻る。何件遊んでも NPC は増えない。

以前は無実の3人を町の住人として残していたが、繰り返すぶんセーブに溜まり
続けた（1件3体）。町が見知らぬ人で埋まるほうが害が大きいと判断して
引き上げる形にした。

MOD が作った NPC の控えは `state\city_case_cast.json` にある（セーブの中では
なく外）。置き去りがあれば次の起動で自動的に片付く。

#### 困ったとき

| 症状 | やること |
|---|---|
| 「噂は立ち消えになった」と出る | 容疑者を作れなかった。`out\city_case.log` を見る |
| 「この町には、聞いて回れる場所が無い」 | その町に聞き込みできる施設が無い。別の町で受ける |
| 話しかけても事件の話が出ない | 相手が違う。「調べの進み具合を確かめる」で行き先を確認する |
| 会話の中身と「分かったこと」が噛み合わない | 証言者は尋ねなくても自分から話す作りだが、言い回しは AI が決めるので、遠回しになることがある。全く触れられていないなら `out\city_case.log` を添えて報告してほしい |
| 同じ相手が前の話を引きずる | 会話の記憶はゲームが持っている。手がかりを得た後は新しく差し込まないので、次第に収まる |
| 事件の人物が町から消えた | 決着すると引き上げる作り。異常ではない |
| 仲間にした容疑者が消えない | パーティーに居る者はわざと消していない。外せば次の掃除で片付く |
| 依頼を受けてから始まるまで待たされる | AI が事件の文章を書いている。長すぎるなら設定の「AI の返事を待つ秒数」を縮めるか、「事件の文章を AI に書かせる」を切る |
| 待機表示から戻ってこない | 待ち時間を過ぎれば必ず戻る。戻らないなら `out\live_crashes.log` に `send_request_on_id` のスレッド例外が出ていないか見る |
| 毎回同じ8人が出てくる | AI が呼べていない。`out\city_case.log` に `cannot take a request yet` か `using the built-in cast` が出ているはず |
| 容疑者の見た目と説明が食い違う | 一覧に出る特徴（黒髪・大柄など）が正で、推理はそちらで合っている。文章のほうが外れているだけ |

## 3. 検証の記録（`docs\VERIFICATION.md` §2 相当）

### 2.31 `902_city_case` 街の事件（2026-08-02〜04、実機で成立）

街を回って聞き込み、手がかりを突き合わせて犯人を告発する。実機で通しまで
確認済み。ここに至るまでに設計を3回、実装を3回外しているので、その記録。

#### 設計で外した4点（どれも遊んでみるまで分からなかった）

| 何を作ったか | 何が悪かったか | どう直したか |
|---|---|---|
| 手がかりを一本道の鎖にした | 推理が一切要らない。言われた場所へ行ってボタンを押すだけの作業 | 手がかりを「犯人についての事実」にし、容疑者を除外する形に。順番は無く、いつでも告発できる |
| 行き先が分からないという声に道順を教えて応えた | それがとどめだった。考える余地が完全に消えた | 場所は並べるだけにして、どこから当たるかは選ばせる。渡すのは道順ではなく材料 |
| 既存 NPC を犯人に選んだ | 愛着のある NPC が犯人にされうる。しかも実際には `混乱する村人たち` という群衆が選ばれた | キャストは事件のために生成する。既存 NPC を使う経路は持たない（推理にも使えない ― 特徴が分からないため） |
| 事件の合否を「全部集めれば1人に絞れるか」だけで見た | 条件は通るのに同じ働きしかしない手がかりが並ぶ（下記） | 「どの手がかりも抜けない」を条件に足した。最低3本も要求する |

> **「行き先が分からない」の答えは道順ではない。**
> プレイヤーが退屈なのは歩く先が分からないからではなく、
> 歩いた先で何も考えることがないからだった。

##### 4点目 ― 「解ける」を条件にすると、無駄足が混じる（2026-08-04）

実機のログに出た事件がこれ。

```
容疑者 4人とも大柄。76/77 は黒髪の女、78/79 は淡い髪の男
  c1 犯人の髪は黒かった  -> 78, 79 が消える
  c2 犯人は女だった      -> 78, 79 が消える  ← c1 と全く同じ
  c3 ハルカのアリバイ    -> 77 が消える
```

当時の条件（真犯人以外が全部消えるか）は通っている。それでも
c1 と c2 はどちらか一方で足りる。もう片方を拾うために町を横断するぶんは
まるごと無駄足で、「大柄」も4人全員なので一覧の文字が1つ増えるだけ。

生成器を2万回まわして測ったところ、50.5% の事件に完全に重複した手がかりが
含まれ、79.3% では手がかりを1本抜いても解けた（＝拾う意味が無い手がかりが
ある）。1件の不運ではなく、条件の書き方そのものが緩かった。

直したのは条件の1行で、「1本でも欠けたら絞れない」を足しただけ。
これで重複も、他が既に消している者しか消さない手がかりも、同時に落ちる ―
どちらも「拾いに行った意味が無い」という同じ症状だから。併せて手がかり
最低3本（容疑者4人以上のとき）を要求する。条件を厳しくしたぶん振り直しの
回数が要るので `CAST_ATTEMPTS` を 40 → 300 にした（3〜8人のどの設定でも
取りこぼしが消える）。振り直すのは町に出る前の計算だけで、NPC はまだ作って
いない。

> **「解ける」は事件の質ではない。**解けるかどうかしか見ていないと、
> 解くのに要らない手順がいくらでも紛れ込む。測るべきは
> 集めたものが全部働くかのほう。

#### 実装で外した3点（NPC 生成）

| 試したもの | 結果 |
|---|---|
| `World.generate_character(id, data)` | `KeyError: '<id>'` |
| `save_area_json:generate_npc(...)` | 例外は出ないが何も作られない。世界丸ごとのダンプ（452KB）を検索しても渡した名前が1件も無い |
| `world_dict['npcs'][id]` に書いてから `generate_character` | `KeyError` のまま |

3つ目で「読んでいるのは `app.world_dict` ではない」と確定し、決め打ちをやめて
心当たりの辞書を全部探して全部に書く形（`302_` の `ui.party_stores` と同じ
考え方）にしたら通った。答えはログが教えた:

```
npc stores = [('world.characters', 47), ("app.world_dict['npcs']", 45),
              ("app.save_data_dict['npcs']", 48)]
```

> **2回続けて「ここだろう」で外したら、決め打ちをやめる。**
> このプロジェクトには既にその形（候補を全部集める）があり、最初から
> そちらを使えば1回で済んでいた。

#### 4つ目 ― 項目は揃っていたが、並び順が違っていた（2026-08-04）

そうして作れるようになった NPC は、33項目を漏れなく持っていた。それでも
順番がゲームの書く順とまるで違っていた ― ひな型が21項目しか持っておらず、
残りの12項目（`name` や `id` を含む）が `dict.update` で末尾に足されていた
から。

```
ゲーム:  name, id, category, profile, ... , knowledge, display_position_in_battle
MOD:     state, experience_point, ... , memory, name, category, ... , id, config
```

セーブは辞書をそのまま JSON に落とすので、この順がそのままファイルの行順に
なる。セーブを上から順に見せる道具（別途あるセーブエディタ）では、項目が全部
揃っているのに表示が崩れる（利用者の指摘・2026-08-04）。

正しい並びは実際のセーブから起こした（`savedata_plain.json` の `npcs`。
51体中50体が同じ33項目・同じ順で、残る1体も `speech_style` が無いだけ）。
ひな型に33項目を正しい順で全部持たせたら、`dict.update` が既存の鍵を動かさない
性質だけで並びが保たれる。併せて `knowledge` の型も直した（`{}` ではなく
`[]`）。表は GAME.md §2.23。

> **「項目が揃っている」は「形が同じ」ではない。**
> セーブのように辞書をそのまま落とす相手には、並び順も仕様のうち。
> 検査も「集合が一致するか」ではなく「1つずつ同じ位置か」で書く。

#### 設計の5点目 ― 遊ぶほどセーブが汚れていく（2026-08-04）

決着した事件の犯人には `is_dead` を立て、無実の3人は町の住人として残して
いた。住人が増えていく味を狙ったつもりだったが、繰り返し遊ぶと
1件につき3体ずつ溜まり続ける（利用者の指摘・2026-08-04）。

実セーブ（790KB・NPC 51体）で測った量:

| | |
|---|---|
| 生成直後の NPC | 約 1.4KB |
| ゲームが中身を埋めた後 | 3〜8KB（`inventory` と `life_log` が主） |
| `npcs` がセーブに占める割合 | 約 2割 |
| 1件の事件 | 4体。10件で 40体 |

> **害はバイト数のほうではなかった。**人数は土地の人物一覧にも、ゲームが
> 会話や描写のために組む文脈にも効く。町が見知らぬ人で埋まることのほうが
> 実際の困りごとで、容量はその症状の一つでしかない。

##### 消せる根拠（セーブの構造を読んで確かめた）

セーブの施設は名簿を持っていない。実セーブの `facility` の項目は
`name` / `id` / `description` / `facility_type` / `owner` / `connections` /
`config` だけで、誰がその施設に居るかは NPC 側の `location` から実行時に
組み直されている。クエストも `client_name`（名前の文字列）で持っていて
id では参照しない。

つまり `npcs` から消せば世界から消える。実行時のぶん
（`world.characters` と施設に組まれた名簿）も同時に外す ― 残すと、その
セッションの間だけ幽霊が立ち続ける。

##### 印は NPC に持たせられないので、台帳を外に置く

「この NPC は MOD が作った」という印を NPC 自身に足すと、33項目の並びが
壊れる（上の4つ目）。だから台帳は外部ファイルに置いた
（`state/city_case_cast.json`）。事件の控えを `state/` に持つのと同じ考え方で、
セーブはゲームの形のまま、MOD の都合は `out/` に。

台帳より前に作られたぶんは台帳に載っていないので、下地の名前と完全一致
するものを拾って掃除する（`ledger.legacy_ids`）。名前は「流れ者のミレイユ」
のように固有性が高い。部分一致では拾わない。

##### 決めたこと

| | |
|---|---|
| 決着したら | 当てても外してもキャスト全員を消す。セーブは事件の前に戻る |
| `ARREST_CULPRIT` を切ったとき | 犯人だけ町に残す（設定の意味を保つ）。台帳に「残す」と書いて掃除の対象から外す |
| パーティーに居る者 | 消さない。連れ歩いている相手の参照を切ると何が起きるか分からない |
| 置き去り | 世界を読み込んだ後の1回だけ掃除する。事件の最中に人が消えると訳が分からなくなる |
| 画面 | 黙って消さない。「町を離れていった」と出す ― 消えたこと自体は世界の変化 |

> **「増えていく」は、足すときではなく**足したものを誰が片付けるかを
> 決めていないときに問題になる。作る経路を書いた時点で、消す経路も
> 一緒に決めておくべきだった。

#### 会話の中身とヒントが噛み合わない（2026-08-04）

「会話内容と得られたヒントが全くかみ合わない」（利用者の指摘）。
原因は2つあり、どちらも「手がかりは会話の中身ではなく行動で立つ」という
作りと、実際の会話とのあいだの隙間だった。

##### ① 指示が条件付きなのに、手がかりは無条件で立っていた

証言者に差し込む文が「尋ねられたら、自分が見た・聞いたこととして話す」
だった。ところが手がかりが立つ条件は「その人物と会話した」という行動なので、

> プレイヤーが尋ねなければ相手は何も言わないのに、
> 会話を閉じた瞬間に「分かったこと」だけが出る。

判定を会話の中身に寄せる道もあるが、それは `305_` が4周外した路（AI に
判定させる）に戻ることになる。判定はこちらが持ったまま、AI の側を確実に
する ― 「尋ねられていなくても、世間話のついでに自分から切り出す」に
変えた。

> **AI に「条件付きで」と言ったなら、こちらの判定も同じ条件にする。**
> 片方だけ無条件だと、噛み合わないのは当たり前だった。

##### ② 印が残ったまま、別人との会話で発火していた

印（`state['asking']`）は LLM の呼び出しで立ち、会話終了で消える。だが
会話が閉じられずに終わることがある（画面が変わる・中断する）。すると
印が残り、次に別の誰かとの会話を閉じた瞬間に、前の相手の手がかりが出る。

`ASK_TTL`（古い印を捨てる仕組み）は宣言されていたが一度も使われていな
かった ― `at` に時刻を控えるだけで、比べる側が無かった。

直したのは2点で、どちらも入れる:

| | |
|---|---|
| 相手の id を突き合わせる | 閉じた会話の相手が印の相手と違うなら発火しない。印は捨てずに残す ― 相手のところへ戻れば、その会話を閉じたときに出る |
| 古い印は捨てる | `ASK_TTL` を実際に比べる。相手の id が取れない版でも効く最後の網 |

##### この修正で踏みかけた罠

相手の id を `frames.attr(manager, "in_conversation_id")` で読んだが、
`frames.attr` は属性が無いと `'<missing>'` という文字列を返す。
そのまま id として扱うと「相手は居るが誰とも一致しない」になり、
手がかりが永久に立たなくなる。検査を書いていて掴まえた。

> **「取れなかった」を「取れた」と区別できない形で受けない。**
> 既定値が偽値でない関数は、必ず明示的に見分ける。

#### 事件の描写を LLM に書かせる（2026-08-04）

下地の8人から選ぶ作りだったので、何度遊んでも同じ顔ぶれが出た。MOD から
LLM を直接呼び、その事件専用の人物と文章を書かせる形にした（利用者の要望・
2026-08-04）。

##### 既存プロンプトの流用は要らない ― 汎用の入口がある

```
scripts.llm.llm_manager:send_request(manager_name, message, structure,
                                     max_tokens=16384, timeout=None)
scripts.llm.llm_manager:create_model(model_name, /, **field_definitions)
```

`manager_name` / `message` / `structure` の全部をこちらで決められる。
`manager_name` は `output_data/<世界>/<主人公>/<名前>/` のログ先になるので、
`mod_city_case_writer` という独自の名前を使えば、何を頼んで何が返ったかが
そのまま残る。この MOD が同梱 MOD で初めて LLM を直接呼ぶ。

`create_model` は pydantic のもの。構造化出力の型を自分で組める。ただし
`Literal` は使わない ― 空の `Literal[]` は pydantic が拒否してゲームごと
落ちる（`203_probe_create_model` が押さえた落ち方）。型は全部 `str` にして、
縛りは検算側で持つ。

##### 境界 ― 論理は1文字も渡さない

| | |
|---|---|
| コードが決める | 犯人・容疑者の特徴・どの事実が誰を消すか・手がかりの必要性と解けること・言い分の裏が取れるか |
| LLM が書く | あらまし、容疑者の人となり（名前・職・来歴・人柄・立ち絵の語）、特徴の手がかりの言い回し |

渡すのは「見た目の指定」と「触れてほしくない語」だけ。犯人も手がかりの
効き先も渡していないので、何が返っても事件は壊れない。最悪でも「文章が
下手な事件」で、解けない事件や矛盾した事件にはならない。

##### 検算 ― 2つとも確かめる

「髪が黒い」を頼んだのに「黒髪の大柄な女を見た」と返ってくると、渡して
いない特徴まで漏れてその1文で犯人が決まり、推理が消える。

1. 頼んだ特徴の語が入っているか
2. 他の軸の語が入っていないか

落ちたらその1本だけ定型に戻す。全部捨てないのは、1本の失敗で他の出来まで
巻き添えにしないため。人物のほうは逆に1人でも欠けたら全部捨てる ―
一部だけ下地で埋めると「この人だけ文体が違う」という綻びになる。

##### 書かせないことにしたもの

| | なぜ |
|---|---|
| 言い分（その晩どこに居たか） | 論理の一部（犯人だけ裏が取れない）。人となりと同じ応答で書かせると、AI が犯人を無意識に怪しく書いてタダで割れる |
| 裏取りの手がかりの文 | 特定の容疑者の名を挙げて消す文なのに、名前は同じ応答で作らせている最中でまだ無い。返るのは誰も指していない文になり、拾っても誰も消せない。検算で弾くのではなく最初から頼まない（頼んでから捨てると待ち時間が丸ごと無駄） |

##### 待たせるあいだ画面を止めない／ただし触らせない

推論は数秒〜数十秒。押下と同じ流れで待つとゲームが固まるので、別スレッドで
書かせ、返ってからメインスレッドに戻って事件を始める（`ui.Screen.schedule`）。
顔ぶれは待ちに入る前に組む ― 後で組み直すと、書かせた人物と実際に立つ
人物が別物になる。

固まらない代わりに、選択肢は押せるままになる。書いている最中に町を出たり
別の依頼を受けたりできてしまうので、ゲーム自身と同じ待機表示にする
（`ui.Screen.busy_on`。`.` → `..` → `...` を全枠に出し、`is_button_enabled` を
落として送信ボタンも無効にする。利用者の指摘・2026-08-04）。

##### 見張りが飛ばなかった

`Clock.schedule_once(..., 135)` で予約した強制解除が、実機で飛ばなかった
（15:26 に予約、15:36 になっても記録が無い。ゲーム自体は生きていた）。
理由は掴めていないが、掴めていなくても直せる:

> **1本の予約に安全装置を託さない。**画面を塗り直すたびに通る経路
> （`offer`）でも期限を点検するようにした。予約が飛べばそちらが早く、
> 飛ばなくても塗り直しで必ず解ける。どちらか片方が生きていればよい形。

> **ロックを掛けるより先に、解ける保証を置く。**
> `send_request` が `timeout` を守る保証はこちらには無いし、スレッドが固まる
> 可能性もある。掛けっぱなしになると選択肢が永久に押せなくなるので、
> `LLM_TIMEOUT + BUSY_GRACE` 秒後に無条件で解く見張りを、`busy_on` と
> 同じ場所で予約している。事件は始めないが操作だけは返す。

`busy_on` の最中は `is_button_enabled` が落ちているので、`when_idle` を使う経路は
そのあいだ待たされる（§2.34 で踏んだ噛み合わせ）。この MOD で `when_idle` を
使うのは会話終了の一言だけで、待機中に会話は起きない。

`offer` は待機中なにもしない ― 全枠が `...` で塗られているので組み替えても
見えないうえ、解けた瞬間に一瞬だけ古い並びが見える。

##### 検証

偽の LLM を差して通しで確認している（`[描写]` の節）。偽物は頼み文を読んで
それに沿った文を返す ― どの軸が頼まれるかは事件ごとに変わるので、決め打ちの
文を返す偽物では通ったり通らなかったりした（実際に不安定になった）。

壊れた応答（`None` / 空 / 人数不足 / JSON でない文字列）でも事件が始まる
ことを4通りで確認。始まらないより定型で始まるほうがよい。

待機とロックの検証だけは偽の `kivy.clock.Clock` を差して非同期の経路を通す。
入れないと `has_clock()` が偽になり、その場で待つ同期の道を通ってロックを一度も
踏まない。予約は溜めておいて手で進める形にしてあるので、「まだ返ってきていない
状態」をそのまま検査できる ― 返ってこないまま見張りだけを走らせて、
ボタンが戻ることまで確認している。

> **LLM を使うかどうかより、「何を渡さないか」のほうが設計。**
> 論理を渡さなければ検算は軽くて済み、失敗しても degrade するだけで済む。

#### 思い違いの証言 ― 消し込みを推論に変える（2026-08-04）

候補を増やしても面白さの伸びには限りがある、という判断（利用者）。実測でも
40件中39件が手がかり2本で、1件は「2箇所で聞いて表を消し込む」だけだった。
語彙をいくら増やしても、操作は最後まで集合の絞り込みのまま。そこが天井。

そこで証言の1本を間違いにした。

```
犯人は小柄だった        → 大柄の2人が消える
犯人は袋を提げていた    → 手ぶらの1人が消える
犯人の髪は黒かった      → 残った1人も消える   ← 全員消えた
```

全部信じると誰も残らない。ここで初めて操作が変わる ―
「当てはまらない者を消す」から「どれが嘘かを見つける」へ。

##### 一意に決まらないなら混ぜない

「嘘を外せば1人残る」だけでは足りない。真の証言を外したときにも1人残ると、
どちらが嘘か決められない。だから組む時点で3つとも確かめ、満たさない置き方
には混ぜない（`resolves_once`）:

  1. 全部信じると誰も残らない（合図が立つ）
  2. 嘘を外すとちょうど犯人1人
  3. 真の証言を外したときは1人にならない（0人か2人以上）

3つ目が要点。これを見ないと「どちらを外しても1人」という、当てずっぽうでしか
決められない事件が出る。検証の作り物を書いていて自分で踏んだ ―
手で組んだ例が最初この条件を満たしておらず、検査が落ちて気づいた。

##### `eliminated` から犯人を引く細工をやめた

以前は保険で犯人を除外集合から引いていた。真の事実は犯人を消さない（事実は
犯人についてのものなので当然）ので無害だったが、思い違いはわざと犯人を消す
ので、引いてしまうと食い違いそのものが見えなくなる。

##### 実測

60件回して組めなかった事件は0件（歩留まりの低下なし）。思い違いあり31件・
全部真29件（設定 50%）。手がかりは3本が40件・2本が20件で、1件の長さも延びた。

嘘が真の証言と同じ軸に落ちることがあり、そのときは直接矛盾する
（「酒のにおいがした」と「煙のにおいがした」）。狙って作ってはいないが、
いちばん読みやすい形になる。

> **遊びを深くするのは、選択肢の数ではなく操作の種類。**
> 属性を8軸から16軸にしても消し込みは消し込みのまま。1本を嘘にするだけで、
> 同じ材料が別の遊びになった。

#### 候補を増やした ― 効くのは「軸」より「値」（2026-08-04）

さらに増やせるかを測ってから広げた。

| 増やすもの | 手間 | 効き |
|---|---|---|
| 軸の値（2→3） | 小。コード変更ゼロ | 最大（配り方が 2^12 → 3^12 で 130倍） |
| 題材 | ほぼゼロ | 線形（8→16 で2倍） |
| 軸そのもの | 中（言い換えの衝突） | C(N,3) で効く（8→12本で 3.9倍） |
| 1件で引く軸 | — | やめる（一覧が読めなくなる） |

軸を足しても一覧の語数は増えない（引くのは常に3本）が、値を足すと配り方の
幅だけが跳ねる。読みやすさの天井を上げずに幅を広げられるので、ここが
いちばん効率がよい。

7軸を3値にし、題材を16本、言い分を 公16／単独10 にした。

```
軸の引き合わせ      56 通り
題材 × 引き合わせ  896 通り
4人への配り方      20,804,931 通り
題材まで掛けて     332,878,896 通り
```

軸を足すときの唯一の壁は言い換えの語が他の軸と衝突しないこと（`carry` の
「大きな袋」が `build` の「大きな」と衝突して正しい文が捨てられた例がある）。
検査が捕まえるので、足して回して赤が出たら語を選び直すだけで済む。

> **「増やせる形」を作ったら、次は「どれを増やすと効くか」を測る。**
> 同じ手間でも桁が違う。ここでは値を増やすのが軸を増やすより 30倍以上
> 効率がよかった。

#### 双子をやめたら、もっと悪い漏れが出た（2026-08-04）

「双子設定は面白さに寄与しない」（利用者の指摘）。犯人と特徴が完全に一致
する者を必ず1人置いていた ― 特徴だけで犯人を決められなくして、裏取り
（アリバイ）を要る形にするため。一覧に同じ行が2つ並ぶだけで、そこから考える
ことは増えていなかった。

外したので、それを支えるためだけに在った「裏取りが必ず1本要る」も一緒に外れた。
裏取りは、特徴で消しきれない者が居るときにだけ出るようになった。

##### 代わりに出た漏れ ― 犯人が「多数派」で割れる

素直に「他の者は犯人と1軸だけ違う」形に置くと、条件は綺麗に満たされる。
どの手がかりも1人だけを消すのでどれも抜けないし、余る軸も無い。

```
犯人   a1 b1 c1     ← a1 が3人、b1 が3人、c1 が3人
2人目  a2 b1 c1
3人目  a1 b2 c1
4人目  a1 b1 c2
```

犯人は「どの軸でも多数派」の唯一の1人になる。一覧を眺めるだけで、
手がかりを1本も拾わずに当てられる。双子よりはるかに悪い。

これは偶然ではなく必然だった。手がかりが「どれも抜けない」ためには
1本ごとに固有の1人を消す必要があり、手がかりの数が容疑者の数と同じなら、
全員が1軸だけ違う形しか残らない。

##### 配るのをやめて、選ぶ側に回った

直し方は「配り方を工夫する」ではなく、どの手がかりを使うかを後で選ぶ
（`choose_facts`）。特徴は自由に振り、覆えて・どれも抜けない部分集合を
選んで手がかりにする。選ばなかった軸は一覧に残って赤鰊になる ―
見た目は違うのに、それを言う証言が無い。

> **制約を満たす形が1つしかないなら、その形自体が答えになる。**
> 「条件を満たすように配る」と、配り方から解が読める。
> 配るのは自由にして、条件は選ぶ側で満たす。

実測 40件で、一覧だけで割れる事件は 0件・見分けの付かない組も 0件。
手がかりは2本が 34件、3本が 6件（3本になるのは裏取りが入るとき）。

##### この直しで2つ壊した

- `pick_clues` が候補を組み直していた。選んだ部分集合を渡しているのに、
  中でもう一度全候補を作っていて、重複した手がかりが戻った
- 裏取りが居ない人物を指した。`build_cast` は AI に書かせる前に走る
  ので、そこで文に焼いた名前は下地のもの。`dress` で入れ替わった後は
  別人を指す。名前が確定してから組み直すようにした

> **順番のあるものを前倒しで文字列にしない。**
> 名前が後で変わるなら、名前を含む文はその後で組む。

#### 一覧に意味の無い語が並んでいた（2026-08-04・実機）

材料を JSON に出した直後の実機で「犯人の特徴が被りすぎ」（利用者の指摘）。

```
68 エレーナ  足を引きずる・低い声・煙のにおい・女   ← 犯人
69 リナ      足を引きずる・低い声・煙のにおい・女   ← 双子（設計どおり）
70 ゴードン  足を引きずる・甲高い声・煙のにおい・男
71 オーリン  足を引きずる・低い声・潮のにおい・男
```

`足を引きずる` が4人とも同じ。読む側にとっては意味の無い1語が全行の
先頭に並んでいた。

##### 本数の出し方が間違っていた

特徴で見分ける必要があるのは`人数 - 2` 人だけ。犯人と、犯人と全部同じ
双子は特徴では分けられない（裏取りで分ける）。そして手がかりは「どれも
抜けない」ことを求めるので、1本が1人だけを消す形に落ち着く ―
つまり使える特徴の手がかりは `人数 - 2` 本まで。

4人に3本引けば、1本は必ず余る。余った軸は使い道が無く、
「全員同じ値」になって一覧を濁す。

`patterns.axes_wanted(人数)` で `人数 - 2`（上限 `AXES_PER_CASE`）を引くように
した。4人なら2本。併せて、振り方の偶然で揃った場合のために
「引いた軸がどれも何かを分けているか」も組む条件に足した
（`all_telling`）。性別も一覧に出るので同じ扱いにしている。

> **「多いほど豊かになる」は、絞り込みの遊びでは逆になる。**
> 使い道の無い属性は、選択肢を増やさずに読む量だけ増やす。
> 並べる語の本数は、増やせるかではなく何本が意味を持てるかで決まる。

なお性別は一覧に出るが手がかりにはならない（人物に付いてくるもので、
引く軸ではない）。赤鰊として機能するので残してあるが、全員同じでは
ただの余白なので、上の条件に含めた。

#### 受け皿の道だけが壊れていた（2026-08-04・実機で起動せず）

材料を JSON に出した直後、実機で事件が始まらなくなった。検証は 307件
全部通っていたのに。

```
KeyError: 'short'
  city_case.py:515 in draw_axes  → patterns.py:250 in tables_for
patterns: 1 incident(s), 2 axis/axes, 8 person/people   ← ファイルを1つも読めていない
```

原因は2つが重なっていた。

① `ctx.mod_dir` を押されてから読んでいた。ローダの註に
「`apply()` の外では `None` になるので、フォルダを後で使うなら `apply()` の中で
控えておく」と書いてあるとおりに踏んだ。材料を読むのはボタンが押されてから
なので、`None` を掴んでファイルが1つも見つからなかった。

② 受け皿（`BUILT_IN`）を素通しで使っていた。ファイルは `read_axes` を
通るので `short` が補われるが、既定値は通らないので抜けたまま。

##### なぜ検証を全部通ったのか

検証の `FakeCtx` は常に `mod_dir` を持っていた。だから受け皿の道が
一度も通しで走っていない。①が無ければ②は表に出ず、②が無ければ①は
「材料が同梱のぶんだけになる」で済んでいた。2つ揃って初めて落ちた。

> **受け皿は、普段通らないからこそ壊れていても気づけない。**
> 用意しただけで安心せず、受け皿だけで通しで動くことを検査に入れる。
> `mod_dir` を持たない `FakeCtx` を1つ足して、事件が最後まで組めることを見る
> ようにした。

直しは2つとも入れた。`apply()` の中で `mod_dir` を控え、既定値も
ファイルとまったく同じ読み方（`normalise`）を通す。

> **受け皿は本番と同じ口から入れる。**別の入口を作ると、片方にだけ手を
> 入れたときに形がずれる ― `short` を足したときに起きたのがまさにこれ。

#### 頼み文をその町の実データに接地させた（2026-08-04）

「もっと本格的な RAG を目指すべきか」を検討した結果、古典的な RAG は割に
合わないと判断した（利用者と合意）。理由は量:

| | |
|---|---|
| 1件の事件が持つ知識 | 11件 / 163文字 |
| 会話1回のプロンプト | 約 1,200文字 |

RAG は「入りきらない量から関連するものを選ぶ」ための道具で、入りきるなら
選ぶ必要がない。検索を挟むぶん外す機会だけが増える。

代わりに安くて効くほうをやった ― 頼み文をその町の実データに接地させる。
渡すのは世界と町の説明・実在する施設と主の名前・既に居る人物の名前。
「新しい場所を作らない」「同じ名前を付けない」と併せて指示する。

##### ついでに1つ直った

「町」としてギルドの施設名を渡していた。実機のログに
`【町】鉄錆の徴収所` と出ている。町の名前は `Area.name` にあり、
`Area.descriptions` には `overview` / `facilities` の説明まで入っていた。

> **接地できる材料が在るのに使っていなかった。**「AI に書かせる」を作った
> ときに渡したのは世界名と町名だけで、その中身を見に行っていなかった。
> 生成の質を上げる前に、渡せるものを渡しているかを先に見る。

なお、ゲーム自身は既に検索の仕組みを持っている（`text_to_embedding` /
`find_most_similar_key` / `character_knowledge_retrieval` /
`conversation_facilitator_after_retrieval`）。作るのではなく載る話に
なるので、次に進むならそこ（`Character.knowledges` に事実を入れて、
retrieval が拾ったかどうかで手がかりを立てる）。効果を見てから判断する。

#### 事件の材料を JSON に出した（2026-08-04・通しプレイ後）

材料がコードに焼き付いていたので、何度遊んでも同じ形の事件になっていた ―
盗みだけ、髪と体格だけ、同じ8人。1件ごとに抽選して組み合わせる形にし、
候補は `patterns/*.json` に出した（利用者の要望）。ファイルを足せば幅が増え、
コードは触らなくてよい。

| ファイル | 候補 | 同梱 |
|---|---|---|
| `incidents.json` | 何が起きたか（盗み・付け火・毒盛り…） | 16 |
| `traits.json` | 目撃される特徴の軸（髪・体格・服の色・かぶり物・持ち物・足取り・声・におい） | 8軸（7軸は3値） |
| `whereabouts.json` | その晩どこに居たか（裏が取れる16／取れない10） | |
| `cast.json` | 下地の人物 | 16 |

芯は「軸を毎回引き直す」ところ。1件につき3軸を引くので、髪と体格で絞る回も
あれば、服の色と持ち物と声で絞る回もある。同じ形の推理が続かない。

##### 語彙を増やしても謎が壊れないのはなぜか

検算が材料の側に無いから。必要性・解けること・重複の無さは `build_cast` が
軸の中身を知らずに確かめる。だから軸を足しても、確かめる側は書き換えなくてよい。

材料の側で持っているのは「材料として成立しているか」だけ（値が2つ以上あるか、
語と文が揃っているか）。壊れた項目は落とし、束ごと空になったら同梱に戻る。

##### 増やしたときに初めて出た問題

- 言い換えの語が軸をまたいで衝突する。`carry` の「大きな袋」が `build` の
  「大きな」と重なり、持ち物の手がかりが「体格に触れた」と誤判定されて捨てられる。
  語を選び直して解消し、衝突が無いことを検査に入れた（軸を足す人が同じ穴に
  落ちないように）
- 一覧が読み解けなくなる。3軸を連体形のまま繋ぐと
  「目立つ色の服の煙のにおいのする袋を提げた女」になる。集めた事実と突き合わせる
  のがこの遊びの本体なので、並べ方で邪魔をしない ―
  「目立つ色の服・煙のにおい・袋を提げている・女」と区切ることにした

> **候補を増やすと、候補どうしの干渉が新しい失敗の種類になる。**
> 1つずつ見れば正しい語でも、隣に置くと意味が濁る。増やせる作りにしたなら、
> 増やした人が踏む穴を検査に含めておく。

#### 告発を専用の画面にした（2026-08-04・通しプレイ後）

告発の選択肢を施設の選択肢に混ぜて並べていた。誰を告発するかを選ぶ場面
なのに「出る」「会話する」「クエスト掲示板」が並んでいて、何をする画面なのか
分からない（利用者の指摘）。その画面はこちらのものだけにした。

降り方も2つに分けた。

| ボタン | どうなるか |
|---|---|
| やめる（もう少し考える） | 告発だけをやめる。事件は続く |
| 諦める（調べを打ち切る） | 事件そのものを終わりにする。キャストは全員引き上げ、報酬は無く、真相も明かさない |

真相を明かさないのは、告発すれば当たっても外れても分かる（外したときも
犯人を告げる）ため。そこまで踏み込まずに降りたのなら、答えは持ち帰れない
ほうが筋が通る。打ち切りでキャストを全員引き上げるのは、誰も捕まっていない
ので `ARREST_CULPRIT` の出番が無く、残すと作った NPC が町に溜まるから。

##### 画面を預かると、返す先の面倒まで見ることになる

ゲームの選択肢を退けるので、元の並びを預かって、抜けるときに返す。
`refresh_choice_buttons` は `app.buttons` を組み直さない（組むのは施設の側）
ので、捨てると戻ったときに選択肢が消えたままになる。

踏んだ穴が2つ:

- 施設の目印まで消えた。`is_facility_screen` は `FACILITY_MARK` を見て
  いるが、退けた後は残っていない。そのまま弾くとやめても戻せない
- 別の場所へ移ったときに預かり物が漏れる。ゲームが自分で画面を組み直した
  後に書き戻すと、関係の無い画面に古い選択肢が生える。いま出ているのが
  自分の画面のときだけ戻す（全部が自分の印を持っているか見る）ことにした

> **画面を丸ごと預かる作りは、「返す」より「返さない」判断のほうが難しい。**
> 預けた相手がもう居ないことを見分けられないと、無関係な場所を壊す。

#### 入って即抜けるだけで解が割れた（2026-08-04・実機2回目）

生成は通ったが、会話に入って即座に抜けるだけで手がかりも言い分も手に入った。
とくに言い分は犯人だけ裏の取れない場所を言うので、4人を出入りするだけで
聞き込みを一切せずに犯人が割れた。

原因は印を立てる場所。`conversation_starter`（＝会話に入った時点で走る第一声）で
事実を差し込み、同時に印まで立てていた。会話終了で印が消化されるので、
間に何も起きていなくても手がかりが入る。

直し方は「印はプレイヤーが実際に何か尋ねたときだけ立てる」
（`conversation_facilitator` ＝ `brief`）。第一声には事実そのものを載せず、
「何か知っていそうだ」と匂わせるだけにした（`TEASE_TEXT`）。匂わせも
無くすと、誰に聞けばよいか分からないまま町を歩くことになる。

> **画面に出たことと、控えに入ることを必ず一致させる。**
> 「読んだのに数えられない」も「聞いていないのに数えられる」も、
> 同じ1点（どこで印を立てるか）から生まれていた。

容疑者の言い分も同じ扱いに揃えた（「問われたら答える」→「その会話の中で
自分から語る」）。印が立つのが尋ねたときだけになった以上、その1回で必ず
言わせないと今度は逆の食い違いになる。

#### 目撃情報の検算が厳しすぎた（2026-08-04・実機2回目）

書かせた3本が3本とも落ちた（`facts 0/3`）。

```
writer: fact 1 does not mention '大柄な': '夜中に、大きな影が路地を通り過ぎるのを見た。'
writer: fact 2 does not mention '黒髪':   '暗闇の中で、黒い髪が揺れているのが見えた。'
```

どちらも中身は正しい仕事なのに、語の完全一致で捨てていた。言い換えを
認める表（`TRAIT_HINTS`）を持たせ、頼み文にも同じ表を見せるようにした。

> **緩めるときは、締める側も同じ語彙で緩める。**
> `TRAIT_HINTS` は「その特徴を言えているか」と「他の特徴に触れていないか」の
> 両方に使う。片方だけ広げると、言い換えを認めたぶんだけ漏れも見逃す。

#### 自由施設をやめた（2026-08-04）

告発の場面をゲームの自由施設（`FreeFacilityManager`）に組ませていた。聞き込みを
会話へ移した後は場面がこの1画面だけになり、中身も「容疑者を並べて1人
選ばせる」だけ ― DSL の分岐も `flag_set` も使っていない。それでいて代償が
残っていた（利用者の指摘・2026-08-04）。

| 代償 | |
|---|---|
| 押すと詰む経路があった | `scripts.free_facility` がまだ import されていないか `lint_program` が無いと場面を組めず、告発ボタンを押すと「（いまは調べていることは無い）」と出る。事件は進行中なのに。自由施設に一度も入っていないプレイで普通に踏む |
| ゲームの施設を壊す危険 | `free_*` を横取りする以上、判定を1つ誤れば実在の施設が動かなくなる。1画面のためにこれを負い続けていた |

判定は元から「押された識別子を突き合わせるだけ」なので、場面をやめても
判定は1行も変わらない。自前のボタン（`START_LABEL` などと同じ経路）に
移して、`scenes.py` とフック2本（`_lookup_program` /
`FreeFacilityManager.__init__`）と `PROGRAM_ID` を丸ごと落とした。

> **道具は「使えるから使う」ではなく「必要だから使う」。**
> 聞き込みを会話へ移した時点で必要は消えていたのに、動いているという
> それだけの理由で残していた。機能を削ったら、そのために引いた依存も
> 一緒に見直す。

##### やめたことで生えた要件

自前のボタンは同じ画面でも並べるものが変わる（告発の相手を選んでいる間は
容疑者、それ以外は「気になる噂を聞く」など）。`offer` は「自分のボタンが既に
在るなら何もしない」だったので、告発を押しても容疑者が出てこなかった。
在るものと出したいものを見比べて、違うときだけ差し替える形にした。

容疑者のボタンには決まった接頭辞（`告発する ― `）を付けてある。ボタンは
セーブに焼かれることがあり、そのとき印は落ちる（`ui.Screen.prune_stale`）。
残骸を見分ける手段は文言しかないが、容疑者の名前は事件ごとに変わるので、
固定の頭が無いと前方一致で拾えない。

検証は `scripts.free_facility` を一度も作らずに 361件を通している ―
「無くても通しで解ける」ことがそのまま担保になる。

#### 聞き込みを会話にしたときの2つの落とし穴

① MOD のボタン経由でしか効かなかった。知識の差し込みを「こちらが
起こした会話か」で判定していたので、プレイヤーが普通に「会話する」で
話しかけると何も起きない。話しかけ方ではなく相手の id で判定する形に
直した（手がかりごとに証言者を控える）。

②' 会話で成立するなら、専用のボタンは要らない。「聞き込みをする」を
出していたが、普通に話しかけて同じことができる以上、重複していたうえに
「押せば手がかりが入る」という誤解も生んでいた（利用者の指摘・2026-08-04）。
外した結果、シーン形式の聞き込みも起動経路を失ったので一緒に片付けた
（`scenes.investigate` と `ASK_MODE`）。遊びの経路が1本になった。

② 進行中の事件が古い版のもので、照合が永久に外れた。控えは注入をまたいで
残るので、後から足した項目（証言者）は `None` のまま。読んだ時点で
埋めるようにした。

> **控えに項目を足したら、既にある控えをどうするかを同時に決める。**
> 捨てるか埋めるか。決めないと「新しい事件は動くのに、続きは永久に動かない」
> という最も分かりにくい壊れ方になる。

#### 計測が自分の条件で自滅した

届かない原因を追うトレースを仕込んだが、発火条件を「印が立っているとき」に
していた。その印を立てるのをやめた直後だったので、1行も記録されなかった。

> 計測の発火条件は、**計測したい対象と独立に**すること。

#### いまの作り

| | |
|---|---|
| 判定 | 押された選択肢の飛び先ラベル（`resume['label']`）と id の照合だけ。AI は描写しかしない |
| 真相 | 事件を組む時点で確定。組んだ直後に「全部集めれば1人に絞れるか」を検算する |
| キャスト | 事件のために生成（GAME.md §2.23）。犯人は `is_dead` で退場、無実の者は町に残る |
| 告発 | 自前のボタンだけ。ゲームの自由施設（`FreeFacilityManager`）には一切触らない |
| 材料 | `patterns/*.json` から1件ごとに抽選（題材・特徴の軸・言い分・下地の顔ぶれ）。読めなければ同梱に戻る |
| セーブ | 事件の控えも NPC の台帳も `out/` だけ。`flag_set` も `free_facility_programs` も使わない。生成した NPC は事件のあいだだけセーブに載り、決着すると消える |

オフライン検証は `tools/test_city_case.py`（361件）。上の失敗はすべて
再現する形で入れてある（辞書を1つに賭ける実装、ボタン経由でしか効かない
実装、証言者を持たない控え、採番が進まない実装、群衆、詰んだ事件、
実機で出た「重複した手がかり」の配り方そのもの、
項目を1つ欠いたひな型が並びを崩すこと）。

汚染については5件続けて解いて NPC の数が毎回元に戻ることを検査している
（`[後始末] 繰り返してもセーブが太らない`）。「消える」ことだけでなく
事件中はちゃんと増えていることも同時に見ないと、そもそも作れていない
場合に通ってしまう。

並び順の検査は実際のセーブから起こした33項目をテスト側に直接持たせて、
1つずつ突き合わせている。MOD 側の定義を読んで比べると「自分と同じか」を
確かめるだけの検査になるため。
