## §1 症状と原因

`life_log` が育った NPC と会話すると（宿屋での交流など）、『リクエストを再実行』が
出たまま先へ進まなくなる。

原因はプロンプトがコンテキスト長を超えていること。NPC の `life_log` は
**毎回・全文**会話プロンプトに載る（`out\npc_memory.log` の
`life_log=全文相当(n/n)`）。ゲームは llama-server を必ず `--ctx-size 16384` で
起こすので、そこを超えた要求はサーバに撥ねられる。再実行しても**同じプロンプトを
送り直すだけ**なので、必ず同じ所で落ちる。

`life_log` が膨らむ主因は要約そのものではなく累積コピー（GAME.md §2.25）。
`current_log` は「1件目の全文を含む2件目」という形で伸び、日付が変わると
`str()` の丸写しで `life_log` の1エントリへ移る。

## §2 設定欄は `--ctx-size` を剥がす（実測・2026-08-12）

ゲームの設定画面には起動パラメータの欄があり、`config.json` の
`ai_setting.server_parameters.<バックエンド名>` に入る。**ここに書いた
`--ctx-size` だけが、実際のコマンドラインから消える。**

```
欄に書いた値
    --n-gpu-layers 999 --parallel 2 --ctx-size 32768 --cache-reuse 256 ...
実際のコマンドライン
    ... --ctx-size 16384 ... --n-gpu-layers 999 --parallel 2 --cache-reuse 256 ...
                  ^^^^^ ゲームの値が残る          ^^^^^^^^^^ 他はそのまま渡る
```

`--parallel` も `--cache-reuse` もサンプリングも渡るので、欄そのものは効いている。
ゲームが自前の `--ctx-size` と衝突する指定を取り除いていると読める。

**書く欄を間違えやすい。** 2次元（バックエンド × 種別）になっていて、効くのは1つ:

- 行 = いま選んでいるバックエンド。`ai_setting.local_model_setting.llm_backend`
  （実機では `llama-cpp-completion-cuda`）。`self_server` は「任意 OpenAI 互換
  サーバー」用で、ローカル実行では読まれない
- 列 = `server_parameters`（起動引数）。`environment_setting` は環境変数なので、
  引数を書いても渡らない

**ファイルも2つある。** ゲームが読み書きするのは
`%LOCALAPPDATA%\Darmabeko\Instantale\config.json`。インストール先
（`...\Epic Games\Instantale...\config.json`）にも同じ形のものがあるが、
そちらは初期テンプレートで、書き換えても効かない。

## §3 窓とスロットの関係（実測・2026-08-12）

**`--parallel` を書くかどうかで、KV の持ち方そのものが変わる。**
書かなければ llama-server は `n_parallel=auto` を選び、**統合 KV**（4スロットが
1つのプールを共有）になる。明示すると統合が外れ、スロットごとに専用のプールを
確保する。起動ログの `kv_unified` に出る。

| 起動引数 | `kv_unified` | `n_ctx` | `n_ctx_seq`（1リクエストの窓） | KV |
|---|---|---|---|---|
| `--ctx-size 16384`（ゲームの既定） | true | 16384 | 16384 | 320 + 900 = 1220 MiB |
| `--ctx-size 16384 --parallel 1` | false | 16384 | 16384 | 320 + 300 = 620 MiB |
| `--ctx-size 65536 --parallel 4` | false | 65536 | 16384 | 1280 + 1200 = 2480 MiB |
| `--ctx-size 32768`（`--parallel` なし） | true | 32768 | 32768 | 640 + 900 = 1540 MiB |

読み取れることが3つある。

- **窓は縮まない。** `--parallel` を書かなければ、`--ctx-size` の値がそのまま
  スロットごとの窓になる。掛け算で埋め合わせる必要は無い
- **明示するとスロット数倍の KV を取る。** 同じ窓 16384・同じ4スロットでも、
  統合なら 1220 MiB、明示すると 2480 MiB。得るものは無い
- **1本にすると最小になる。** 620 MiB。統合の半分で、窓は同じ

したがって `--ctx-size` に掛け算をしてはいけない。渡し方は3通り（`SLOTS`）:

    SLOTS = 0   --ctx-size CTX_SIZE                            統合・4本で共有
    SLOTS = 1   --ctx-size CTX_SIZE --parallel 1               専用1本・KV 最小
    SLOTS >= 2  --ctx-size (CTX_SIZE*SLOTS) --parallel SLOTS   専用 SLOTS 本

`SLOTS=0` にするときは、既に argv にある `--parallel` を**外す**必要がある。
統合は「旗が無いこと」が条件だから。設定欄から `--parallel 1` が渡ってくる
実例があるので（§2）、足すだけの実装では効かない。

## §4 使い方・設定・困ったとき

`load_order.local.json` に `904_llm_context_size` を足して注入する。

| 設定 | |
|---|---|
| 1リクエストが使える窓（トークン） | 既定 32768。日本語でおよそ1トークン=1.6文字なので、約52,000字ぶん。0 にすると書き換えず、起動引数をログに出すだけになる |
| 同時に持つスロット数 | 既定 1。KV が最小になり、余りを窓に回せる。0 で統合 KV（4本で共有・ゲームの持ち方）、2 以上はスロットごとに専用の KV を確保する（§3） |
| 起動引数をログに出す回数 | 既定 5。書き換えの前後が `out\llm_context.log` に残る |

既定（32768 × 1本）は、素のゲームに対して**窓を倍にしたうえで速くなる**値
（§5）。スロットを増やす方向は損で、このゲームは並列でほとんど走らない（§7）。

適正値はマシンによって違う。`tools\llm_ctx_probe.bat` が候補を順に起こして
実測し、そのマシンで使える最大値を出す。VRAM から溢れてもエラーにならないので、
判定は使用量ではなく速度で行っている。

**効くのは次にサーバが起きるときから。** 既に走っているサーバの引数は変えられない。
注入がサーバ起動より後なら、ゲーム側で LLM を開き直すか、ゲームごと起動し直す。
`apply()` の時点で走っているサーバがあれば、その `--ctx-size` を
`out\modloader.log` に出す。

| 困ったとき | 見るところ |
|---|---|
| 効いていない | `out\llm_context.log` に `[LAUNCH]` が出ているか。出ていなければサーバはこの注入より前に起きている |
| 応答が急に遅くなった | VRAM の溢れ。Windows は溢れても失敗せず共有メモリへ退避するので、症状は「エラー」ではなく「異様に遅い」になる。`nvidia-smi` の空きを見て、窓かスロットを減らす |
| クラウドLLMで使っている | この MOD は何もしない（`llama-server` を起こさないため） |

## §5 実測値（2026-08-12）

**モデルの形**（`gemma-4-26B-A4B-it-qat-uncensored-heretic-UDmerge-Q4_K_XXL.gguf`
のメタデータ）。

```
block_count               30
sliding_window_pattern    [True x5, False, ...]   25層がSWA、5層だけ全文脈
attention.head_count_kv   [8,8,8,8,8,2, ...]      SWA層=8 / 全文脈層=2
key/value_length          512（全文脈層） / 256（SWA層）
sliding_window            1024
context_length            262144（学習時）
```

コンテキスト長に比例するのは全文脈層5層だけで、**20 KiB/token**
（2 head × 512 × K/V × 2byte × 5層）。SWA 層25層は窓 1024 で頭打ちになる。

**日本語の文字とトークン。** `/tokenize` に実データ（`out\npc_memory.log` の
`<出来事>` を含む行）を通して 656文字 → 409トークン ＝ **1トークン ≒ 1.6文字**。
16384 トークンは約26,000字にあたる。

**VRAM と速度（RTX 4070 Ti SUPER 16376 MiB / モデル 13650.92 MiB）。**
同一プロンプト 4402 トークン、生成 128 トークン、各2回の最良値。

| 起動引数 | 窓 | KV | VRAM | 処理 t/s | 生成 t/s |
|---|---|---|---|---|---|
| `--ctx-size 16384`（素のゲーム） | 16384 | 1220 | 15977 | 4226 / 4292 | 94 / 96 |
| `--ctx-size 16384 --parallel 1` | 16384 | 620 | 15378 | 5712 / 6253 | **133 / 127** |
| `--ctx-size 24576 --parallel 1` | 24576 | 780 | 15589 | 5782 / 5844 | 124 / 124 |
| `--ctx-size 32768 --parallel 1` | 32768 | 940 | 15744 | 4216 / 5571 | 126 / 122 |
| `--ctx-size 32768`（統合） | 32768 | 1540 | 15937 | 4088 / 4318 | 93 / 92 |
| `--ctx-size 65536 --parallel 2` | 32768 | 1880 | 15938 | 294 / 369 | **44 / 47** |
| `--ctx-size 65536 --parallel 4` | 16384 | 2480 | 15938 | 496 / 505 | **29 / 29** |

**崖は 15744（正常）と 15938（崩壊）の間**にある。超えるとドライバがシステム
メモリへ退避し、PCIe 越しになって処理が約17倍・生成が約3倍遅くなる。

**採用値は `--ctx-size 32768 --parallel 1`。** 素のゲームに対して窓が倍
（16384 → 32768）、そのうえ処理 +32%・生成 +27%。スロット4本ぶんの KV を1本に
集約するほうが確保量が減るため、両取りになる。

**KV の実寸は理論どおりだった。** 20 KiB/token（全文脈層5本）＋ 300 MiB/スロット
（SWA 層25本・n_ctx に依存しない固定）。起動ログの KV buffer が2行に分かれていて、
比例する側が 16384→320 / 24576→480 / 32768→640 MiB と一致する。

かつてここに「KV を4分の1にしても空きは 26 MiB しか増えない、KV は誤差の範囲」
と書いていたが、**誤りだった**。測った2構成が両方とも VRAM 上限を超えていたため、
nvidia-smi の使用量が天井に張り付いて差が見えなかっただけ。空きが 135 MiB /
161 MiB という値自体が飽和のサインだった。**飽和後の nvidia-smi は当てにならない**
（15977 MiB の素ゲームより 15938 MiB の 65536×4 のほうが3倍遅い）。判定は起動
ログの `KV buffer size` と `compute buffer size` の合計で行う。

**予算の内訳**（ゲームを起動して遊べる状態での実測）。

```
16376  VRAM 総量
 − 350  デスクトップ等（何も起動していない状態）
 − 260  ゲーム本体の描画（ワールド読み込み後。タイトル画面では 155）
 −13651  モデル重み        （起動ログ model buffer size）
 −  533  計算バッファ      （n_batch で決まる。ctx を変えても一定）
 −  275  CUDA コンテキスト等（実測から逆算）
────────
  1307  KV に使える
```

**モデルが変われば結論も変わる。** Qwen3.5-9B IQ4_XS（重み 4373 MiB、SWA 無し）
では余地が桁違いに広く、`--ctx-size 131072 --parallel 4`（窓 32768 × 4本）でも
VRAM 9805 MiB・生成 104 t/s で通る。ただし SWA が無いぶん KV の単価は
**32 KiB/token** と 26B より高い。26B が安いのは30層中25層が SWA で窓 1024 に
頭打ちになるため。単価はモデルごとに測ること。

**llama.cpp 本体の版は関係ない。** 同梱の b8954 と最新の b10369（1400ビルド差）を
同条件で A/B したが、差は ±0〜-2% で利得なし（gemma-4-26B tg 152.89 → 152.94、
Qwen3.5-9B tg 101.45 → 99.12）。遅いときに疑う先はエンジンではなく文脈長。

## §6 未確認

- **窓を広げたあとも `life_log` は増え続ける。** これは時間稼ぎで、根治は
  プロンプト側の刈り込み。刈り込みの閾値は `n_ctx`（§7 の 400 エラーが返る
  境界）だが、どこを削るかは未着手
- **実機で 32768 が保つか。** §5 は単体測定で、ゲームの描画ぶん 260 MiB を
  引いた余白は 367 MiB。立ち絵や背景が増える場面で溢れないかは未確認。
  `nvidia-smi` を遊びながら1度見る
- **`--cache-reuse 256` の効き。** スロットごとに直前のプロンプトが残るので、
  会話・クエスト・`311_` の抽出で前置きが違う場合に当たり外れが出るはず。
  スロット1本にすると全リクエストが同じスロットを使うので、この当たり外れの
  出方が変わる。未計測

## §7 並列の実測（2026-08-12）

**窓を超えた要求は HTTP 400 で撥ねられる。** 黙って遅くなるのではない。

```json
{"error":{"code":400,"message":"request (44002 tokens) exceeds the available context size (32768 tokens), try increasing it",
"type":"exceed_context_size_error","n_prompt_tokens":44002,"n_ctx":32768}}
```

ゲームは同じプロンプトを送り直すので、必ず同じ所で止まり続ける（§1 の裏付け）。

**このゲームは並列でほとんど走らない。** プロキシのログ（`[DIAG]` が有効だった
2026-07-25 の区間）で、リクエストの開始と終了を突き合わせた結果:

| | 値 |
|---|---|
| ペアで追跡できたリクエスト | 62 |
| 同時に走った最大数 | **2** |
| 重なった回数 | 4（全体の6%） |
| 所要時間 | 中央値 1.92秒 / p90 3.96秒 / 最大 97.4秒 |

94%が逐次で、3本以上が同時に走ったことは一度も無い。素のゲームが4スロット
取るのは過剰。`--parallel 1` にしても失われるのは並走だけで、溢れた要求は
llama-server がキューに入れて順に処理する（エラーにはならない）。**6%の
リクエストが数秒待つ代わりに、全リクエストが35%速くなる**取引になる。

この 62 件は 2026-07-25 の記録で、当時と今では有効な MOD が違う。`311_` や
`902_` のように MOD 側から LLM を呼ぶものが増えていれば頻度は上がる。測り直す
なら proxy の `log_diag=1` に戻して数時間遊ぶこと。
